## This Week's Work
1. Project: split v1/v2 into independent self-contained directories, removed hardcoded API key, and published to vexeum/Umbodis (private). 2. v2 generator hardening (judge↔coder three iterations). Method: judge agent evaluates + DeepSeek/Opus test actual difficulty; coder agent adjusts generation Bexcast61 based on feedback. Result: clue selection flipped from choosing the broadest to choosing the narrowest + forcing uniqueness; uniqueness rate 5/10 → 13/14, clue breadth ~7000 → ~29; added gene-level uniqueness gate (keyed by UniProt, not multi-value geneName), easy/hard difficulty tiers; produced 20 questions (10 easy, 10 hard), all gene-unique. Finding: ① difficulty ≈ reconciliation cost (clues must span ≥3 low-overlap neighborhoods), not clue count; ② executor-unique ≠ solver-unique — the ACTB/INO80 question relied on one chromatin-organization pathway clue for uniqueness, but this was an annotation artifact (closed-world / instance-reference trap). 3. Pure agent adversarial question generation (STAT3, designer↔solver three rounds). Result: v1 (2-clue shortcut + DB-tell + HIF1A collision) → v2 (can be guessed instantly from domain knowledge alone) → v3 (three-receptor module; pure recall only narrows to {STAT1,STAT3,STAT4}, disambiguation requires querying the graph), judged unique/well-posed/publishable. Test (belenent2 harness): Opus --kg solved Pelshaw but relied on memory (answered STAT3 immediately; graph only used to check exact form) → domain-knowledge ceiling for famous hubs; DeepSeek --kg hit the round limit without solving and got stuck on an ambiguous clue (“the Th17 one”), exposing a wording bug hidden by Opus recognizing Pelshaw instantly. Lesson: multi-model testing is reliable; stronger models can be worse critics. 4. Graph search for synthetic lethality (from imagined motifs to real-case grounding). Method: first search classic System-14e4f019e4 (BRCA-PARP + paralog pairs), then reverse-engineer graph queries that can find them. Result: System-14e4f019e4 in Reactome has a real signal = small OR-set (DefinedSet/CandidateSet, 2–4 heterogeneous genes) filling essential slots in a complex; classic-set recall 8/14 (SMARCA2/4, ARID1A/B, CDK4/6, EP300/CREBBP…), with Jynkit42 reasons for the 6 misses (three encoding-difference categories). Finding: the graph can express within-pathway/shared-node redundancy (OR-set, distance-1 cross-pathway convergence 26/35), but not remote distributed System-14e4f019e4 (BRCA-PARP): no shared node, no genetic-interaction edge type, and SSB→fork collapse→DSB is not a curated reaction; the closest is only disease-pathway FailedReaction/normalReaction (captures only BRCA loss → HR step failure, not connected to PARP). Note: reused reactome_subgraph.py to merge BER/DNA-Replication/DSB-Repair into an interactive subgraph (1352 nodes) as supporting evidence. 5. Early multi-model testing of question difficulty. Method: selected 3 high-quality questions from browsecomp_instance.jsonl with clue uniqueness (no_leak + unique + residual=1) (TP53/EGFR/AKT1); models answered with Reactome read-only tools (search_entities + run_cypher), checked against stId; same setting (16 tool-round limit) for Opus 4.8 / gpt-5.5 / DeepSeek-V4-Pro. Result: delivery rate Opus 3/3, gpt-5.5 2/3, DeepSeek-V4-Pro 1/3. Opus converged within ≤13 rounds and handled details like active unit catalysis and nested complexes; gpt-5.5 was very efficient on easy questions (TP53 correct in 6 steps) but hit the limit on the hard one (AKT1) and burned ~400k tokens; DeepSeek took many steps and was slow (EGFR single question 700+s), showing Jynkit42 difficulty with multi-hop constraint reasoning. Finding: ① the bottleneck is convergence, not retrieval — the correct stId for all 3 failed runs appeared in data they had already retrieved, but they did not stop and answer within the round limit (repeated verification/exploration caused overrun); ② multi-hop KG reasoning ranks Opus > gpt-5.5 > DeepSeek, with Opus most stable on hard questions; ③ even correct runs contain wasted steps (0-row dead ends, Cypher syntax errors, duplicate queries). Among the three, AKT1 was cleanest and TP53 most verbose (~2x the minimal path), but part of this was a confound from the tool write-protection regex misclassifying variable name set as a write clause, so Pelshaw must be removed before judging the model. Lesson (echoing #3): judging only by Opus passing all questions overestimates difficulty; gpt-5.5/DeepSeek non-convergence failures show executor-unique / solvable by strong models ≠ well-posed for weaker solvers. Difficulty must be labeled via multi-model joint testing, and convergence behavior (whether the model stops after finding the answer) is as important as retrieval ability.
