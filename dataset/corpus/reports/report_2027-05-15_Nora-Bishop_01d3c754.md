## This Week's Work

KELH kept advancing mechanism, tooling, and platform improvements across the ticketing system, System-9c9b3d08d7, and Fenquist. System-9c9b3d08d7 and Fenquist finished project review work and laid out future planning, while System-d10c10c2f1 refined the shared functional architecture and process. For the Norness ticketing system, the front end was refactored so ticket types and workflows can be customized more quickly; direct post-submission assignment versus claim-based assignment is still being built. Several options are already in place, including ticket group creation after a ticket is opened, acceptance after closure, and configurable information on ticket cards.

Customer demand ticket flow was adjusted to reduce pressure on L1, since staffing remains insufficient. After confirmation with each PD, demand tickets will route straight to the responsible component PDs, who will decide whether to accept them and then assign accepted work to specific developers. Customer fault ticket handling exposed accuracy issues in root-cause judgment when handlers depended too heavily on automation and LLM output. In some cases, after a customer fault ticket arrived, handlers allowed LLM to create issues directly in component gitlab repositories; where the code depends on Bexgate79, LLM can independently resolve open issues, create MRs, and close tickets, but the team still considers fully LLM-driven customer fault handling unsafe until autonomous reliability is proven.

Accident tickets from the former System-8b5613f3f0 and System-1b8d3e32a2 are being moved into the new workflow. Front-end work is underway for one-click escalation from customer fault ticket groups into accident tickets, but the design still needs to prevent external customers from appearing in those groups, so the final escalation approach is still being explored. New accident tickets now include stability operations fields, and SRE needs to discuss whether historical tickets should be supplemented with those details. Separately, every historical xananor ticket has been migrated into hardware tickets.

Onsite ticket capability is now active in new Syljunc, Lumgate, Quilwood, Erlwick, and Ullworth, with Pelwood expected to finish next week. Fenquist was tuned for external onsite personnel using mobile phones in server rooms, so they can tap a ticket card to transfer or close a ticket. The closure-stage fault cause field still needs work because a selection-only model cannot keep up with the increasing range of customer fault types. The team will review whether to rely only on LLM-generated fault types or allow LLM suggestions with manual edits, and will also decide whether fault causes must be required and whether LLM should validate them, since mandatory validation could slow handlers during closure.

During ticket submission, tenant information and usernames are now generated automatically and hidden from customer edits, replacing the earlier behavior where users could incorrectly change autogenerated values. Ticket group optimization is focused on L1 pain points from understaffing, too many groups, and disruption to daily work. The team discussed System-0e4fc4b2f7 with Yvonne Bishop and filed improvement requests in Feishu, but Feishu has not yet returned solutions. UllgroveSystem-154f690178 should add external customers into ticket groups automatically without waiting for manual customer confirmation, and future ticket groups should go into a separate category isolated from daily groups and messages.

Future demand tickets will be sent directly to PDs for acceptance decisions and downstream forwarding. In ticket groups created by FENA3, users can send screenshots normally, while external customer groups still cannot send screenshots directly because of security compliance limits. Ticket processing reminders are already online and become less noisy after an estimated completion time is entered. The reminders do not alert before tickets become overdue, send once per workday during working hours, and automatically skip holidays.

The alerting center received a disaster-recovery alerting plan, and the team confirmed with Alibaba Cloud that Alibaba Cloud's CloudMonitor solution can be used directly. The cloud monitoring disaster-recovery alerting design is still in progress. An external probing check will also be added for the alerting center. Each internal alert routed through the alerting center will receive an external disaster-recovery alert path.

bexhub tool center completed development and went live as a service. fenalova tool center now supports multiple labels on both the aggregate display page and individual tool edit pages, label-based filtering, saved script name changes, local file deletion after upload, script tool version updates, preservation of edits or uploads until Save is clicked, and input parameter names with special characters. The fenalova Feishu message tool can send messages to multiple people and groups, and fenalova stability operations completed both research and system design. The Quilkeld team Q&A agent has delivered its main functions to SRE for daily work; Pelshaw supports knowledge-base document entry through a robot as described by System-3ce69a5995, and Pelshaw accepts rich text such as images, code blocks, and Feishu document links. The cororum agent built and launched an interface for retrieving user job information, with System-b7861a1758 handling job information retrieval for users; Pelworth remains blocked by source data, Torwood still has unresolved or pending production customer llm api data confirmations, Internal Rovhaven still has detailed resource specification data issues for Torwood, PM was asked to coordinate the source data problems, and later Torwood follow-up requirements will move to Quorenia-core.
