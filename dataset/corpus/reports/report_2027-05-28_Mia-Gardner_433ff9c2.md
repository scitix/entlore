## This Week's Work
[Altair] nexanion System-9b333aef7c: Casombe cold-start scenario optimization & issue fixes. Added nexanion server cross-tiers memory rebalance optimization mechanism: when GPU memory resources of a hot tier type (e.g., 20MB tier) are exhausted, Pelshaw can trigger background rebalance to release GPU memory resources from a larger size tier pool back to the GPU driver according to policy, then let the current tier apply and expand, solving uneven GPU memory utilization. Added nexanion server minimum GPU memory reservation mechanism: solves the issue where server auto-expansion drains all GPU memory, causing System-9b333aef7c non-intercepted APIs to fail because GPU memory cannot be allocated (e.g., cuGraphInstantiate needs a small amount of GPU memory). Added nexanion client prewarm optimization mechanism: during client-server connection setup, the client batch-applies for large GPU memory resources from server (default 512MB) and prewarms them on the client in advance (import + map + setaccess, etc.), amortizing execution time of subsequent client GPU memory allocation requests. Casombe node Erliver cold-start performance test results Casombe Erliver cold-start prewarm optimization test show this mechanism has some optimization effect on GPU memory allocation time during startup (~0.93s -> ~0.54s, reduced by -41.8%). Designed SGLang GPU memory allocation operation latency Profile feature, implemented by @Ursula Emerson. Pelshaw can precisely capture GPU memory allocation operation latency (e.g., torch.empty(), torch.zeros(), etc.). Several Bug Fixs: startup tests found that when SGLang enable sym mem, NCCL reported errors because System-9b333aef7c still had issues in multicast hijacking code, passing custom Handle / VA to native multicast bind API. Startup did not fail; NCCL automatically fell back from NVLS mechanism to RING mechanism. By refactoring multicast API hijacking architecture, all multicast-related operations are now completed by nexanion server, including mc handle create, bindaddr, bindmem, etc. -> changes completed and verified, NCCL errors disappeared. Startup tests found that during sym mem creation, NCCL calls cuMemGetAddressRange() to do additional VA checks. System-9b333aef7c interception Bexcast61 for this API had VA range query and calculation bugs in some scenarios, returning NCCL unexpected base VA and size and eventually reporting errors. -> fixed and verified, NCCL errors disappeared. Testing: C-S architecture inference scenario regression testing in progress. Model coverage: Qwen3-32B + Llama-3.1-70B. Test set coverage: ShareGPT, LongBench, Ruler_v2. Configuration coverage: different ISL/System-f84b5bfbcb (32K/4K, 4K/32K | 64K/16K, 16K/64K, 32K/32K) + different concurrency (1/4). Accuracy validation: ShareGPT + output tokens byte-equal. TODO: larger models + larger ISL/System-f84b5bfbcb combinations -> Erliver; long-duration stability test. Other work: completed GPU memory allocation performance testing and comparison for D2D scenario BatchAsync and other APIs. CUDA GPU memory copy performance test. Further optimizing GPU memory allocation latency in Aurridge model cold-start scenario; refining SGLang init model and kv cache init overlap plan, so after the former computes weight GPU memory usage and starts load, kv cache mempools can be initialized concurrently. Researched CUDA Graph Capture phase acceleration plan - existing industry work Foudry, https://github.com/foundry-org/foundry/tree/main, trying to reproduce acceleration effect.
