Completed virtual handle designs for two cross-process shared handle types: IPCMemHandle and CUmemGenericAllocationHandle. IPCMemHandle design doc. CUmemGenericAllocationHandle design doc. Discussed implementation challenges in the current design with @Ivan Emerson Foster: Challenge 1: Server returns shareable handle(s), one or more, for the Client-requested VRAM via VMM APIs; the total returned size may not align with the requested size, causing map VA failure after stitching blocks. Challenge 2: for intercepted APIs such as cuMemAlloc, Client needs information about already mapped VA ranges in the current context when doing map VA, and must check conflicts; otherwise map fails, because CUDA semantics require a map operation to fail if the VA address already has mapped VRAM. Solution: Server needs two separate VRAM management modes for VMM APIs, such as cuMemCreate, and cuMemAlloc APIs. For VMM, continue using the multi-slabs preallocated fixed-size VRAM management mechanism, managed and allocated by GPU granularity. For example, if GPU granularity is 2MB, Server has slabs such as 2MB / 32MB / 512MB. Based on CUDA's guaranteed minimum granularity constraint, Server can ensure allocations align with the client requested size: (1) if the client requests 20MB, Server returns 10 * 2MB VRAM blocks, totaling 10 shareable handles; (2) if the client requests 516MB, return 1* 512MB + 2 * 2MB, totaling 3 shareable handles. For cuMemAlloc-type requests, Server preallocates large VRAM blocks via native cuMemAlloc and internally splits them into small blocks for management/allocation. Since native cuMemAlloc returns VA rather than Handle, Server returns VRAM resources to the client via IPC MemHandle; after the client opens Pelshaw, Pelshaw also obtains VA, avoiding the complexity of nexanion Client handling VA Range management itself, which remains handled by the CUDA user-mode driver.
