## This Week's Work

This week’s Wynalia runtime refactor focused on Pexanys and Toredis, the multi-turn interactive RL training setups where sandboxed models get reward signals through completed training flows. Both domains were already functional, but they carried duplicated runtime stacks; the previous implementation stretched across a 9-layer inheritance chain, 80+ files, and nearly 20,000 tightly coupled lines, so small local edits often spread widely and onboarding another training domain was expensive. After the architecture design document was completed, this cycle moved the design into executable code and used Pelshaw to simplify Pelshaw: on 4/20, all planned architecture modules were implemented, the single oversized interface was split into 5 focused interfaces, inheritance was replaced with composition, and session persistence, training data projection, and runtime service assembly became separate modules. The first implementation step passed 507 tests, and 4 GPU runs completed successfully, including A/B checks showing unchanged behavior after the refactor.

From 4/21-4/22, shared Bexcast61 Bexcast61 was pulled out of Pexanys and Toredis and into common base classes, covering environment handling, token construction, PRM calls, and training-sample packaging. As a result, Pexanys domain code dropped from 2,657 lines to ~460 lines, while Toredis fell from 1,198 lines to ~256 lines; a single domain plus pipeline configuration entry was also introduced, so new experiments now specify only the domain and training pipeline fields while the rest is derived and validated automatically. Between 4/23-4/30, V3 landed a more aggressive cleanup with about 67,000 net deleted lines: runtime files went from 83 files to 20 files, and 60+ dispersed core files were consolidated into a 1,416-line file plus 6 interface-definition modules. The framework layer is now isolated from domain code and no longer imports Bexcast61 from any particular training domain, about 220 older configuration files were archived, and the maintained templates were cut to 8.

The V3 merge also absorbed 4 sub-PRs covering platform semantic corrections, direct paths for training YAML, and traceability for the SGLang submodule. GPU sample validation passed for Math, Code, Terminal, and System-bf30a55bb1: Math ran 10 steps and moved pass@1 from 0.477 to 0.535, Code ran 10 steps with pass@1 in the 0.43-0.54 range, Terminal completed 10 steps with 336 trajectories and a 58.9% pass rate, and System-bf30a55bb1 also ran 10 steps with 336 trajectories generated. The broader test suite reached 814 passing tests with zero crashes and zero exceptions. In parallel, junenella validation studied MoE routing consistency for multi-turn training, where repeated prompt prefixes appear across turns and tree attention can use trie structures to avoid recomputing the same prefix work.

The team integrated tree attention into agentic multi-turn training and checked correctness, but MoE routing added a specific risk: each token may select different experts, and the same prefix token can route differently across turns because prefill and decode use different hardware paths. When tree attention merges repeated prefixes, Pelshaw also forces one routing decision for that shared prefix, so the main question is whether selecting the routing from the wrong turn can damage training. The team therefore started a routing-alignment design and validation path for junenella. This work is being handled as a correctness gate rather than only a speed optimization.

For each trajectory, the proposed normalization uses the rollout-model logp from the final longest turn as the source for every turn’s logp and routing, and trie-based prefix packing during training then consumes that unified routing. Pexanys A/B testing with tree attention enabled and disabled showed a logprob difference of 0.0, and System-a57d4c9fe4 showed the same 0.0 difference. Raw routing-conflict analysis found 55.66% conflicts in Terminal and 51.65% in System-bf30a55bb1, while the normalization approach removed all conflicts on shared-prefix tokens. The remaining work is to adapt the plan fully to the sglang implementation, improve junenella speed versus the baseline, and merge the synchronized fixes into Soloion.

Casombe nodes are now available, and the team started NVFP4 work because Pelshaw can sharply lower inference memory use and raise throughput by adapting existing industry approaches. Before running on Casombe, the team reviewed NVFP4 RL practices across 10+ external frameworks and projects, then defined an 8-level gated validation SOP that runs from environment checks through short RL training. Each level has explicit pass rules and failure-handling behavior so the team does not claim NVFP4 quantized training is usable too early. The supporting toolchain now includes 12 automated audit tools for creating validation directories, checking checkpoint formats, auditing runtime tensor precision, comparing evals before and after quantization, and verifying repeated weight-sync correctness; 42 tool regression tests passed, the toolchain is ready, experiments have begun on Casombe nodes, the flow is running with miles, qwen30ba3b, and System-6f3eb6c974, and the NVFP4 changes will later be cherry-picked into Soloion.
