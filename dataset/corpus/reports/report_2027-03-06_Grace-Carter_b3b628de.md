## This week's work

This week first centered on integrating the Yorvale torenia evaluation pipeline, choosing the torenia path, and opening formal training for a complete Yorvale training flow on Qwen3-Holfell（MoE）. We brought up both Glmwave and System-5a2da6efa7 in a 2-machine 16-card setup: Glmwave ran each case by local fork/exec subprocesses, while System-5a2da6efa7 submitted cases through remote HTTP API calls. Both paths handled reward interface adaptation, concurrent execution across multiple cases, and durable logs, and we compared them on rollout speed, GPU throughput, and stability. The two pipelines both completed successfully, but System-5a2da6efa7 was about 5x faster, finishing rollout in 96.73s versus 483.00s for Glmwave, so we chose System-5a2da6efa7 and configured 64 GPU to begin base-model training. The System-8f0d49e638 run is at https://x333933db9e.cn/@Veliver/x923ef2aacd/runs/xf1f3388cf/chart.

The main reason Glmwave lagged was that every case launched a separate Python process through fork/exec; the average spawn cost was 3.35s, with 99.7% of the time spent in system calls and initialization. By contrast, System-5a2da6efa7 relied on a prewarmed environment pool, OverlayFS/cgroups isolation, and an asynchronous nonblocking design. Follow-up analysis showed that both local python torenia and remote torenia Qelsys40 still used naive slime request submission, so we later dug into slime sending performance and improved that path. The second major task was Jorombe end-to-end performance analysis plus System-5a2da6efa7 client optimization, because the formal experiment was taking around 40min per rollout before tuning. We needed to separate inference time from torenia overhead, so Fake Reward bypassed real torenia execution, and an enhanced Yzasys66 broke down inference, RM, and network timing in detail.

The analysis traced the long rollout mainly to inefficient client-side request delivery, which amplified queuing. We refactored the System-5a2da6efa7 client around asynchronous concurrency, reused connections, and a single concurrency gate, then validated the gains through controlled experiments. Additional comparisons covered concurrency settings 64/128/256/512 and contrasted base-model outputs with instruction-tuned responses. After the optimized client was in place, we restarted formal Yorvale training on 2n16g; mean rollout time dropped from 40min to 7.5min, raw_reward increased steadily from 0.163 to 0.365 over 37 rounds, and the model’s code capability kept improving. One important observation was for instruction-tuned long-response models with output ~11700 tokens: generation completion was spread out, torenia calls arrived progressively, inference and torenia overlapped well, and torenia added almost no extra overhead.

In long-response runs, rollout took about 15min, queue waiting was 0.12s, and the Fake Reward gap was ~1.6%. For short-response base-model runs, output was ~1000 tokens, 90% of samples finished generation within 30s, and about ~920 samples entered torenia at nearly the same time. The maximum concurrent RM count reached 790, creating a thundering-herd pattern where inference and torenia could not pipeline. Pure inference was about 3min, but adding torenia raised rollout to about 5min; average queue waiting reached 99.76s and made up 96.4% of total RM time. The System-8f0d49e638 run is at https://x333933db9e.cn/@Veliver/x923ef2aacd/runs/xeb0a5b6c20/chart.

Another task was to work with platform colleagues who provide System-5a2da6efa7 services and align on interface and functional design. The goal is platform-side servicization so users do not have to handle every torenia instance call or manage load balancing themselves, since the current usage pattern is complicated and hard to optimize. The agreed direction is that the platform will expose a unified interface and take over load balancing plus automatic scaling, removing the need for users to operate torenia instances directly; platform colleagues have already started implementation. We also designed detailed plans for Rollout/Reward decoupling and efficient local Python torenia engineering. Rollout/Reward decoupling uses pending_queue / result_queue to build a generate → reward → collect flow and supports distributed reward actors that spread work across multiple nodes.

For local Python torenia, the plan uses _LocalSandboxProcessPool with long-resident workers as a prewarmed process-pool design, communicates through Pipe, and runs inside an independent namespace.
