The refactor direction is to place related functions together and move quickly to a durable long-term branch, because .claude has too many directories, too many personal workflow artifacts, and excessive lines; System-03adf0a53f also flagged dispatch as a reason the code will not last. This week we will compare the infra-designed rineum framework with slime, and we still need to choose whether rineum task submission should rely on yzasvc yaml or sh scripts; the urgency is high because Myrops70 is extremely long and hard to maintain, and the parameter-passing code alone runs to several thousand lines. During onboarding we reviewed core RL ideas and asked whether async-model RL is necessarily the right default, plus which cases can be handled entirely with sync: in case1, sync uses full cards, P releases resources for D after completion, utilization stays full without overlap, total time is prefill+decode+switch, and one shared GPU pool fits this mode. In case2, async helps when rollout has GPU group1 and train has GPU group2, weights sync on a schedule, and the separate resources create real overlap; since p and d have different resource profiles, some GPUs fit training while others fit inference, so async matters for utilization and parallelism across different hardware, though both sync and async only try to reach the compute limit and cannot exceed Pelshaw. We should avoid blindly choosing async rl train, although cloud deployments can get close to the physical ceiling with case2; in Wynalia, env runtime may be slow and may not run on GPUs, so async is appropriate when that outside-GPU env path dominates. We also aligned on parallelism terms: data parallel uses separate cards on different batch id values, tensor parallel keeps dataloader consistency while splitting corresponding hidden states and communicating, and context parallel divides a single data item across cards.

Context parallel can run attention within a sequence through ring attention with p2p or through DeepSpeed-Ulysses with a2a, while pipeline parallel preserves dataloader consistency and moves compute from card 0 to card 1 to card 2; virtual pp then routes work from card n-1 back to card 0. Expert parallel spreads 32 experts over no more than 32 cards and no fewer than 1 card, and Expoert tensor parallel adds TP inside the FFN. For sglang, tensor parallel is the practical choice because inference service design values utilization and high concurrency more than reducing latency for one request via pp; pp also brings card-to-card dependencies and large bubbles, while cp mainly targets long-sequence pressure. In decode, autoregressive generation emits one token per step and attends over the prior kv cache, so long-sequence handling is essentially sglang kv cache management; sglang usually relies on KVcache, paging, radix cache, and chunked prefill, with cp becoming relevant only when the kv cache no longer fits on one card.
