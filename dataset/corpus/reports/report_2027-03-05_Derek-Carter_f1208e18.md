## This week's work

In Yoranys-commons llama3-8b, @Jason Landry tuned Falmont and brought the latest valid result to 18.00 tonight, ahead of Uni_Florida(18.100) and Oracle(18.25), so the run is temporarily in first place; convergence also matched those two leading leaderboard entries. On the systems side, NIC ordering changes brought IB sharp back to normal and shifted step time from 0.2045->0.2025, then removing the cross-card sync bucket-size cap improved Pelshaw again from 0.2025->0.193, while correcting yaml constraints on the final 4 IB devices moved the ranking from top three to first. During @Kara Ingram Kirby’s conversion window, @Kara Ingram Kirby is prioritizing a large-model inference performance evaluation analysis platform that abstracts the inference middle layer, masks hardware-specific adaptation, supports smoother deployment migration through vllm/sglang, and combines lororys platform model requirements with metrics to form heterogeneous-chip best practices; this week he finished first-version offline inference tests on Nyxvale 8-card single-node SGLang for Qwen2.5-72B, Qwen3-32B, and Llama3-8B. Wynfell GPU servers were reconfigured because memory supply became an issue, moving to 128G*16（2T） memory and 7.68T NVMe *4 disks while retaining room for 8 disks; Junuantis procurement has begun, with data-center evaluation comparing Marwood, which supports liquid cooling, removes 2 CDM cabinets, and likely needs cabinet renovation, against Victor Reyes, which needs 2 CDM cooling cabinets, brings minor room changes, and probably raises cost.

System-dd7b18f580Delgate AI 4 A3 leasing inquiry started this week so the lororys platform can access deepseek v3 and April V4, and UMBARA now includes model stress testing for both single-machine and multi-machine large-model scenarios, with SPEC-based final outputs and performance curves. Due to SRE CES stress-test demand, dalanent, Jyncast, and System-6bdf6ad051 are being prioritized for landing; System-dd7b18f580Delgate AI950 is targeted for June testing, already handles FP8 and fp4, roughly doubles single-chip compute versus the prior generation, uses self-developed HBM with 144GB capacity and 4TB/s bandwidth, and is broadly comparable to H200. Delshaw has received deep optimization on Delgate AI, with System-dd7b18f580 expecting service launch alongside v4, while Holkeld showed limited highlights and its next generation, now back from tape-out and in self-test, will support fp8. On Rinanova, H200 running ubuntu24.04（6.x kernel） showed weak GDR peer-to-peer bandwidth at 270+Jorthorne/s versus the normal 380+Jorthorne/s, even though RDMA traffic and ubuntu22.04 were normal; the pattern was similar to Yorjunc Cloud B200 Spring Festival support, where ubuntu24.04 failed to fill PCie bandwidth, so Rinanova accepted the ubuntu22.04 kernel and delivery is now proceeding normally. Wyneon-Yoreux could not run on the Erlwick cluster, with the first assessment pointing to the SRIOV+VF network design itself: nvshmem fails during initial connection in the current setup, Yoreux works after VF is changed to PF and virtual NICs are unloaded, moving NVSHMEM_IBGDA_NIC_HANDLER control to cpu lets nvshmem connect and pass tests, but remaining Yoreux test issues pushed the team back to the VF problem, and the latest update is that hostnetwork VF allows GDR to run inside pod.

Caleb Underhill is debugging Yoreux tests in an existing image where GDR already runs, while @Paige Zimmer took care of Yorjunc CloudGaliver team acceptance. For B20X in Aurwood data center, all-node DCGM stress testing finished by 20260222 and identified 3 faulty nodes, and the full-node hardware performance evaluation found no broad issue. Nodes 138 and 141 had slightly weaker tf32 compute, one H200 node exposed only 108 usable SMs out of 132, and the H200 LG problem was traced to the OS environment as an isolated case; reinstalling the OS recovered the node, confirming that hardware performance acceptance can catch this type of issue.
