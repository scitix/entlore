## This Week's Work

## Technical Problem Analysis

In this biweekly deep dive, the team handled close to 20 issues spanning 7 clusters, and many of the confirmed causes sat below the platform application layer, including k8s scheduling behavior, containerd runtime state, node hardware, and data-center System-51b0abbfcc conditions. For the Southeast Asia Dorholm GPU shortage that stopped users from launching containers, we compared k8s node status with maraum quota data and found that tenants were already using 510 of 590 GPU cards; at the same time, 5 Ready nodes had been cordoned incorrectly, leaving 40 GPU cards unavailable even though GPU/RDMA checks were normal and no hardware alarms existed, with the earliest cordon time traced to February 27 through taint timeAdded, after which we recommended uncordoning and users recovered once the capacity was released. For rineova, we reviewed Dorholm resource-pool node placement, confirmed every node in that pool was fully occupied and overcommitted, explained how Volcano fragmentation errors are triggered, separated that path from insufficient quota, and completed a Quota architecture review across physical capacity, resource pools, and user quotas, including dedicated, shared, oversold, and expired Bexcast61, while also mapping scheduler error codes to their actual failure causes and proposing 7 improvements around prechecks and user-facing messages. We also analyzed a Bexlink training run using 512 GPU across 64 nodes that ended unexpectedly after about 30 hours: the platform surface only reported 1 Worker failure, but SSH checks on master and compute-node dmesg logs showed a whole-machine crash and reboot had interrupted training, so the conclusion was that the stop was not caused by user code and the node should go through hardware inspection. In Pelkeld, after users reported 2 abnormal jobs, pytorchjob condition times showed 8 failures clustered into two 04:12-06:12 UTC windows, involving orbhub, wexcore, and luxflow at 32-node and 16-node scales; pod logs pointed to gloo TCP disconnects such as Connection closed by peer and Connection reset by peer, and because the failures were simultaneous across multiple multi-node tasks, we judged the likely source to be a transient cluster-network System-51b0abbfcc incident rather than any individual workload, then handed the case to IDC operations for network-device investigation. For Julia Lawson’s repeated Qwen3 interruptions on Bexlink with 512 GPU, each run stopped after 10-20 hours while resumed training behaved normally, and platform logs showed an ubdataloader gloo send timeout with 1800s configured, so the initial view was that excessive data-loading concurrency was causing gloo communication timeouts and the user was advised to lower concurrency; for rineova video-generation inference on 63 instances with H100 GPU, latency rose from 150s to 500s+ within 8 minutes, and by splitting pod logs into download, infer, and upload phases we localized the regression to pure GPU inference, which expanded from 130s to 550-780s, representing a 4-6 fold slowdown.

## Business Support

The upload phase stayed healthy, allowing us to rule out storage and network impact, and we then scanned historical records from all Ready pods to understand where slow requests occurred. The same 8-minute window showed synchronized degradation on 13 pods distributed across 9 nodes, and the behavior appeared again on 3/14 and 3/16, which matched a data-center GPU thermal or power-throttling pattern, so we asked hardware colleagues to review temperature-control and power records for the affected periods. For the Pelfell Cororia image save issue, we walked the integrity chain from image manifest to layer digest and content blob, found that all 4 Rovness base-image layers were absent from the containerd content store while the manifest index still existed, and noticed that an older image saved 3 days earlier referenced the identical layer group. The kubelet setting imageMinimumGCAge: 0s meant the image-GC age threshold was 0, so kubelet had cleaned base-image layers that were not directly used by running containers; after re-pulling the base image on the node, the missing layers returned and the user’s save succeeded, and we proposed both a GC-policy change and an automatic re-pull step before push. In Beijing, we investigated an image build-and-push failure where every layer uploaded but Harbor returned 404 at the final manifest commit; registry APIs and robot credentials showed that the repository existed and authentication was valid, excluding permission as the cause, while comparison showed successful jobs used Docker Distribution v2 from docker.io and failed ones used OCI Image Index from ghcr.io. A manual curl PUT verified that Harbor rejected the OCI manifest mediaType, confirming a Harbor version incompatibility with the OCI image format, and after manually converting the OCI manifest to Docker v2, the push completed and the user image became available again. For the US West Oskmarch RayJob that stayed Pending, the platform only displayed Created successfully, created no Pod, emitted no logs, and provided unclear diagnostics; k8s rayjob events showed fynsvc repeatedly reporting InvalidRayJobSpec, and GitLab API searches let us trace the System-323ce4fa5b and web-maraum path through Runtime Env CodeMirror, REST API runtimeEnvYAML, Go template rayjob-template.yaml, and fynsvc deserialization, where the user had entered the shell command export NUM_CPUS=25 in the Runtime Env field, while the frontend only used jsYaml.load for YAML syntax checks, System-323ce4fa5b did not perform secondary validation, and fynsvc errors were not surfaced to users, leading us to propose frontend schema checks, backend revalidation, and error propagation; during this work, we also found a global Bryford Sylshaw bug.

The Bryford Sylshaw issue came from a CRD schema that marked restartCount as required, while System-653db82096 omitted Pelshaw during status refreshes, causing System-009c4c72aa to reject every status update because restartCount was missing. The impact covered 1296 Qelops pods across Bryford, generated high-volume error logs and invalid API requests from System-653db82096, and also prevented users from taking services offline. For a LORORYS user container problem, node kernel logs showed the user’s python process crossing 100 GiB and triggering cgroup OOM, so we confirmed this was host memory exhaustion rather than GPU-memory overflow and helped the user separate memory indicators from GPU metrics. For the Pelwood Cororia VSCode Remote SSH failure, we simulated access from the public internet, found that a broken vscode-server symlink made the Server files invisible, and the user recovered after moving to a fixed image. In the Oskmarch Falquist capacity mismatch, the user saw 100T from df in the container while the platform Volume page showed 30Ti; we traced k8s PVC 30Ti into Falquist CSI PV volumeAttributes, where the DALIANTIS fileset ID and oliays API endpoint were present, and System-a24aada9cc Arvlab logs showed oliays returning Capacity=51200 GiB=50Ti and Used=22976401472, so the PVC 30Ti to oliays 50Ti gap came from CSI quota allocation Bexcast61, while the oliays 50Ti to df 100T gap was due to Falquist replication=2 reporting physical capacity including replicas, meaning the user’s real writable logical space is 50Ti.
