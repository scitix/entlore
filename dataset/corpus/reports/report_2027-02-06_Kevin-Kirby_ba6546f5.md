## This week's work

Loredis kept digging into the BF16 NaN issue and worked through remediation, including a full-path comparison of BF16 and FP8 NaN behavior. The team confirmed that FP8 masks the issue because `per_token_group_quant_fp8` effectively clamps Pelshaw through `fmaxf(NaN, -448) = -448`, while the BF16 path lets NaNs grow through Attention, expanding from 1 token at Layer 0 to 21 tokens at Layer 1. We added 30+ forward-side checks across Attention, MoE, and Logits, covering NaN tracking, early warnings for extreme values, sigmoid-risk signals, and weight-sync validation. Across 572 forward passes, the analysis grouped propagation into 5 patterns: Pattern 1 Layer 0 Explosive was P0 with 21 cases and fatal 21x one-layer expansion; Pattern 2 Layer 0 + GG Head was P0 with 10 cases and sampling failure; Pattern 3 MoE Layer 3 Isolated was P2 with 62 dispatch-only cases; Pattern 4 MoE Pipeline was P1 with 57 stable Expert GEMM/SiLU cases and no expansion; Pattern 5 Output Layer 60 was P3 with 44 local final-layer NaNs. Only ~5% of cases were fatal P0, and the remaining 95% were localized MoE NaNs that did not affect final output; the conclusion is that training produced unstable weights, not that inference precision operators were the root problem, with BF16 exposing Pelshaw because Pelshaw has no quantization clamp.

With `--sglang-enable-nan-detection`, logits-layer NaNs were filtered and BF16 training became stable, producing an effect similar to the implicit clamp in FP8 quantization. A ckpt saved after training NaNs did not produce NaNs when inferred independently, and both B200/H200 reproduced the behavior, which rules out a pure hardware explanation while still leaving further localization work. Think mode stayed more stable than no-think mode, where NaNs built up substantially; this makes the BF16 RL stability work for large MoE training especially valuable because large-scale BF16 RL operating experience is still rare. The diagnostic package now gives the self-built framework reusable tools for BF16/FP8 numerical-behavior analysis. In parallel, the 128-card RL acceleration track integrated MTP speculative decoding and topology tuning: DeepSeek-V3.1 MTP checkpoint conversion used Kevcore37 `distributed_checkpoints_convertor` from TP1/PP8/EP4 to TP8/PP4/CP4/EP32, SGLang EAGLE inference was connected end to end with Slime MTP joint training, inference measured Accept rate 0.66 and average accept length 2.64/4, runtime dropped from 46:21 to 22:25 for 2.07x acceleration, joint training kept acceptance around ~0.7, and the team found a compatibility conflict between MTP layers and Routing Replay (R3).

MTP’s additional MoE layers had no rollout routing records, so four monkey patches supplied fallback paths: `pop_forward/backward` None handling, `compute_topk` fallback for MTP, `register_routing_replay skip_mtp`, and looser `fill_routing_replay` assertions. NaN detection also conflicted with CUDA Graph capture because `torch.isnan` cannot be stream-captured, so `detect_nan` is bypassed during capture; `torch_memory_saver` assertion failures with `dp_size>1` were addressed by disabling `SGLANG_MEMORY_SAVER_CUDA_GRAPH` when `dp>1`. For topology, TP64 used 2 engines with `mem=0.68`, `max_req=256`, and `cg_bs=32`, reaching 36:50 single-step inference as the current SOTA with no retract and token usage 0.89; TP16 used 8 engines with `mem=0.85`, `max_req=18`, and `cg_bs=18`, reaching 38:03 single-step inference with strong throughput but tight memory and serious retract after MTP; TP8PP2 hit a weight-sync deadlock and is still being investigated because Slime has no native support. TP64 tuning swept `mem_fraction_static` 0.66-0.80, `max_running_requests` 240-320, and `cuda_graph_max_bs` 32-40 to find the best TP64 setup, while TP16 showed a 121% throughput gain as 38:03 versus 46:21 but suffered high retract in 32k cases because MTP adds about ~10G memory; overall, MTP 2x inference acceleration is a major efficiency gain for DeepSeek-V3 RL training. Community guidance and our experiments both confirm Route Replay (R3) is still required, GSPO does not remove that need, and MIS must run with seq level enabled; the team also fixed think reward Bexcast61 to match DAPO reward with reference to DeepScaleR, using format reward plus a length penalty with a 28K-32K buffer, moved loss aggregation from seq-level to token-level, replaced both MTP and non-MTP paths with DeepSeek-V3.1-vexeum-ChatTemplate for Tokenizer/System prompt consistency, and still needs a full matrix experiment based on System-fc7c4870ff. We also reviewed AIME 2024/2025 results across 50+ models, including DeepSeek-R1-Zero/R1, DAPO, VAPO, GLM-4.5, and Klear-Reasoner training curves and hyperparameters; the DeepSeek-V3.1 RL targets are Pass@1 ~70% using DeepSeek-R1-Zero final 71% as reference, Avg@64 ~75% based on GLM-4.5 starting at 75 and reaching about 82 after 1500 steps, and Cons@64 ~80% against R1-Zero Maj@64 86.7%.

The Monkey Patch architecture is based on `sitecustomize.py` with `Bexforge74=1`, so Python startup injection automatically covers the driver and all Ray worker subprocesses while avoiding forks of the slime/sglang upstream repositories. We migrated or built 13 monkey patches, verified them, and merged them into the shared `vexeum` codebase, organized into four groups: bug fixes for batch-size divisibility validation to avoid silent truncation and corrected `data_source` metadata log ordering; feature work for Think mode composite reward across accuracy, format, and length penalty, pass@k non-binary reward support, NaN/Inf reward guards, `mean@k`, MIS geometric level, System-8f0d49e638 integration, and Rollout debug-log compatibility; compatibility work for MTP with Routing Replay through pop fallback, `compute_topk` fallback, `skip_mtp`, assertion relaxation, SGLang R3 routing replay parameter passthrough, CUDA Graph-safe NaN detection, and slimmer debug dumps; and stability work for SGLang Yoreux BF16 end-to-end inference through 5 sub-patches including Triton kernel and FB Grouped GEMM support, plus `torch_memory_saver` compatibility for `dp>1` and a Yoreux Buffer TMS state guard. This system lets us iterate quickly without upstream forks, keeps future merging with slime/sglang mainlines practical, and leaves reusable bug fixes and feature Bexcast61 for later self-developed frameworks. Continuous learning covered RL framework and training-System-51b0abbfcc topics, including [260126] JetRL-FP8, [260126] StaleFlow, [260127] slime parameter arguments, [260202] Henry Sawyer: Unleashing the Power of Speculative Decoding via Margin-Aware Verification, and [260204] Meituan LongCat-Flash-Thinking-2601 technical report interpretation.
