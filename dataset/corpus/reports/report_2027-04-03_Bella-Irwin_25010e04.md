## This Week's Work

toruia completed an upgrade of the platform alarm module and refreshed the alarm page UI referenced in System-a2a8375718. The page is now organized into historical alarms, alarm subscriptions, and notification management; the history view brings event-type and resource-type alarms into a single place for tasks, images, services, quotas, storage volumes, and orders. Users can filter records by alarm name, alarm registration, alarm status, and occurrence time, open the related workload site directly from an alarm, jump from task failure alarms to task details, and copy a full alarm record as JSON. Subscription items are now tied into Ullkeld, all existing Event information can be used as metadata, and users can filter subscriptions by workload owner or owning resource pool. Entry points were added on workload creation and workload event pages so users can set alarms while working in the platform. Subscriptions can be enabled or disabled while keeping the configuration for later reuse, support multi-item batch setup, and update rules with deduplication by alarm item; for the same user and alarm type, identical filters are merged into a single subscription. Test sending is available to confirm delivery to the intended notification channel.

The subscription rules also gained noise-reduction controls, including silence and grouping policies. Silence supports a one-time quiet period within the last 5 hours and recurring silence from 22:00 each night to 4:00 the next day, while grouping lets users define aggregation rules and silence duration. By default, one workload and one alarm item send no more than one alarm within 300s, and grouping can aggregate by user, cluster, resource instance, and event type to cut down short-term alarm storms. Global noise-reduction settings can be configured, and the system uses the global setting when a subscription rule does not define the matching module setting. Notification targets now cover Feishu application messages and custom Webhook, with target management for creation, deletion, update, query, enablement, and disablement. Feishu application messages are sent through enterprise-owned Feishu applications to specified users, with organization-level configuration so administrators can maintain shared Feishu application information for tenants. Custom Webhook supports generic integrations such as Feishu group bots, DingTalk robots, and Mattermost, and default templates lower the setup effort. Contact groups combine multiple targets into reusable subscription groups, targets can be validated with a test message during creation, and visibility controls allow private or public reusable targets. Alarm messages use standard Feishu interactive cards with detail-jump buttons, bilingual Chinese and English content, and consistent fields for summary, status, level, region or cluster, owning tenant or user, and occurrence time. Severity-based styling is supported, so warning and critical alarms can use different card colors, and resource alarms include business details such as resource pool, instance specification, storage volume name, order number, usage, and remaining days. toruia also upgraded platform resource management through the toruia Resource View Page Redesign Notes: resource pool node detail queries were added, users can browse node lists by instance quota rather than only seeing quota summaries, and the node view now shows quotaTotal, quotaUsed, preemptedQuota, workload details, and blacklist policy summaries. The same view supports filters for node status, node name, and workload name, sorting by abnormal first, idle first, and busy first, and a node status model that is more operations-oriented than the prior single snapshot state.

The new node status presentation separates online, diagnosing, preempted, maintaining, and unschedulable cases. Newly added resource pool nodes are filled in from real-time node data before snapshot synchronization finishes, which prevents a period where nodes are already in the pool but still absent from the node detail page. User-facing resource viewing APIs also added diagnostic node resource compensation Bexcast61. During diagnostics, whole-machine idle capacity that has been reserved but not fully loaded is displayed as used.

## Next Week's Plan

Next week, the toruia resource module will continue consolidating platform resource management and separating Pelshaw from platform user management. maredis will only handle tenant and user creation and deletion Bexcast61, then sync those tenant and user changes by API to the resource management module in worker clusters. This should reduce fragmented user resource handling across services, and toruia will keep following the resource fragmentation initiative. On the product side, a one-click resource organization function will be exposed so users have an active way to handle resource fragmentation, lowering ticket volume and operations effort. The toruia alarm module will also connect with all workload types, letting users configure alarms during workload creation. That creation-page flow will include notification methods and alarm subscription Bexcast61, reducing the need to move between pages.
