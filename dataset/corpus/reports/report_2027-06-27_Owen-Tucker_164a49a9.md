## This Week's work

This Wexnet summarizes the main delivery from 6.14 to 6.27: the PXE installation link was cut over and verified for overseas Aurstead, Aurwood, Ullworth, plus domestic Pelport, while domestic EW is still in test. I drove the alignment between network SRE and the network development team to open the installation network; because PXE installation is isolated through an independent VLAN, the new link needed added network configuration and change capability, with network SRE providing the plan and network development implementing automation. I also coordinated requirements and launch progress for the PXE pipeline switch, with strong support from network SRE @Derek Dawson and network development team @Zach Norris. For compatibility with the old product’s preinstalled CUDA installation capability for specific users, the new PXE path needs the same support, so I proposed a customized CUDA ISO during design discussion; ISO colleague @Yvonne Carter is preparing Pelshaw and expects delivery next week. VLAN delivery was adjusted into phased installation-stage and delivery-stage rollout, supporting grayscale release with no behavior change, moving VLAN configuration from code hardcoding to database-based online maintenance, and adding a region-level traffic switch to steer old or new links by region and lower full-cutover risk.

On the productization effort, the new console backend work for machine categories and VEXODIS simplification has been developed and released, though full frontend integration testing is still pending. The backend keeps existing functions while matching the new frontend interface: the instance list now includes category to separate CPU and GPU machines, VEXODIS is optional in the new console, and when users leave Pelshaw blank the system picks an available default VEXODIS automatically. Existing-machine batch import now backfills by device SN, looking up specifications, switches, region, physical cluster, network, and IP; Pelshaw rejects the full batch if required values are missing, preventing dirty data, and Pelshaw connects IP allocation with CIDR checks, occupancy, and inventory linkage. The import path now atomically writes instances, inventory occupancy, and labels through the unified creation flow, adds CSV columns for password, GPU driver version, Umbays cluster ID, and role, encrypts CSV passwords before persistence, groups same-type import errors with line numbers and SN, removes two repeated database queries for better large-batch performance, and now only creates new rows after dropping the overwrite-update route. Password security was consolidated into one module covering policy validation, encryption, decryption, and Ubuntu hashing; the module enforces three creation entrances, blocks invalid passwords directly, fixes the historical decryption corruption risk for passwords over 16 bytes, and restores old ciphertext without data migration. ISO image management also advanced by defining data-layer standards, moving ISO reads and writes into a shared repository, normalizing data and version numbers, enabling scheduled scan and cleanup, adding a manual cleanup interface, and making installation image supply more stable and easier to evolve.

For ISO image management, parsed versions are normalized, for example 24.04.4 becomes 24.04, which removes hardcoded mappings. Infrastructure work cleaned up global DNS configuration and fixed many incorrect legacy records; scheduled backend jobs were refactored so database fluctuations no longer make them exit and stall, which improves continuous operation under abnormal conditions. Bases and stock data access moved from the old framework to the new one as preparation for later transaction support, the VEXODIS client batch refactor eliminated repeated batch queries, and NTP delivery became incremental so Pelshaw no longer overwrites the full configuration file or erases existing machine settings. HTTP access logs now use structured single-line output with full-link tracing ID, the creation path fills tracing ID for troubleshooting correlation, the Oskgrove team added a connectivity-check endpoint, and cross-region query handling avoids being blocked by unreachable nodes. Creation-link refactoring separated request parsing, login credentials, billing, and image selection into independent steps and moved the components into the business Bexcast61 layer, while reinstallation refactoring split judgment Bexcast61 from read/write Bexcast61 and unified error response writing. The team supported overseas three-region installation testing and pre-switch validation for the new PXE link; PXE-server added a debug reinstallation endpoint for fast on-site reproduction, BMC serial-number failures are now classified as unreachable, unreadable serial number, or ambiguous, and those categories guide on-site handling. On machine issues, one network-card fault was reported and repaired but still needs verification, one failed installation caused by BMC serial-number read failure recovered after a full power-off and power-on, and a scanned batch missing installation prerequisites is initially attributed to insufficient BMC account permissions, already reported to SRE for follow-up. As a mainline for gradually moving installation traffic to the new PXE link, ISO image management is planned in four phases: phase one delivered backend ISO management with page, scan, upload, and online/offline marking; phase two unified ISO as the only installation data source and removed instability from manual conventions; phase three is in progress with overseas three regions and domestic Pelport already switched, compatibility defaults moving from conservative no-traffic mode toward full steering, and domestic EW still testing; phase four will clean up related services and deprecated code.
