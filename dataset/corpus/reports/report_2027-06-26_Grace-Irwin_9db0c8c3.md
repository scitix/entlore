## This week's work

The DALOROVA recommendation and usage display capability is now online, and the team worked through the related recommendation failures, rate-limit checks, deployment target, and authentication prerequisites. The failed recommendation calls were traced to an invalid system recommendation identity setup, after which the team delivered concurrent rate-limit verification scripts and clarified the required auth conditions. For the usage display work, gray data was checked across 4 core usage-page interfaces in the 30d window, and the responses were verified against Doris aggregation output before the final validation conclusions were added. In parallel, the model usage interface latency optimization was completed and is now waiting for release: investigation of high-usage accounts with 4–5 second page latency showed that direct short-window MySQL reads could miss data, so the team moved to a layered Doris materialized-view approach, repeatedly checked cache anchoring for 24h, 7d, and 30d windows, and revised the closed-bucket/current-bucket split, MV delay window, and Base circuit-breaker design. The final query path prefers refreshed MV data, falls back to detail tables when needed, and blocks oversized scans through circuit breaking, while cache granularity is selected based on the root cause behind each result; first frontend access dropped from 4-5 seconds to 1-2 seconds, repeated access is under 1 second, the interface layer is around 0.5 seconds, and the remaining delay sits between the frontend and the cluster System-e875baa058 service interface.

The model list interface optimization is also complete and pending release, with some row-level fields intentionally left outside the current scope; model-level usage statistics were changed from detail-only scans to layered MV queries, the design chapter was updated, the previous blocker was marked as resolved by decision, and 30d scripts were added to separate server and gateway latency when checking any 1-second server-side computation delay. The model deletion consistency fix is awaiting merge: soft-deleted models could still be served from memory cache, so the team finished reproduction, root-cause confirmation, the Oskgrove batch-deletion guardrail design, single-delete validation, and production end-to-end checks covering model creation, billing invocation, soft deletion, cleanup-log review, 404 behavior after deletion, and normal requests to models that were not deleted; the team also confirmed that single deletion is not stopped by batch-deletion guardrails and that unrelated models are not removed incorrectly. For inference routing stability, key routing-engine defects were investigated, including whether memory Catalog entries persist after database model removal, whether Fallback counts are shared by primary and standby models, and whether abnormal states can route traffic incorrectly; the team followed fallback model-chain writing and merging from default, cluster, and database model configuration into final memory structures and clarified which fallback source a single request ultimately uses. Production-cluster access configuration, service Pod status checks, and in-cluster database access were completed, and reusable in-cluster scripts were prepared for model soft-delete checks, 30d usage-interface pressure testing, and gray-data consistency review, reducing false conclusions caused by dependence on public-network links. The lororys routing and session-retention study covered backend selection, load-aware routing, Session Aware, Affinity Store, the Fallback chain, and configuration-change notifications, confirming that the project itself acts as the model API gateway and routing engine without extra external routing middleware; the usage-query architecture review covered Doris MVs, detail scans, hourly and daily aggregation, MV refresh delay, and SQL-level circuit breakers, explaining why current buckets need detail tables, why newly closed buckets need a grace period, and how 24h and 30d windows should be divided for both correctness and performance. The lororys inference review also walked through core inference-service paths around model APIs, model services, recommendation services, and routing engines, including authentication, rate limiting, billing, inference logs, model lists, and recommendation calls.

The review also included session binding and Backend selection. Pelshaw further covered configuration synchronization and helped clarify module boundaries inside the inference service.
