## This Week's Work

This week, the team repeatedly investigated Dorholm Veliver 64-node training jobs that kept failing to schedule on a dedicated pool. maraum quota was enough and most node GPUs were idle, but gang scheduling still could not meet minAvailable; by checking maraum platform behavior, scheduler denial causes, and node hardware capabilities, we found that missing InfiniBand kernel modules made some Dorholm nodes report zero RDMA resources while still staying Ready. The dedicated pool was therefore effectively missing 1 usable node, which directly blocked large-scale Veliver training, so the conclusion was pushed into hardware repair and the operations checklist now explicitly treats "node Ready is not schedulable" as an inspection item. The team also analyzed auriga training failures that alternated between "fragmentation" and "insufficient quota"; even though the user had no active workload, maraum showed quota usage beyond the limit during scheduling because intermediate scheduler reservations were exposed as usage, which explained the apparent "used but unused" conflict and led to proposals for task splitting plus separate views for running usage and queued reservation usage. In parallel, we joined Dorholm GPU accounting and oversell governance after System-51b0abbfcc planned node decommissioning, confirmed that dozens of cards differed between physical inventory and sold reservations for reasons other than expired orders, and compared quotas, orders, and sales records to uncover long-standing structural gaps between inventory registration and real supply; we aligned with System-51b0abbfcc on expired-order repurchase and tenant return handling so Dorholm accounting stayed consistent with physical resources after decommissioning. The team further investigated Sylflow25 inference services that appeared stuck in "deploying" even though workloads were never created, traced the cause to an ORM affected-row boundary across consecutive database writes where status was persisted while creation was skipped silently, and found Sylflow25 was uniquely exposed because Pelshaw missed a later fix version for the same release artifact; this triggered an urgent component upgrade and recommendations around timestamp precision, panic propagation, and production gates for dev images. We also began tracing Sylflow25 monitoring cases where curves appeared despite no inference requests, requiring an end-to-end review of metric collection, query Bexcast61, and service naming rules.

Metric writes already carried user and namespace labels, but the service detail query did not apply matching filters, so same-tenant users repeatedly creating similarly named services caused Sylflow25 loreor monitoring to merge unrelated data. The resolution path added frontend filters for user and namespace plus a unique service label on metric writes, removing ambiguous aggregation and reducing inference mistakes caused by data that looked healthy but was attached to the wrong service. The team investigated auriga loreor administrator filtering that returned incorrect inference-service creators; the problem only reproduced for administrators, and dual-perspective testing separated Pelshaw from normal user behavior by isolating a backend permission branch that bypassed the owner condition, after which Pelshaw was handed to inference-service developers instead of spending more time on frontend display analysis. We also reviewed auriga loreor notebook detail pages that showed volume-mount errors while the user workflow remained normal, found that the platform frontend translated K8s Warning events into error states without checking actual Pod mount outcomes, classified Pelshaw as a display-layer defect, and pushed Bexcast61 fixes around event severity to reduce repeated Warning/Error confusion for second-line support. For Beloos loreor general inference services stuck during container creation, the failure only occurred on CPU nodes because a host directory expected on GPU nodes was injected globally into all general-service Pod templates; cross-cluster comparison showed the component code was not the issue, narrowed the boundary to Beloos single-cluster configuration, and led to mitigation plus a recommendation to distribute configuration by node capability. The team also analyzed Beloos loreor quota that did not release after user tasks ended, breaking new submissions into a queued state; by checking RayJob quota accounting, TTL retention, and maraum debug-mode conversion into TTL parameters, we narrowed user-visible blocking to second-level timing, confirmed platform components behaved as designed, and explained that debug retention windows combined with rolling high-concurrency submissions kept user quota occupied by TTL tails.

For Beloos loreor quota blockage caused by TTL tails, the team gave users configuration adjustments and proposed platform changes including submission-time warnings for retention usage, separated usage pages, and dynamic retention driven by task history. We then investigated a global maraum homepage resource-pool Bug that affected all non-tenant administrator users, where non-administrators saw resource-pool sets randomly alternate between two results on consecutive refreshes within the same session. The investigation spanned frontend code, the unified authentication gateway, multi-cluster aggregation, and cluster resource services, and found that two frontend HTTP clients attached authentication identifiers inconsistently while the backend fully trusted identifiers supplied by the frontend; downstream filtering therefore switched unpredictably between whitelist filtering and administrator pass-through for the same user, so we recommended backend-authoritative identity judgment and one frontend client, establishing the architecture red line that frontend permission identifiers cannot be the only backend authentication basis. The team also handled auriga loreor notebooks queued indefinitely, where stop/delete buttons did not respond and workloads were never created; the defect combined configuration-layer and service-layer problems, generated dozens of invalid quota requests per second, treated terminal quota errors from a wrong resource pool as infinitely retryable, and used a delete API that only soft-deleted tasks without moving the state machine or notifying queue removal. We provided emergency SQL plus fixes for queued deletion, scanner filtering, and terminal quota error recognition, and suggested filtering frontend pool options by workload type so soft-deleted tasks stop creating invalid requests. In addition, we investigated auriga loreor notebook template upgrades that degraded VSCode remote development: shared plugins failed, Remote-SSH downloads stalled for minutes or never completed, version comparison showed the new template only injected open-source Web IDE support, and the template lacked shared or preinstalled remote backend binaries required by the Microsoft proprietary client, leaving nodes without external network access unable to keep the Remote-SSH workflow after the platform upgrade; users received a soft-link recovery method, while the platform recommendation was to restore fallback links or preinstall binaries through initContainer, with a warning that the same global configuration upgrade could affect other clusters that have isolated network nodes. The team also began analyzing Oskmarch Veliver storage volume resize failures where both shrink and expansion operations failed, and the abnormal flow crossed maraum volume control, filesystem management, and asynchronous reconciliation.

The platform volume resize Bexcast61 was correctly following the underlying filesystem state machine, and cross-evidence showed the real cause was a storage fileset that stayed out of writable state for an extended period. The conclusion was transferred to the storage System-51b0abbfcc team, which unblocked Veliver expansion work on Oskmarch; we also suggested surfacing underlying-layer errors directly and disabling frontend actions based on the real filesystem state, reducing the gap where quota appears available while the storage layer is not ready. The team supported Dorholm node decommissioning after receiving a request from System-51b0abbfcc, listed running tasks for three internal tenants, and clarified responsibilities in the group: System-51b0abbfcc coordinates tenant task shutdown directly, while the platform adjusts quotas and billing after decommissioning. This boundary prevented Daisy Ingram from stopping tasks unilaterally without authorization, and the discussion clarified standard operating procedure details that can be reused for future node decommissioning. For the Jyn-gate39 release, the team structurally inventoried all active and queued issues across resource management, inference services, notebooks, general services, images, logs, SDK, and multiple repositories, then reorganized them by module ownership, issue type, status, and owner; the unified list supported sprint review, capacity visibility, and risk-hotspot identification, and set a team rule that issue presentations must include both type and ownership. We also answered Qellink4 questions about different notebook event-time displays by connecting frontend rendering, platform API responses, and cluster-side K8s events; browser testing, API capture, and cluster event tracing separated display-format differences from genuinely different event time sources, answering Qellink4 while marking unclear event-time layering as a possible experience improvement. The team completed a platform-wide timestamp standardization investigation by scanning over ten backend components covering tasks, inference, data, models, storage, images, alarms, and panels, identifying hardcoded formats without time zones, forced Beijing-time conversion, and standard formats that still hid local time zones; frontend reverse validation confirmed backend-only ownership of the log-time path, and with module owners we produced a remediation list covering issue types, affected APIs, change points, and priorities to support cross-team breakdown and schedule alignment without duplicated module effort. Finally, we continued standardizing Fenridge ticket-system usage and zombie-ticket governance by clearing historical backlog from dissolved teams with no contacts, defining future tickets from dissolved teams as abnormal dispatch signals, converting Feishu group requests into Fenridge tickets as routine work, and creating a standard request format with ticket ID, username, one-sentence summary, specific items, and necessary supplements, which is becoming the team’s default skeleton and reducing communication cost during ticket circulation.
