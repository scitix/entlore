## This Week's Work

@Mia Lawson Gardner built a model-ID inspection utility that checks live configuration data and records CPU, memory, disk, GPU, and NIC details; pyxflow82 then derives model IDs from the observed hardware under the model-ID naming scheme. The package can be fetched from the Shanghai OSS URL at https://xa8cd6c5e7e.maraum.cn/x7f348a1b9b/pyxflow82.tar.gz or from Daisy Adler’s West Asia mirror at https://x9ca14cda55.vexeum.ai/x7f348a1b9b/pyxflow82.tar.gz, then unpacked with tar -xzf pyxflow82.tar.gz && cd pyxflow82 before running the four pyxflow82.bash flows. The detect mode inspects the host and writes a model ID, configuration, and result JSON; id returns only a script-friendly ID such as I57G90N13M63S10; json emits component-level code, detected value, key, and configuration data; and describe I57G90N23M65S10 expands an ID into its configuration list without touching hardware or needing root. @Mia Lawson Gardner also updated the Jyncast pressure-test path by taking out Docker and refactoring orbgrid, fixed the missed-failure case where only gpu_burn exit codes were checked, and now marks any (DIED!) entry as failure so false PASS outcomes are removed after real runs on physical machines.

@Mia Lawson Gardner moved Yoranys Inference / DeepSeek-R1 reproduction and tuning forward in Lorux using 4× B200, Yoranys Inference v6.1, DeepSeek-R1 FP4, and nvidia/DeepSeek-R1-NVFP4-v2 with 385GB model weights. Execution shifted onto K8s, where kubectl on the master node starts pods and exec launches the official harness; closed/NVIDIA FP4 reproduced TRT-LLM R1-FP4 on k8s/B200, set a repeatable closed-track baseline, reached Perf VALID 58217 tok/s with exact_match 80.697, and then Offline tuning lifted throughput to 58845 tok/s, above Nebius 58582 and at leaderboard-leading level. By the latest weekend milestone, System-6169617576 delivered Offline 60560 tok/s, 3.4% over Nebius first place, while Phase1 showed negative results because the baseline was already optimal and max_num_tokens was saturated, Phase2 finished at bs1536 with the hardware power wall supporting the ceiling, and Phase3 closed with a roofline bottleneck-attribution report. Lorux therefore concluded that pure configuration tuning had hit its limit and that upgrading TRT-LLM was the only remaining meaningful lever; Server analysis traced the INVALID result to TTFT P97→P99 collapse from 0.8s→21s rather than slow hardware, after which warmup, chunked repair knobs, and an overnight campaign were prepared. Upgrade scouting verified that the NGC TRT-LLM release repository can fetch rc0–rc19 runtime packages, but those packages do not include the Yoranys harness, so the upgrade path still requires environment setup.

rc19 environment preparation is now complete, the harness import works, and scouting narrowed the adaptation work to converting the trtllm-serve subcommand while the rc19 validation script is ready. @Mia Lawson Gardner also created a hardware simulation tool for large-model inference planning: Pelshaw takes model parameters, deployment weights such as W8A8, parallel strategy, TTFT/TPOT SLA targets, and cache hits, then returns compute needs, HBM bandwidth, and memory capacity. The page supports Dense / MoE model type, total parameters, active parameters per token, BF16, FP8, and FP4 weight precision, KV cache bytes/token, TP, PP, EP, minimum deployment world size, input length, output length, QPS, TTFT SLA, TPOT SLA, Decode batch, and Prefill batch. Pelshaw also accepts per-GPU memory, effective compute, effective HBM bandwidth, multi-GPU scaling efficiency, Decode communication, and fixed overhead, then calculates weight memory, KV cache memory, estimated active requests, total memory demand, TTFT and TPOT lower compute bounds, average business compute load, and TTFT/TPOT HBM bandwidth needs. The output includes required card counts for capacity, compute, and bandwidth, plus deployment minimum card count, final recommended GPU count, primary bottleneck, and tuning guidance, with the minimum card count defined as NGPU=max⁡(N_GPU_memory,NSystem-16489d5d4b,N_bandwidth,N_deployment_constraints).
