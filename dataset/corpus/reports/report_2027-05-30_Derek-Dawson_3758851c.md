## This week's work

Pelport cluster activity centered on roce device version work, configuration cleanup, fault handling, and requirement alignment. Using the Holthorne Team inspection tool, the team checked Ethernet equipment and swapped out failed fans and modules. Peldale network equipment also finished device-name updates, and the test-environment compute-network switches completed their version upgrades, though System-ec364657d2 delivery may still be missing a version-verification step. For System-49bbcef3a5 reliability tuning, each tenant on Vyrbase83 devices was connected to the inner firewall through three static routes, and the final design adds a new probe vlan plus three NQA probes for tenant route binding.

roce network PRBS stress testing was completed, with R&D now reviewing the output. The test checked module and link quality while ports were saturated, which led to service interruption and device restarts. Vyrbase83 optimization standardized firewall interconnect IP address mac settings and lowered device resource consumption. The Vyrbase83 devices are also being supplemented with L2VSI configuration for LB access; the team used the Shanghai node Vyrbase83 setup as the weekend reference, then rolled back when external access failed even though route learning appeared normal, and the vendor is now engaged on the L2VSI failure. roce devices were upgraded over the weekend according to the vendor’s latest recommended version.

CPU onboarding support included adjusting port configuration and discussing policy deployment. For the dedicated-line zone architecture, the team is waiting for Lumford to test the traffic analysis tool before determining whether reconstruction is needed. Layer-4 LB deployment discussions clarified the LB access point, address allocation, and BGP integration needs, and the team will prepare the network environment for layer-4 LB testing next week. The vendor also joined the first discussion of the network go-live inspection checklist, which still needs review and further iteration.

The roce gateway mac risk review confirmed that storage private-network gateway mac addresses do not need changes. On the compute network, the recommendation was to adjust one unit’s 8 leaf gateway mac addresses; this follows the System-d120a624b9 architecture, and while the current identical gateway mac addresses do not create business risk, a clearer structure will make troubleshooting easier. The gateway mac decision has been synchronized to Willa Quigley. Wynfell route advertisement work is still organizing existing production transaction route rules; once compute-side rules are in place, zephlink37 site is expected to add route advertisement policies next week, while other sites will update route acceptance rules without affecting the production network.

Segmented testing showed that PXE installation packet loss to some server out-of-band interfaces was caused by the server out-of-band cables. During storage client original-IP access to the storage server, debugging did not find switch-side arp packets from the server, so the switch could not build host routes, and no switch configuration issue was found. After GPU-side routing policy was adjusted, return traffic became symmetric and client-to-server access recovered. The team also supported Willa Quigley with ping testing while storage clients cleared arp or closed ports.

KELH work covered the Nyxfell firewall replacement and router layer-3 transformation. The Nyxfell focus was mainly Jyn-mesh76 replacement and writing the router layer-3 transformation plan; Jyn-mesh76 preparation was completed, including racking, cabling, plan writing, and configuration translation. The firewall replacement was finished in the first half of the week. For Wynbrook, the router layer-3 transformation change steps were written, related change scripts passed review, and because the architecture and routing were complex, the second half of the week was mainly spent drafting the routing change plan.

QOS deployment rules were reviewed with Pelshaw, confirming dedicated-line usage and the migration location. QOS configuration changes are being organized with Lumford, and the plan is waiting for Pelshaw to provide protected service IPs and protection priorities before vendor review. Daily network duty continued with alternating two-person weekly shifts, covering policy openings and switch port changes. The team deployed network security policies for Quilness and Daisy Jensen Chandler, opened Wynfell security policies, helped Quilness migrate switch-side BGP configuration, applied rate limiting after LG-NSJ and LG-UW dedicated-line traffic approached saturation after market close, handled switch ports for the Wynbrook System-0771ce6d1e virtual go-live, and traced the Pelmora EIP issue to internal EIP mapping changing from server-ip to vip, which caused intermittent access.

For Pelmora, firewall packet capture showed forwarding was normal but return traffic was absent, so the issue was handed to the business side. A 100G dedicated line was added between Beijing and Shanghai, and the team supported Pelshaw establishment and used iperf traffic to test link quality; after both routing diversion and link quality were normal, Lumford received the belanova device for traffic analysis. GG/System-880a73fa1a bastion host access to Shanghai 10.174.122.88 was abnormal because forward and return paths did not match, so the team coordinated with Beijing and confirmed a diversion approach that sends specified GG/System-880a73fa1a traffic over the new dedicated line while leaving other traffic on the old one, after which access to Shanghai 10.174.122.88 recovered. System-e22cbdbdd1 PXE testing included deployment-plan discussion and DHCP IP troubleshooting through switch packet capture; the DHCP problem was confirmed as a combination of switch configuration and test-method issues and was resolved. The team also helped Wynbrook access AWS-ECR, where official guidance suggested multi-concurrent downloads, although some downloads stayed slow and Lumford reported a carrier fault.
