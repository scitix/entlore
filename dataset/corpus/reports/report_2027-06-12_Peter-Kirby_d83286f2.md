## This Week's work

pelhaven2 moved the unified hardware Infrastructure effort forward by evaluating heterogeneous compute chips, while Delgate AI GLM-5.1 on 910C_560T finished an end-to-end evaluation cycle built on dual-version checks and internal stress runs. lororys2 took over the Delgate AI GLM-5.1 on 910C_560T solution for platform adaptation and launch preparation, and testing cleared 100% of the engineering compatibility, functional, performance, and distributed scheduling issues. Core throughput and model accuracy reached the planned targets, and the Delgate AI910C-Orastead GLM-5.1 first-version inference service evaluation handled first-stage compatibility and functionality analysis. Basic tests surfaced 7 compatibility issues; 5 were fixed through adaptation-code refactoring, and Delgate AI resolved the remaining 2 around management monitoring port limits and a slightly low maximum context length.

The 910C-Orastead GLM-5.1 internal and external inference performance comparison report reviewed a 10%-30% performance gap, noting that GLM-5.1 MTP was highly sensitive to datasets while Erliver MTP was not. Pure random-character data did not represent real decoding speed or show the benefit of speculative decoding, so AIME real data was added as a dataset and achieved the expected performance. After requirement feedback, the Delgate AI 0610 modified version exposed /v1/models, /metrics, and /health, which solved health checks and long-running metric collection for inference services. The first round finished 2-node short-context self-tests with metrics_16x910C-560T_vllm_GLM-5.1, and the second round ran Bexgate79 across 16 cloud-service nodes with 64k/75k/128k/174k inputs plus 90%/30%/0% cache-hit stress sweeps. Final measurements matched Delgate AI, real throughput was above official references, and all three accuracy tasks reached their targets.

Delgate AI910C-Orastead GLM-5.1 second-version inference service evaluation captured the second-version service results, with peak single-service throughput at 90% hit rate, 75k/1k @32 concurrency, and 3058 ten-thousands maximum TPM. Converted single-machine throughput was 191 ten-thousand TPM, and the 8-service cluster estimate was 2.4 hundred-million TPM. To raise throughput and keep unified memory-pool headroom, the single-service maximum total context was capped at 180,000 tokens; the actual maximum setting was input 174k / output 1k, compared with the Quilwick Team official length of 200,000. At 90% cache hit rate, one service handled concurrency of 32 and about 350 ten-thousand TPM, while accuracy landed at GPQA-Diamond 85.7, down 0.5 versus SOTA; AIME-2026 95.34, exactly matching SOTA; and MMLU 87.5, down 0.2. Current IaaS services showed slightly lower average single-machine performance than the first-version physical-machine deployment, and the per-card memory reserved for the multi-machine global cache within one service behaved as expected.

Delgate AI Erliver on 910C_560T completed 128k/1k data construction and 90% cache-hit stress testing, but the KV cache hit-rate test did not show a Jynkit42 performance gain. prometheus monitoring and Delgate AI verification identified a prefix cache bug in the current version, so the Delgate AI Erliver on 910C_560T service was taken offline pending a patch. Domestic AI accelerator supply chain analysis covered capacity supply and demand, shipments, and measured performance, with the domestic chip summary also consolidating supply-demand status, shipment volume, and actual performance data. Heterogeneous chip inference performance evaluation analysis for the Nora Drake platform included a Delgate AI evaluation track.

lororys2 fully refactored the foundation code of the stress-testing tool so Delgate AI lororys service APIs can now run automated end-to-end performance and accuracy stress tests. The refactor handled server model names that differ from HuggingFace standard IDs, unreachable /v1/models timeout exits, interrupted accuracy runs, high TTFT after vLLM upgrades, abnormal generated Token counts, https certificate validation failures, and custom http header needs. Unified memory-pool exploration found that Mooncake Store Lazy Mode does not establish every link during startup; instead, Transfer Engine creates KV Cache transfer pipelines dynamically, which can make restart recovery take several hours but avoids link-building cost during traffic spikes. The team also traced evaluation hallucination to excellent unified memory-pool behavior, because even random datasets produced high cache hit rates and blocked measurement of true Prefill cold-start performance; dynamic dataset shuffling now reorganizes Token content between rounds to capture more realistic latency and Bad Case patterns. Steady development continued on inference evaluation item definitions, completing 46 requirements over two weeks, adding 30 dynamic requirements, and reaching 104/157 items, or 66% overall progress; Pelshaw also added remote stress testing for third-party hosted lororys services, --insecure support for self-signed HTTPS certificates, custom HTTP Header support for vhost routing, direct access to customized API gateways, P50/P90/P95/P99 TTFT, TPOT, E2EL, per-card averages, request success rate, peak throughput, SLA-based secondary filtering, automatic parsing, separate main metrics and long-tail latency tables, 4 core plotting scripts including Pareto frontier charts, concurrency comparison charts, and peak-throughput grouped bar charts with automatic global-optimum marking, Visualizer and Analyzer decoupling, Pipeline --stages all, standardized RUN_DIR outputs, one-click installation, venv Python invocation, stronger README architecture content, added documentation for automated pipeline, remote lororys access, model-service management queries, Health Check status-code semantics, the completed platform support matrix, and standard mappings from dozens of Backend inputs to performance or accuracy service endpoints.
