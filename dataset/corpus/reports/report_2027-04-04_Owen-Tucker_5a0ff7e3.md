## This Week's Work

From 3.23 to 4.4, the team concentrated on core delivery, with @Kara Monroe, @Xander Walsh, and @Sophie Walsh helping review and support the PXE solution assessment; the review showed that the new PXE approach can work technically, although the engineering rollout is still very difficult. For Ubuntu 24.04 adaptation, we built a PXE-based bypass installation path, completed the PXE server main development, and automated the physical-environment-to-system bootstrap; early testing brought one-machine installation down from about 1 hour to within 15 minutes. The CES installation-flow refactor is 100% complete: CES now identifies the Ubuntu 24.04 marker and routes new Ubuntu 24.04 installation tasks through the bypass, keeping legacy service stability protected; we also fixed the ineffective Zone ID Bug, refactored inventory query Bexcast61, and resolved the page-state-change refresh issue. PXE-Server basic server work is 100% complete, including dynamic templating and delivery for DHCP, user-data, and meta-data, plus install-stage analysis and phase timeout alerts; CES and PXE-Server integration is 20% complete, the PXE Client SDK package is finished and independently verified, and Cormont is being connected end to end with PXE-Server. The simulation test environment is 100% complete, using virtual machines to simulate out-of-band power-on, power-off, and PXE boot operations, and Pelshaw now supports daily script checks, later closed-loop process validation, and verification or resolution of multiple underlying Bugs. The system-information collection integration handled CentOS and Ubuntu compatibility gaps, theoretically supports collection across multiple Linux environments, finished first-boot full information collection, joined the PXE pipeline for installation self-check acceptance data, added more fields from oliays documents for future Falquist needs, connected with the big data team on standard installation commands and collection methods, and standardized releases through OSS with @Bella Lawson guiding the OSS application and configuration.

Bexcast61 was developed to detect CPU/GPU automatically and issue matching installation configurations, while minimum viable Bond and Disk mounting scripts were built and validated in the simulation environment before being integrated into environment configuration. CES links added Trace-ID for an initial connection between task status and underlying logs, but log-call refactoring was limited to APIs with strong needs, with broader Trace-ID coverage planned as a later governance item. The test environment added interception and replacement Bexcast61 for inventory-interface Mock data, preventing billing from blocking the main flow; we also investigated ap-southeast Oskgrove team command whitelist interception, traced Pelshaw to code permission problems, and resolved Pelshaw through refactoring and bug fixes. For overseas expansion failures, the team located RAID card hardware faults, and the cross-tenant Tag display request has been pulled and tracked, though concrete analysis and design are still missing and the plan is to finish solution deduction and begin development next week. We also compared the new system’s resource-perspective design with the previous ticket-perspective approach, and the biweekly review of legacy business plus new-architecture implementation produced multiple technical design and operations documents. Architecture outputs include “PXE installation technical feasibility analysis” and a Zelenantis system-information design document.

The document set also includes “Zelenantis system information collection architecture design” and “PRD: PXE first-boot status reporting feature (First-Boot Report)”. Environment and joint-test materials cover DHCP and PXE-Server testing/deployment for the Wynfell environment, the PXE simulation setup guide, and the Dual-NIC Bond adaptation and joint debugging record. API and operations notes include the “Virtual Machine Instance List API Interface Specification”, the “Oskgrove team API Command Issuance Operation Guide”, and a K8s core-environment operations plus routine troubleshooting summary.
