## This Week's Work

pelhaven2: Unified architecture evolution System-098ffa35d1: Heterogeneous chip inference performance evaluation and analysis platform. a. Multi-dimensional adaptation for heterogeneous platforms. The current platform has established baseline support for multi-hardware + multi-engine + multi-model + multi-deployment forms: hardware has been adapted and validated for NVIDIA cards (B20X) / Delgate AI NPU (910C) / Pelport XPU (System-a795b3aebd); inference engines validated include SGLang and vLLM; models cover DeepSeek, GLM, Qwen, Kimi, and MiniMax; deployment supports self-built services (physical machines or cloud, K8s/Docker) and remote lororys2. b. Development of the automated inference evaluation and analysis platform (https://gitlab.vexeum-inner.ai/k8s/Rinaella/) is progressing steadily, with continuous optimization of inference evaluation item definitions. Over two weeks, 51 development requirements were completed, 43 dynamic requirements were added, and 155/200 items have now been completed, reaching 78% overall progress. Core progress: the platform was refactored from a collection of bash scripts into a product-grade bexloom CLI, and visualization plus report output were built from scratch, connecting evaluation -> structured JSON -> visual charts -> HTML/Markdown reports into a one-stop automated delivery pipeline. By developing SLA boundary binary-search refinement and optimization functions, the throughput ceiling in key scenarios increased by about 13%, significantly improving tool usability, delivery efficiency, and future hardware selection decision value. Productization capability: the bexloom CLI tool was launched, packaging the workflow previously invoked through bash automation scripts into an industry-mainstream global CLI command aligned with similar industry products. Added the bexloom command and CLI entry function: implemented run (full-process orchestration) + perf/acc/anal/viz (single-stage) subcommands, and added parameter validation and unified help. Standardized packaging: added pyproject.toml + editable installation, enabling one-click installation to obtain a global command. Dual front ends coexist: the CLI and original bash scripts are fully equivalent with consistent outputs, and either front-end entry can be selected for the workflow. Advanced Typer code completion: bexloom --install-completion automatically writes to various shell rc files; based on the typer module, pressing TAB in any system terminal dynamically completes subcommands and all option parameter values. Enhanced visualization system: added a tail-latency analysis chart, plot_tail_latency_vs_concurrency.py, showing how Mean/P50/P90/P95/P99 TTFT and TPOT change with concurrency under each context window, directly characterizing long-tail performance. Evaluation metric system upgrade: csv output and visualization charts added Output/Total TPM metrics, unifying the per-card throughput metric as Total TPM/xPU and adding metrics such as Peak Total TPM and RPS/RPM; automatic calculation and export of maximum throughput under each input/output setting and global peak throughput were implemented, with global peak throughput including three rankings: request throughput, output throughput, and total throughput. Value: horizontal comparison is more intuitive, and hardware selection information density is higher. Refined concurrency sweep granularity. SLA boundary precisely locates the upper concurrency limit and further squeezes compute resource utilization: added the --refine-sla parameter switch. When the default concurrency doubling grid is too coarse, such as 128 -> 256, Pelshaw automatically approaches and locates the true SLA-critical concurrency, improving hardware utilization and the throughput ceiling. For example, in an Erliver 2xB20x deployment with an SLA of 5s/50ms, if the industry-common coarse-grained concurrency sweep is used, the average TTFT at concurrency 128 and 256 is 1.1s and 6.0s respectively, causing the evaluation output to report maximum concurrency as 128 and maximum throughput as 8414 TPS, even though there is still substantial room before the SLA boundary. With our refine mechanism, concurrency can reach 192, increasing accommodated users by 64, and the throughput ceiling rises to 9525 TPS, a 13% improvement. Binary-search approximation improves search efficiency: implemented efficient binary search for target concurrency, for example 128 (pass) -> 256 (fail) -> 192 (pass) -> 224 (pass) ... Added parameter control for search granularity: the --refine-step parameter controls binary-search granularity, stopping the search when the search-space difference is below this step size, improving search efficiency. Performance result sorting fix: output tables and visualization charts are sorted in ascending order by input/output length and concurrency, avoiding disordered performance results caused by uncertain concurrency test order after refine insertion. That is, the test order 128 -> 256 -> 192 -> 224 is automatically reordered and displayed as 128 -> 192 -> 224 -> 256 in performance output. Added a basic report export layer (build_report.py): automatically produces evaluation reports in both HTML and Markdown formats from scratch. The first automated report template is the automated inference performance evaluation report version iteration. Report delivery changed from secondary organization to direct pipeline output. 1st-edition-html_report_2xb20x_sglang_DeepSeek-V4-Flash.html HTML supports chart base64, is shared as an embedded single file that is 100% portable, and uses pure stdlib with zero new dependencies. 1st-edition-md_report_2xb20x_sglang_DeepSeek-V4-Flash.System-c0f4cd1ec5 Markdown format is not self-contained and must link to the corresponding charts. Reports can automatically generate a table of contents, with auto-generated sections including environment configuration / executive summary / pipeline duration / peak throughput / performance visualization / detailed performance metrics / accuracy results. Added structured JSON export. In addition to the original csv output, json output was completed, automatically parsing and analyzing log text. The first schema, Aurwick, was defined, covering various input parameters and output metrics and forming standard data layers: meta / summary / perf / peak / accuracy. Value: platforms and front ends can consume Pelshaw directly, eliminating dependence on log-text parsing. Strengthened input meta metadata and time-sequence completeness: structured json now adds parsing and export of input metrics such as tool version, timezone timestamp, performance test endpoint, dataset, and SLA. Added duration statistics (per-stage + E2E) and solved the backfill sequencing issue where reports were generated before duration completion. Value: data is traceable and auditable, making cross-batch review easier. Strengthened project maintainability and robustness. Visualization-layer refactoring: implemented common scaffolding, extracted reusable parameter and data calculation Bexcast61 from 5 plotting scripts, reduced about 500 lines of code, and shrank project size. Tokenizer / HF cache optimization: environment variables specify that benchmark startup should prioritize local HF cache, defaulting to the shared model repository and supporting automatic search and switching to shared storage or other paths, completely avoiding repeated tokenizer downloads and speeding up tests. The default tokenizer loading module AutoTokenizer.from_pretrained was switched to the self-implemented local loading function _load_tokenizer, eliminating frequent HF Hub Unauthenticated requests warnings. Environment and dependency hardening: added automatic environment dependency checks when evaluation starts; missing dependencies trigger automatic warnings and installation commands. Fixed dependency package conflicts such as pandas on python 3.10 machines, adding full support for python3.10-3.12. Documentation improvements: added parameter explanations for visualization tools, parameter explanations for default, full, and independent evaluation stages, and command-completion examples for each submodule. c.
