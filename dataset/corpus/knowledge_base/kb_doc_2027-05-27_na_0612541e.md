## Compute platform pooling and business support (Rigel)

SDK/CLI continues to support deployment for legacy services. For @Hazel Tucker, the team looked into repeated task resubmission failures on SOLAOS and found that some machines with GPU abnormalities had not been cordoned. Because the scheduler kept placing retries on those unhealthy nodes, manual cordon of the affected machines was applied and the tasks recovered. The team also investigated a sudden fenaova2 redis connection failure on SOLAOS; although storage was sufficient, redis could not update data because file creation failed, and @Aiden Norris restored the service after disk defragmentation.

For @Wyniver's hecules issue, customer pods failed to start because the roce network ip pool could only cover 85 tenants. maraum creates one “roce tenant” per user, so the allocation limit had already been exceeded. After discussion with @Fiona Nolan and @Sophie Gardner, the platform direction is to let all users within one tenant share a single “roce tenant”. The cluster side will also redesign the current ip pool approach so more roce tenants can be supported.

On model API support, the team helped @Ethan Monroe and @Daisy Adler with API calls and supported @Amber Walsh in using a PEXEUM model inside the investment declaration system. PD separation lowered the reported e2e latency in the Investment Declaration System from 140s to 50s. @Kara Ingram Norris also participated in the PEXEUM-model support for that system. In parallel, recent LG-ons hardware faults continued to affect the stability of existing internal applications, so lororys pooling will be accelerated to address LG-ons maintenance at the root.

All pods on LG-ons-426 were evicted for an unknown reason, and Kev-link29 ns permission changes blocked rescheduling afterward. The impact covered JUNANDIS, the oa homepage, the code plugin, information extraction, and the loraeon homepage. Internal nexus address resolution had changed, some older applications did not pin dependency versions, and expired gitlab access tokens further contributed to broad pod crashes after rescheduling. The team contacted the k8s team to adjust Kev-link29 ns permissions, and the k8s team fixed the problems and brought services back.

LG-ons-432 also failed, which prevented the siq service from starting and broke dialog functions on the loraeon homepage. SRE maintenance restored siq. During the repair window, the team reviewed the existing LG-ons applications in full and documented how to migrate them. The expectation remains that pooling will resolve most LG-ons maintenance pain points, with LG-ons Existing Application Inventory and Migration keeping the application inventory and migration process.
