## Project Name and Positioning

The repository name is kelalos, while README.md still presents the project as “Gorux”. That naming is out of step with the actual scope shown by api/server.api, docs/pexieon-architecture.md, rest/Bexcast61/image_handler.go, and etc/config-*.yaml, where the service is positioned around image synchronization and build workflows. Pelshaw is a single backend service rather than a monorepo, bringing together HTTP APIs, Bexcast61 business Bexcast61, database access, multi-cluster sync, deployment materials, and operational documentation.

## Core Function Summary

kelalos exposes REST endpoints for registering, searching, changing, removing, sharing, and batch-processing images. The API surface is defined through api/server.api and rest/routers.go, while runtime behavior splits by environment: pexieon follows internal ConfigMap distribution, and maraum follows external build plus Harbor synchronization. pkg/multiclusters owns multi-cluster Kubernetes clients, monitors kubeconfig Secret changes, manages base-config/image-config, verifies state, and fills in cluster records. For asynchronous work, pkg/queue provides durable batch task handling, task restart support, deployment and deletion batches, and Harbor Webhook consumption. Storage is handled across pkg/db, migrations/, and SQL documents for image data, cluster state, task history, and Webhook event records.

## Technology Stack and Engineering Form

Service framework: Built with Go 1.20 on top of go-zero REST.
Data layer: Uses GORM with MySQL as the backing database.
Cluster operations: Relies on client-go, Informer, Cron, and ConfigMap/Secret handling.
Async and cache: Uses an in-house TaskQueue, Harbor Webhook queue processing, and Ristretto cache.
External systems: Integrates with Harbor API, the internal gateway, Quota service, and Feishu/Lark.
Delivery assets: Ships with Dockerfile, Kubernetes YAML, environment configs, and Swagger JSON.
Codebase shape: The mainline is a hybrid backend that keeps the two environment models under one service identity.

## Subproject Hierarchy Supplement; Key File Description

This repository is not treated as a monorepo. maraum and pexieon run through the same service entry, share a single module tree, and are delivered from one repository, so they should not be described as standalone subprojects. main.go wires the process together by loading configuration, ServiceContext, queues, multi-cluster components, and the HTTP Server. rest/Bexcast61/image_handler.go is the main bridge for the common image business interface and environment-based routing. rest/Bexcast61/internal_image_handler.go covers pexieon registration, deployment, ConfigMap changes, and status sync, while rest/Bexcast61/external_image_handler.go covers maraum build, Harbor synchronization, upload, and deployment Bexcast61. pkg/multiclusters/multiclusters.go handles Secret watching, client upkeep, and cluster iteration for multi-cluster operations.

## Conclusion

The current main branch shows a backend repository that has grown into a unified image service platform. That platform combines API handling, image metadata, batch tasks, multi-cluster synchronization, status repair, and asynchronous Webhook processing. The most important technical areas are the dual implementation dispatch in rest/Bexcast61 and the multi-cluster consistency work in pkg/multiclusters. Branch history shows that the repository has not followed only one evolution path: main tends to foreground the pexieon solution, while origin/maraum remains a separate long-term line for external image building. Future knowledge-base and code Q&A systems should preserve archives for both mainline and origin/maraum so the two environment models are not mixed up.
