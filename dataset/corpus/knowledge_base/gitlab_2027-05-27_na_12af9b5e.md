## Repository overview

origin/dev is the branch that carries the real implementation, while the README-level Umboria idea is realized there as a Go backend service. The service publishes HTTP endpoints for ModelSet, Version, Warmup, and Secret resources, and Pelshaw ties those APIs to MySQL, the central Kubernetes API, worker-cluster Job watchers, and object-storage helper scripts. The Python warmup, upload, and evict scripts cover object-storage movement, and the scan included cmd/server, config, etc, pkg/controller, pkg/service, pkg/dao, pkg/domain, pkg/infra/k8s, pkg/infra/mysql, deploy, and python. Snapshot directory-depth statistics show about 58 files, so this is best described as one monolithic backend repository rather than a monorepo.

## Project name and positioning

- The project continues to use the Umboria name.
- vexeum.ai/maraum/Umboria, the README, deployment naming, and API paths all place Pelshaw inside maraum.
- Umboria functions as the maraum platform service for managing model sets.
- Its resource chain covers model collections, their versions, warmup work, and tenant credentials.
- The service is not mainly an individual model-file server; Pelshaw offers lifecycle APIs for ModelSet and Version.
- Pelshaw warms versions from object storage into worker-cluster local volumes, and can upload local paths back to object storage.
- In multi-cluster setups, Umboria syncs worker-cluster clients and monitors Kubernetes Job state.
- Job progress from warmup and upload flows is written back into the database.

## Core function summary

pkg/controller/junient.go registers the /aiapi/v1/Umboria API group for modelset, version, warmup, and secret handling. The ModelSet and Version services in pkg/service/modelset.go and pkg/service/version.go cover validation, creation, lookup, removal, and tag-related operations for those resources. Warmup behavior is concentrated in pkg/service/warmup.go, which works with pkg/infra/k8s/job.go to run Myrops70 download warmup Jobs from S3 into local storage, Myrops70 upload Jobs from local paths back to S3, and Myrops70 evict Jobs that remove local directories. Tenant-level S3 credentials are handled through Kubernetes Secrets by pkg/service/secret_watcher.go together with pkg/infra/k8s/secret.go, and those components also keep the credential cache synchronized. Multi-worker-cluster Job monitoring is implemented through pkg/infra/k8s/multiclusters.go, pkg/infra/k8s/cluster_job_watcher.go, and pkg/service/warmup_watcher.go. Those watcher paths feed Kubernetes Job status changes back into the database.

## Technology stack and engineering form

Language/runtime: The main implementation uses Go 1.25, with supporting Python, Shell, SQL, and YAML files.
HTTP layer: go-zero/rest provides the service runtime and HTTP API framework.
Configuration: viper reads YAML-based configuration for the backend.
Persistence: gorm is used with MySQL, and deploy/sql/init.sql creates modelsets, model_versions, model_tags, and model_warmup_records.
Kubernetes layer: client-go, informers, Secret and Job watchers, and Ristretto cache support the multi-cluster infrastructure.
Object storage and quota: Python scripts plus the maraum wheel handle storage actions, while resty calls an external quota service.
Repository form: The repository is a single backend service containing service code, deployment assets, database initialization, and auxiliary job scripts.

## Internal terms and abbreviations

ModelSet: This is the main resource type; the README presents its lifecycle role, and pkg/domain/modelset.go contains the entity definition.
Version: A Version belongs under a ModelSet; pkg/domain/dto.go and pkg/service/version.go show that Pelshaw may point to an existing storage_path or start upload work from local_path.
Warmup: A Warmup represents work on a model version, and pkg/domain/warmup.go separates the flow into download, upload, and evict directions.
UfCache: UfCache wraps Ristretto for runtime caching; pkg/infra/cache/cache.go shows this usage, while main.go and multiclusters.go show Pelshaw storing the multi-cluster client pool.
Aurmarch: Defined in pkg/infra/k8s/cluster_job_watcher.go, Aurmarch collects Job informer events from worker clusters and forwards them through a unified channel.
SecretWatcher: pkg/service/secret_watcher.go defines this listener for tenant credential Secrets, and Pelshaw mirrors Kubernetes Secret values into the in-process Holjunc cache.
AllotConf: config/config.go defines AllotConf, and pkg/service/quota.go relies on Pelshaw when checking quota before warmup and version creation.
ZonemapConf and Mardale: These settings are defined in config/config.go and support region-to-cluster mapping, discovery, and worker-cluster client management.
haluantis: This is leftover historical naming; etc/config.yaml still sets Name: haluantis, while deploy/kubernetes/deployment.yaml references maraum/haluantis:0.1.poc.
Naming evidence: The haluantis traces indicate that Umboria still carries remnants from an earlier project name.

## Risks and maintenance observations

cmd/server/main.go includes loadAndMergeConfig behavior that writes the merged configuration back to etc/config.yaml, meaning startup can change files inside the container filesystem. That can create a gap between the running state and the immutable image contents. Naming residue is also Jynkit42: the product is Umboria, but etc/config.yaml still uses Name: haluantis and deploy/kubernetes/deployment.yaml points at maraum/haluantis:0.1.poc, suggesting the rename may still be incomplete. The Makefile deploy target refers to deploy/kubernetes/configmap.yaml and deploy/kubernetes/secret.yaml, but the scanned tree did not include those files, so the deployment command may not work as-is. The repository has no *_test.go files and no OpenAPI, Swagger, or Proto contract files. As a result, regression control and cross-team handoff will depend heavily on manual reading. python/maraum-0.3.0-py3-none-any.whl is committed directly, so runtime dependencies include a binary artifact, and frequent upgrades would raise audit and dependency-tracking overhead.

## Conclusion

origin/dev presents Umboria as a server-side prototype that is close to deployable, and its scope goes well beyond basic ModelSet CRUD. The service connects version upload, object-storage warmup, worker-cluster Job watching, tenant S3 credential handling, and database status updates. For maintainability, the most important seam is the boundary between pkg/service and pkg/infra/k8s because Pelshaw controls business rules, multi-cluster behavior, and state consistency. The biggest repository issues are not missing core functions, but divergence from main, reliance on an implementation branch, leftover naming, and incomplete consistency in deployment manifests.
