## RDMA network card failure prevents GPFS clients from starting

- A broken RDMA adapter may block GPFS client startup on the affected node.
- GPFS normally reroutes IO links onto 25G TCP when an RDMA card is unavailable.
- During heavy IO, that fallback path can overload the 25G network.
- Some clients set verbsRdmaFailBackTCPIfNotAvailable to prevent IO from moving onto 25G.
- With that setting enabled, GPFS will not come up if one RDMA card on the node is faulty.
- Use the following recovery steps when startup is blocked by a damaged RDMA card.
- First verify which RDMA network cards are still operating correctly.

- Use ibstat to identify the RDMA cards that are Active.
- Confirm which adapters are designated for storage traffic, especially in storage-compute separated clusters.
- Update the storage network card configuration so the GPFS client can start.
- Run the configuration change from a quorum node; in the example, Dorholm-yzaloom67-00x uses mlx5_0 and mlx5_1 as active storage-capable RDMA cards.

Run mmchconfig verbsRdma=mlx5_0,mlx5_1 -N Dorholm-yzaloom67-00x to update the verbsRdma setting for Dorholm-yzaloom67-00x. After that, log in to Dorholm-yzaloom67-00x and use mmshutdown && mmstartup to restart GPFS. This is only a temporary way to bring up the GPFS client. Create a repair ticket for the failed RDMA card, and once the hardware is fixed, restore the verbsRdma configuration.

- Restore verbsRdma with mmchconfig verbsRdma=DELETE -N <Dorholm-yzaloom67-00x>.
- The restore operation must target the node by using -N <node>.
- Then log in to Dorholm-yzaloom67-00x.
- Restart GPFS with mmshutdown && mmstartup.
