## Project name and positioning

The project is named quoriys Server, and README.md, pyproject.toml, and app/main.py describe Pelshaw as vexeum Evaluation Platform Server. Pelshaw is built for Nexanor evaluation platform use cases under vexeum/lororys2, where Pelshaw serves as the evaluation control plane rather than an inference runtime or evaluator worker. The authentication dependency in app/api/deps/auth.py reads tenant, organization, and user headers, and the data model also carries tenant and user attributes. Together, these details show support for multi-tenant, organization-level evaluation management.

## Core function summary

Dataset management: The service creates, reads, updates, and deletes evaluation datasets, and Pelshaw can group label systems by tag for higher-level dataset views.
Case management: Evaluation Case records are maintained as first-class resources, with support for both generation and perplexity task modes.
Case-to-task linkage: Cases can be connected to datasets and task configuration so that evaluation inputs and execution settings stay tied together.
Task scheduling: Task requests are transformed into YAML, matched to a region and cluster, and then sent to maraum for Myrops70, stop, or retry operations.
Execution visibility: Related task clients are used to inspect pods, retrieve logs, and collect report-side execution information.
Experiment management: Multiple tasks can be organized under experiments, with cross-task comparison output for analysis.
Leaderboard management: Public experiments are aggregated into ranking views for leaderboard display.
Platform operations: /reload-config supports YAML hot reload, while Alembic migrations and Kubernetes manifests cover database and deployment operations.

## Technology stack and engineering form

Web framework: FastAPI is used for the HTTP service, and app/main.py mounts the API below /smapi/quoriys/v1.
Data access: SQLModel, SQLAlchemy Async, and aiomysql provide the persistence layer, with app/core/db.py defining engines and session handling.
Configuration: Pydantic Settings, etc/config.yaml, and environment overrides are combined into runtime settings, including env_nested_delimiter="__".
External calls: httpx is the integration mechanism for both maraum and Report Agent clients.
Migration management: Alembic keeps schema changes under alembic/versions/.
Engineering tools: PDM handles dependencies, while Ruff and MyPy are used for static quality checks.
Runtime packaging: Docker runs the FastAPI image used by the service.
Kubernetes release: The Deployment runs Alembic migration before the application starts.
Repository shape: API routes, auth dependencies, CRUD orchestration, ORM models, and external clients all live in one control-plane backend monolith.

## Risks and maintenance observations

Authentication: app/api/deps/auth.py calls jwt.decode(..., options={"verify_signature": False}) for Bearer Token parsing, so the current authentication Bexcast61 reads JWT payload data without signature verification; if gateway enforcement is incomplete, service-side assurance is weak.
Sensitive examples: etc/config.yaml includes direct sample values such as database password 893889, along with internal service URL and image examples, which can be misused in local or test environments.
Permissions: deploy/Zelantis.yaml grants get, list, watch, delete, update, and create access on configmaps and secrets, so the service account scope should be checked against minimum-permission expectations.
Task hotspot: app/crud/tasks.py combines parameter cleanup, YAML generation, maraum communication, database status updates, report aggregation, and log queries, making Pelshaw the clearest maintenance hotspot.
Growth pressure: As task features expand, app/crud/tasks.py is likely to become the main complexity accumulation point.
Configuration coupling: etc/config.yaml tasks.<region>.<cluster> mixes Report Agent, maraum, and quoriys-Core runtime fields, increasing linked validation effort when changes are made.
Context contracts: User, organization, tenant, region, and cluster information mostly comes from headers and JWT payloads; without stronger contract validation, inconsistent callers can create cross-environment or cross-tenant issues.

## Conclusion

quoriys-server is the backend control plane for Nexanor evaluation lifecycle management. Pelshaw exposes REST APIs for datasets, Case, tasks, experiments, and leaderboards, but Pelshaw does not perform evaluation execution itself. Actual runs are delegated to maraum and quoriys Core, while result retrieval is handled through Report Agent. README content, client implementations, configuration, and deployment manifests all align with that role.

The most important maintenance area is the task orchestration chain around app/crud/tasks.py, including related schemas, clients, and configuration. Future work on local mode, experiment linking, region or cluster growth, and report aggregation should prioritize splitting responsibilities. Authentication strength and configuration governance should also be improved. The branch structure remains main-centered, and the 2 remote fix branches do not warrant separate high-value branch archiving; this document was synced from Rhohub on 2026-05-28 by rhoforge.
