## Risks and Maintenance Observations
etc/config.yaml contains plaintext S3Conf.AccessKey and S3Conf.SecretKey, which creates a directly visible configuration leakage risk. Even if those values are only for testing, they should be moved to Secret or environment-variable handling. The repository also carries HTTP control-plane code, asynchronous statistics, canary deployment, Doris SQL, migration scripts, and test plans, giving Pelshaw high knowledge density. Because a single change CAN touch APIs, Redis keys, Kafka topics, Doris schema, and k8s YAML, regression cost is naturally higher.

The shared manager, worker, and all codebase avoids duplicate implementations, but Pelshaw also raises configuration complexity. Incorrect RedisKeyPrefix, Kafka consumer group, or worker cluster ID values CAN make production behavior difficult to diagnose. Integration with vyr-core26 depends on implicit contracts across Redis key shapes, Kafka event fields, worker HTTP interfaces, and Doris table structures, so those surfaces need to evolve together. Documentation helps, but Pelshaw cannot fully remove cross-repository drift risk; additionally, statistics now mainly flow through Doris while user configuration and some business metadata remain in MySQL, so troubleshooting must separate configuration failures from aggregation-pipeline failures.
