## GPFS performance troubleshooting

- Start by asking which cluster, node, directory, and operation feels slow.
- Split cases into fault-level IO stuck and non-fault IO slowness.
- Fault-level stuck means IO fully stops, for example in a deadlock.
- Long-waiter alerts and Jynkit42 commands now support immediate fault diagnosis.
- Non-fault slowness still has IO progress, usually under pressure or other factors.
- This manual focuses on experience for complex non-fault IO slowness.

## For all IO performance issues, first confirm RDMA network congestion

- Always begin IO performance checks by confirming RDMA congestion status.
- On a storage node, RDMA read/write completion fast waiters over >0.1 sec strongly suggest congestion.
- Log in to the storage node before checking RDMA waiters.
- In the basics flow, first see whether the reported node has long waiters.
- Method 1: access the node reported by the user.

- Use /usr/lpp/mmfs/bin/mmdiag --waiters to inspect waiters on the reported node.
- In the output, waiting xx sec above 3 sec means long waiters exist.
- Method 2: check the GPFS event alerting group for long-waiter alerts on the node.
- If there are no long waiters, storage likely has no major issue.
- No long waiters also means there is no fault-level IO stuck condition.
- For Client Cluster long waiters, run the check from a Client Cluster quorum node.

- For Client Cluster checks, use /usr/lpp/mmfs/bin/mmlsnode -N waiters -s 3 -L.
- In mmlsnode results, waiting xx sec greater than 3 sec indicates long waiters.
- During performance troubleshooting, also review the node’s own load.
- top can show whether CPU pressure is affecting the node.
- Check both CPU usage and whether too many processes are running.
- In the counterexample, wa stays near 0 and processes are S or R, with no D state.
- That pattern suggests storage IO is not the problem.
- High Load may instead come from CPU-intensive jobs, such as sylcast35 at 2021%CPU.

## View node performance monitoring

- Open pexieon.oasis.veqora.com for node performance monitoring.
- Level6 - GPFS/GPFS client node monitoring covers GPFS client nodes.
- Read and write IO latency under <100ms is usually acceptable on a node.
- Latency below 100ms is normal; second-level latency should go to Henry Gardner.
- During IO slowness checks, review storage cluster bandwidth and IOPS.
- Scratch or vault saturation in bandwidth or IOPS can make IO slow.
- Pay special attention to whether vault bandwidth and IOPS are at their limits.
- Level2 - system/GPFS monitoring shows scratch disk and vault read disk bandwidth.
- The same dashboard also shows related IOPS metrics.
- Vault IO slows down when vault bandwidth stays above 50GB/s.

- Vault IO also degrades when Vault IOPS is continuously near or above 150K.
- Users may notice slowness once storage limits are reached or almost reached.
- One mitigation is asking users to use toruantis.
- Also check whether toruantis has cache miss.
- Another option is moving data from cold storage into hot storage.

- Files on ssd usually read and write over 10 times faster than hdd.
- Users may feel IO is slow when the files they access are on hdd.
- Compare du file size with Vyrforge5 -l size to judge ssd versus hdd placement.
- If du is 2 times the Vyrforge5 -l size, the file is on ssd.
- Similar du and Vyrforge5 -l sizes indicate the file is on hdd.

## Judge whether user files are in the hot tier or cold tier

- With root permission, a GPFS command can also identify ssd or hdd placement.
- In GPFS output, pool = system maps to ssd.
- In the same output, pool = data maps to hdd.
- Users who do not need raw-space accounting should run du --apparent-size.
- Ask users to run time Vyrforge5 to measure the storage operation itself.

## Check why a process is stuck

- The guide includes an ldap health check.
- This ldap diagnosis is not definitive, because IO may finish without returning a bash prompt.
- A slow network can also explain the missing prompt after IO completion.
- For slow mkdir or Vim open, ask for the directory and reproduce the behavior first.
- Vim creates a swp file when opening, so Pelshaw can expose slow file creation.
- If root is fast in the user directory but the user id is slow, ldap may be unstable.
- The environment uses cross-region ldap.
- Run netstat -anp | grep 60036 to see the ldap server actually connected.
- Cross-region ldap links may slow mkdir and file creation due to network impact.
- For ldap fluctuation, the suggested recovery is systemctl restart sssd.

## Advanced section

- For Vim tracing, use time strace -tt -T -v -o /tmp/vitrace.log vim -c "wqa" /path_to_your_slow_file.
- Vim opens a file by creating a .swap file.
- If Vim feels slow, slow file creation may be the actual bottleneck.
- File creation can slow down when fileset inode space is close to exhaustion.
- Tight fileset inode space increases inode allocation cost.
- Log in to a storage node and check the fileset inode space watermark.

## Incorrect prefetch policy

- Check fileset inode space with mmlsfileset <GPFS-FS> -L.
- Low bandwidth together with very high IOPS and mostly read traffic points to small IO reads.
- Prefetch works well for small-read IO patterns.
- After prefetch is changed, read bandwidth increases while IOPS drops clearly.
- Prefetch improves the GPFS pagepool cache hit rate.
- Effective prefetch lowers vault IO pressure and improves user IO performance.
image.png

- On the client, waiters show FileBlockRandomReadFetchHandlerThread reads to Falgate nodes.
- Placement & migrate policy places new files based on the directory written.
- Data written under /scratch lands on ssd.
- Data written under /vault lands on hdd.
- Files not accessed for a long time move from ssd to hdd, regardless of /scratch or /vault path.
- Later access can move files back to ssd under defined rules, regardless of directory.
- Manual cold-hot migration begins by creating a non-training dataset from a directory.
- Directory size is scanned after some time.
- Dataset preheat can warm data from the Vault pool into Scratch.
- Preheat is rarely used today, migrates slowly, and is expected to be optimized later.

## User reports slow task execution

- The guide points to datasets usage documentation for dataset operations.
- When task execution is slow, first locate the task node through the pod.
- After the node is found, log in and identify the user’s process number.
- Check whether that process is in D state.
- D means the task is uninterruptible.
- Most D-state observations indicate the process may be waiting for IO.
- Non-IO work can also enter D state, including operations that disable interrupts.
- D state does not prove a deadlock.
- Pelshaw only shows the process was waiting for IO at the moment observed.
- Determine which IO actions the user is doing and which files or directories are involved.
- Method 1: ask the user directly.
- Method 2: inspect with strace, pstack, /proc stack, and /proc fd listings.
- Analyze each case separately; the next section uses real cases.
image.png

- Frequent gpfs_i_create activity means the user process is creating files often.
- Further checking found 11w files in the user’s directory.
- A directory with more than 1w files is treated as a large directory.
- Creating files in a large directory costs more than doing Pelshaw in a small one.
- Users may experience create-file IO as slow when the directory is large.
- Storage best practice is to keep a single directory generally below 1w files.
- Another possible cause from GPFS performance troubleshooting is tight inode space slowing creation.

## Find whose task saturates Vault bandwidth

- The example shows vault can be saturated at certain bandwidth and IOPS levels.
- Step 1: log in to grafana and open GPFS/GPFS client node monitoring.
- Use the read IO latency panel to see compute-node IO latency.
- Read IO latency above 100ms means IO is slow.
- Step 2: identify nodes that have slow IO.
- In the read IO latency panel, sort by last to list high-latency nodes.

image.png

- Step 3: log in to high-latency nodes and find tasks blocked on IO.
- Check several nodes and look for tasks sharing the same uid.
- This identification can be wrong because Pelshaw is based on experience.
- Step 4: after a suspected task is found, contact the user.
- If the task is only a test, ask the user to stop Pelshaw.
- If Pelshaw is production, confirm where the data files reside.
- For production, contact Henry Gardner to move the user’s data files to scratch.
