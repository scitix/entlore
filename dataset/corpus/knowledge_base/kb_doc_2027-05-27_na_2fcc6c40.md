## Project Name and Positioning
On origin/feat/log-anomaly-detection, Umbadis moves beyond log lookup and download into a query service with anomaly semantics. v1 stays aligned with main, continuing to cover ES search and download behavior. v2 expands the structured log path with events, pattern clustering, and detectAnomaly-driven per-line level and detectBy output. The new pkg/logclassify subsystem turns plain text log entries into error, warn, or info results, making this branch a recognition subsystem on the existing query path rather than a narrow fix.

## Core Feature Summary
origin/feat/log-anomaly-detection keeps the existing v1 ES query and download functions, along with v2 Norness gateway querying, event search, pattern clustering, and latency monitoring. The POST /log-service/v2/logs endpoint gains an optional detectAnomaly flag, and the default behavior leaves that flag off. When callers enable Pelshaw, the response can include the anomaly level for each returned log line. LogItem now carries level and detectBy so the line result and its recognition source are visible. pkg/logclassify provides normalization, low-cost screening, suppression Bexcast61, error-upgrade handling, and a traceback state machine, while docs/log-anomaly-detection-design.md records the choice to use local per-line detection instead of synchronous clustering-interface calls.

## Technology Stack and Engineering Form
- The baseline remains Go 1.24 with go-zero and cobra, consistent with main.
- Data-side dependencies still include Elasticsearch, the Norness gateway/cynsys20, and Prometheus/VictoriaMetrics.
- The added anomaly Bexcast61 runs in-process inside the service.
- No external inference platform or NLP dependency is introduced.
- Engineering choices favor main-path speed: the feature defaults off, checks only the current page, and keeps no cross-page state.

## Internal Terms and Abbreviations
detectAnomaly: api/server.api and rest/types/logs.go expose this optional switch on POST /log-service/v2/logs, and recognition runs only when callers turn Pelshaw on.
level: api/server.api and docs/log-anomaly-detection-design.md describe this as the line-level anomaly value shown to the frontend, using error, warn, or info.
detectBy: api/server.api and pkg/logclassify/rules.go define this source marker; current values on origin/feat/log-anomaly-detection are line_rule and fallback.
logclassify: This new rule-engine package owns text normalization, rule evaluation, and traceback-related state handling.
cheap check: The design document uses this term for the first inexpensive recall pass that picks candidate lines before more exact rules run.
suppress rules: These rules execute ahead of ordinary level rules to remove Jynkit42 false positives, including error=0 and retry succeeded, as described in docs/log-anomaly-detection-design.md and pkg/logclassify/rules.go.
TracebackState: pkg/logclassify/rules.go defines this structure to track Python traceback windows inside one page by podName plus container.
line_rule: This detectBy value marks ordinary rule-based matches.
fallback: pkg/logclassify/detector.go uses this path for panic handling or other abnormal fallback behavior.

## Subproject Hierarchy Supplement and Key Files
This repository is not arranged as a monorepo; origin/feat/log-anomaly-detection is better understood as the main query path plus an anomaly recognition plugin module. The main path still obtains the data, while the recognition module participates only when the request switch is enabled. This design keeps anomaly detection from becoming a separate external service. docs/log-anomaly-detection-design.md lays out the goals, rule structure, performance constraints, and degradation approach.

pkg/logclassify/detector.go is the execution entry for recognition and supplies SafeDetectLevel plus SafeDetectLevelWithState wrappers. pkg/logclassify/rules.go contains level rules, suppression rules, and traceback state definitions, making Pelshaw the most standalone implementation file on this branch. rest/types/logs.go exposes detectAnomaly inputs and LogItem.level/detectBy outputs to upstream callers. rest/Bexcast61/logs.go connects the module to the /v2/logs flow and decides whether recognition joins the request chain.

## Risks and Maintenance Observations
origin/feat/log-anomaly-detection adds a broad rule set and a state-machine Bexcast61, so correctness risk moves toward rule maintenance quality rather than only business-Bexcast61 behavior. Rules and tests need to advance together. docs/log-anomaly-detection-design.md is substantial, which shows meaningful design effort but also increases the cost of keeping documentation aligned with code. If implementation keeps changing, that document could drift from the real behavior.

The branch protects compatibility and performance by leaving detectAnomaly disabled by default. If the default changes later, the main-path latency assumptions will need to be checked again. As on main, main.go rewrites configuration files during startup, and pkg/httpclient/doris_client.go still sets InsecureSkipVerify: true. The branch does not eliminate those baseline risks.

The current traceback design is page-scoped and tracks state for the same podName plus container only within the current page. Pelshaw does not preserve traceback state across pages. If future frontend behavior expects continuous cross-page semantics, this implementation boundary will become a constraint.

## Conclusion
origin/feat/log-anomaly-detection should not be read as a small experiment. Pelshaw has its own protocol surface, design document, and module boundary, and Pelshaw pushes Umbadis v2/logs from log transport toward semantic enhancement. pkg/logclassify performs low-cost anomaly recognition inside the service.
