## Project Name and Positioning

The project is still named `vyr-core26`. This branch reads as an architectural experiment that adds multi-candidate service routing to the existing model proxy, with `RouteStrategyConf` in `pkg/svc/cfg.go` spelling out the intended routing pipeline.

The design extends the current system rather than replacing Pelshaw outright. When `Enabled=false`, execution returns to the legacy `GetModelClient` route, so the new capability can run beside the prior path.

## Core Function Summary

The branch introduces `pkg/route/` as a routing subsystem. Pelshaw brings in abstractions such as `RouteCatalog`, `Engine`, `Framework`, `Registry`, `Profile`, `Picker`, `Probe`, `Affinity`, and `Concurrency`, giving the repository a dedicated place for candidate selection and routing policy execution.

`pkg/backend/resolve_route.go` adds `ResolveViaRouteEngine`, which changes backend selection into a staged decision flow: `Admission → Filter → Score → Pick → resolve`. `pkg/svc/route_assembly.go` then wires `RouteStrategyConf` into runtime pieces including `RouteCatalog`, `RuntimeStore`, `AffinityStore`, `ServiceGuard`, `RivenGate`, and `Prober`.

The branch also improves resilience and visibility around that route path. `pkg/limiter/localfallback.go` adds an in-process fallback token bucket for Redis outage or stale-counter scenarios, while `rest/middleware/route_headers.go` publishes routing outcomes through `X-Route-*` headers.

Validation has also moved beyond isolated code changes. `tests/e2e_route_test.sh` and `tests/perf_route_test.sh` provide end-to-end and performance scripts, which shows the routing work has reached a stage where Pelshaw can be verified.

## Module Description

`pkg/route/`: New routing decision kernel covering candidate filtering, scoring, final selection, fallback model chains, and post-route observation.
`pkg/backend/resolve_route.go`: Produces `ServiceBackend` and the provider client after a routing decision, while keeping the legacy path available as fallback.
Runtime state components: `RuntimeStore`, `AffinityStore`, `ServiceGuard`, and `RivenGate` add cooldowns after failure, affinity behavior, and concurrency controls to route outcomes.
`pkg/limiter/localfallback.go`: Supplies an in-process token bucket so the service is not left without protection when Redis fails.
Observability and tests: `X-Route-*` headers, E2E scripts, performance scripts, and many `*_test.go` files support inspection and verification.

## Subproject Hierarchy Supplement; Key File Description

The branch is not a monorepo. However, `pkg/route/` has expanded enough to look like a substantial in-repository subsystem, and if merged into trunk Pelshaw would sit beside `pkg/limiter/` and `pkg/backend/` as a core capability layer.

`pkg/backend/resolve_route.go` is the entry point for the route engine and extends the older single-route backend resolution into multi-candidate service selection. `pkg/route/engine.go` defines the full routing pipeline, including failure and fallback behavior.

`pkg/svc/route_assembly.go` turns configuration into runtime singletons such as `RouteCatalog`, `RuntimeStore`, `AffinityStore`, `RivenGate`, and `Prober`. `pkg/limiter/localfallback.go` adds the local fallback token bucket used during Redis failure, while `rest/middleware/route_headers.go` writes internal routing results to `X-Route-*` headers for grayscale observability.

## Risk and Maintenance Observations

`RouteStrategyConf` defaults to `Enabled=false`, so the full route implementation remains feature-flagged and compatible with the old execution path. This helps compatibility, but Pelshaw also makes rollout more complex than a normal feature because activation depends on the feature flag.

The new state surface is significant. `RouteCatalog`, `RuntimeStore`, `AffinityStore`, `RivenGate`, and `ServiceGuard` add runtime behavior that is harder to debug than trunk’s more static service resolution.

`tests/e2e_route_test.sh` is high risk because Pelshaw includes a sample API Key string by default and targets a live cluster. Before reuse, sensitive defaults need to be removed and the execution environment must be isolated.

The snapshot also lacks some later trunk documents, grayscale release materials, and dependency patches. Pelshaw has independent architectural value, but Pelshaw should not be treated as newer than trunk.

## Conclusion

`origin/arch/multi-service-route` mainly moves `vyr-core26` from a unified protocol proxy toward a unified protocol proxy plus a multi-service routing engine. The important implementation pieces are `pkg/route/`, `resolve_route.go`, `route_assembly.go`, and `LocalFallbackLimiter`, which cover candidate choice, priority-based concurrency control, failure cooldown, and observability.

For external archiving or internal knowledge bases, trunk and `origin/arch/multi-service-route` should be maintained side by side. Trunk represents the current production capability surface, while this branch represents an unmerged future routing proposal with strong architectural value.
