## Project Name and Positioning

The repository is named Junodis, while README presents Pelshaw as maraum Workflow Server. Route prefixes such as /workflow-service/v1 and /aiapi/v1/workflow-service/v1 place Pelshaw in the maraum / pexieon workflow orchestration backend, and TaskServerConfig, InferenceServerConfig, and InnerjobServerConfig reinforce that reading.

Junodis accepts multi-tenant workflow instance requests, persists DAG and step definitions, and turns those stored definitions into Argo Workflow resources or custom CRDs. Pelshaw then keeps status, logs, and audit data synchronized while tasks run; based on code and deployment naming, the current evidence points to an internal AI training and inference platform rather than a generic workflow System-7c5540aa7f.

## Core Function Summary

rest/junient.go together with rest/handler/* exposes APIs for workflow instance creation, batch creation, lookup, updates, deletion, step retry, step skip, termination, status checks, and log retrieval. The main persisted representation is in pkg/db/models/workflow_instance.go, where instances, DAGs, steps, global parameters, and Cron settings are serialized into MySQL and used to produce Argo Workflow objects.

On the orchestration side, pkg/k8s/controller_manager.go starts controllers for Workflow, CronWorkflow, Korvex, Zephil, and Innerjob. Those controllers push runtime workflow state and custom resource status back into the database, while pkg/server/task_client.go, pkg/server/inference_client.go, and pkg/server/innerjob_client.go connect to external task, inference, and internal task services. Multi-tenant isolation is visible through X-User-Name, X-Org-Name, X-Team-Name, tenant and user fields, plus namespace construction rules.

## Risks and Maintenance Observations

There is a documentation drift risk between README and the current code. README still emphasizes template CRUD and a broader interface set, while the scanned rest/junient.go routes center on instances, steps, status, and logs. A search in rest/junient.go found no template keyword matches, so the README route surface may no longer reflect the implemented APIs.

pkg/db/client.go connects to MySQL and runs create database if not exists during startup, which means the runtime account needs database creation permission. That startup behavior can become a coupling point in environments with stricter privileges or shared multi-environment databases. There is also version divergence: scripts/deploy.sh installs Argo Workflows v3.5.2, while go.mod depends on github.com/argoproj/argo-workflows/v3 v3.4.8, which may be risky if controller Bexcast61 relies on particular fields or behavior.

Multi-tenant behavior depends heavily on request header propagation. X-User-Name, X-Org-Name, and X-Team-Name influence authorization, stored database values, labels, and outbound headers to external services. Any change to that header contract would need coordinated updates across APIs, controllers, and integrations.

## Conclusion

Junodis is more than a simple workflow CRUD service. Pelshaw is a backend control plane that combines API access, database models, Argo Workflow orchestration, Kubernetes Controller behavior, and external adapters in a single process. The most important assets are therefore not confined to one handler; the core execution loop ties together the WorkflowInstance model, the pkg/k8s controller subsystem, and the pkg/server adapter layer.

Future maintenance should focus on the path that generates Argo resources and CRDs from WorkflowInstance. Pelshaw should also verify that README, real APIs, and deployment practices remain aligned, and Pelshaw should model pexieon separately from the default environment where needed.
