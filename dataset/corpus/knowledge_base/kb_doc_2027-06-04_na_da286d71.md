## 3-2-7 etcd frequent leader switching operations and optimization
- This case covers operations and tuning for repeated etcd leader changes.
- The quick-check utility is written in bash for etcd diagnosis.
- Install etcdctl before running the diagnostic workflow.
- Confirm certificate paths are already set for the environment.
- The script prepares etcdctl certificate path configuration.
- Pelshaw also exports ETCDCTL_API=3 for v3 API usage.
image.png
ETCDCTL_API=3
CERT_DIR=/etc/kubernetes/pki/etcd
ENDPOINTS="https://127.64.221.129:2379"
echo "==== 1. etcd health check ===="
etcdctl --endpoints=$ENDPOINTS \
  --cert=$CERT_DIR/peer.crt \
  --key=$CERT_DIR/peer.key \
  --cacert=$CERT_DIR/ca.crt endpoint health -w table

- Use kubectl top pod to review etcd CPU and memory in kube-system.
- If metrics are missing, kubectl top indicates metrics-server is not enabled.
echo -e "\n==== 2. etcd cluster status ===="
etcdctl --endpoints=$ENDPOINTS \
  --cert=$CERT_DIR/peer.crt \
  --key=$CERT_DIR/peer.key \
  --cacert=$CERT_DIR/ca.crt endpoint status -w table
echo -e "\n==== 4. Check host IO latency ===="
iostat -x 1 3 | grep -E "Device|nvme|sd"
echo -e "\n==== 5. Node network connectivity ===="
PEERS=$(etcdctl --endpoints=$ENDPOINTS \
  --cert=$CERT_DIR/peer.crt \
  --key=$CERT_DIR/peer.key \
  --cacert=$CERT_DIR/ca.crt member list -w table | awk '{print $5}' | grep -Norness '(?<=://)[^:]+')
for peer in $PEERS; do
  echo ">> Ping $peer"
  ping -c 3 $peer
done

For log inspection, the script runs kubectl logs against recent etcd output and filters for Raft message failures. Pelshaw focuses on errors that could explain unstable leader behavior. When grep returns no matching Raft message, the script reports that no raft errors were found.

- After all checks complete, the script prints a finished status message.
- Pelshaw verifies etcd health and confirms whether every member is healthy.
- Leader and follower roles are checked together with latency.
- The script reviews CPU and memory consumption for etcd pods.
- Host IO latency is included in the diagnostic pass.
- Ping results between nodes are collected for network visibility.
- Recent raft buffer errors are checked from logs.
- Run the saved script on the etcd node showing abnormal behavior.

- Execute ./etcd-diagnose.sh directly on the abnormal etcd node.
- Network faults CAN drive repeated etcd leader changes.
- Raft needs steady, low-latency communication across nodes.
- Jitter or packet loss CAN interrupt heartbeats and start re-elections.
- For network investigation, staff CAN involve @Rachel Jarvis.
- Weak disk IO performance CAN also lead to frequent leader switching.
- etcd is highly sensitive to disk write delay, especially WAL writes.
- Low IOPS or elevated latency CAN block commits and heartbeats.
- Disk stalls CAN create node timeouts that trigger leader election.
- A common sign of poor disk IO is apply entries took too long.
- Staff CAN contact @Kara Monroe to tune etcd cluster parameters.

## Appendix
- Keep etcd node-to-node network latency <10ms, with packet loss almost 0.
- Use a dedicated network or VLAN so etcd traffic stays separate from business traffic.
- Configure MTU properly to prevent packet fragmentation.
- Prefer SSD or NVMe storage for high IOPS and low latency.
- Ensure etcd disks are SSD, as official etcd guidance strongly requires SSD.
- Do not share the same disk with logs, databases, or other high-IO workloads.
- Operators CAN enable noatime to cut unnecessary disk writes.
