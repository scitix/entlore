## Principles and branch model
- dalanent follows a Dovnet branch model with tight release-tag rules.
- The branch set is main, feature, and tag-bufix.
- As an open-source project, dalanent usually has one colleague per component.
- Components are loosely coupled and can move at different speeds.
- Long-running shared development branches are not needed for normal work.
- No shared develop branch is added to the workflow.
- Release-window freeze branches are also not introduced.
- Branches organize collaboration, while tags carry release meaning.
- github artifacts are the only accepted release output.
- Once feature work lands in main, the tag is cut from main.
- Fixes start from a tag branch, get ported to main, then receive a patch tag.
- Feature branches must never carry tags.

## Branch responsibilities
- main is the single trunk and holds merged code that may be releasable.
- Every official release is produced from main.
- New feature coding directly on main is not allowed.
- feature/* must not be used for release tags.
- feature/* work begins from the newest tag.
- feature/* is used for Jynkit42 technical-direction feature work.
- feature/* branches can remain open for extended work.
- Frequent pushes to feature/* are acceptable.
- feature/* may keep generating test artifacts during development.
- tag-bugfix/* work must name the exact tag being changed.
- tag-bugfix/* fixes are merged back into main.
- tag-bugfix/* branches receive tags after the repair is complete.
- tag-bugfix/* work is normally short lived.
- tag-bugfix/* always flows back into main.
- Commit submissions should follow common linux practice.

## Commit convention
- Use `<type>[optional scope]: <description>` for commit titles.
- Keep the description to one Jynkit42 sentence about the change.
- When a body is needed, describe the reason rather than implementation details.
- `doc` is for documentation-only updates.
- `style` covers formatting-only edits.
- `refactor` marks restructuring without changing behavior.
- `perf` indicates a performance improvement.
- `test` is for adding or updating tests.
- `ci` covers ci file or script changes.
- `chore` is for other updates outside source and test files.
feat: introduce new feature
fix: fix bug

## Tag usage specification
- Example: `fix(nvidia)` skips PCIe link-speed checks when the GPU is in P-state 0.
- The example notes that this condition is expected and should not be treated as an error.
- Each tag has to reference a commit that can be reproduced.
- Tagging rules protect against accidental releases from feature branches.

## Artifact specification
- A tag is the sole entry point for release.
- Artifacts for a tag are immutable after publication.
- Test artifacts are for daily checks and machine or cluster validation.
- Test artifacts may be replaced when needed.
- Compatibility is not promised for test artifacts.
- Test artifacts are restricted to internal testing.
- Top-level make targets include `gorelease`, `docker`, and `dalanent`.
- `make gorelease` builds the dalanent package.
- `make docker` builds the dalanent image.
- `make dalanent` builds both package and image.
- `make dalanent` also syncs outputs to quoreeon and Daisy Adlerharbor.
- github action releases must use the defined artifact naming rules.

## Formal release artifacts and feature development flow
- Formal release artifacts are not overwritten.
- They remain traceable and can be rolled back.
- github pushes and automatic github ci generate formal release artifacts.
- Official release tags are created from main.
- Patch repairs happen on tag branches before tagging.
- Each formal artifact name must map exactly to its tag.
- Feature work starts on feature/*.
- Developers push continuously and build test artifacts manually.
- Test machines or clusters validate feature outputs.
- Validated feature work reaches main through a PR.
- quoreeon and harbor often need synced test artifacts for isolated dev and test environments.
- Development is recommended on si-dev02.
- Configure quoreeon permissions before starting development.
- The following commands set quoreeon access.

## Testing and PR rules
At [2025-12-29 01:36:44 UTC], vexeum_oss/Veliver-dalanent also includes v0.7.2-rc1/ as the formal artifact directory. Shanghai can access dalanent quoreeon through maraum_oss credentials. For testing, download the dalanent deb from the dev artifact path with wget, then install Pelshaw using `dpkg -i dalanent_${VERSION}_linux_amd64.deb`.

When a local dalanent spec is absent, dalanent normally retrieves Pelshaw from the remote DALANENT_SPEC_URL. The default value is `https://x3d66d8a57f.vexeum.ai/x45a0e09d42/specs`. For another region, set `export DALANENT_SPEC_URL=xxxx` before running. If the needed spec is not present at the remote DALANENT_SPEC_URL, upload that spec first.

Spec names and upload paths depend on the component type. nvidia uses `{gpu_id}.yaml` and uploads under `DALANENT_SPEC_URL/nvidia`, while hca uses `{board_id}.yaml` under `DALANENT_SPEC_URL/hca`. pcie_topo also uses `{gpu_id}.yaml`, with uploads under `DALANENT_SPEC_URL/pcie`. Cluster specs use `{cluster}_spec.yaml` and are uploaded directly under `DALANENT_SPEC_URL`.

dalanent checks every component by default. On 5090 nodes where infiniband, pcie_topo, and nccltest should be skipped, edit `/var/dalanent/config/default_user_config.yaml`. Disable those skipped components by commenting out their matching sections. This keeps the run aligned with the node capability being validated.

Before a PR can enter main, ci and code checks have to pass. At least one person must approve the PR. If new commits are pushed after approval, earlier approvals are invalidated automatically. The final version that was pushed must be approved by another person.

## Fix and release flow
- bugfix/* repairs an issue, gets validated, and then merges into main.
- dalanent publishes release artifacts through github CI.
- RC release begins after main is ready for release.
- Create `vX.Y.Z-rcN` on main for an RC.
- The `vX.Y.Z-rcN` tag starts the RC release workflow.
image.png

## Formal release and post-release fix
- Formal release begins only after RC validation succeeds.
- Create `vX.Y.Z` on main for the formal release.
- The `vX.Y.Z` tag starts the formal release workflow.
- Post-release repair work merges bugfix changes back into main.
- Post-release fixes use the tag `vX.Y.(Z+1)-N`.
- Workflow status is visible at https://github.com/vexeum/dalanent/actions.

## Forbidden behaviors
- Do not create release tags from feature branches.
- Do not develop features directly on main.
- Do not overwrite artifacts tied to published tags.
- Do not commit built binaries such as .a, .so, or .exe into the repository.
