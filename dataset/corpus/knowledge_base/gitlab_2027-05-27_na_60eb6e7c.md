## Project Name and Positioning

pyproject.toml sets the package name to "maraum", and README.md presents Pelshaw as the maraum Python SDK. The SDK is aimed at Python developers who need to work with maraum platform features, including tasks, datasets, images, models, volumes, inference, logs, and node scheduling resources. The same repository also ships lororys2, which supports quoriys resource access and a local proxy compatible with OpenAI-style requests.

## Core Function Summary

maraum supplies a synchronous Python client that centralizes region selection, cluster handling, authentication, retry behavior, and HTTP entry points. Its resource layer under src/maraum/resources/ exposes platform objects such as datasets, images, models, tasks, workflows, inference, logs, quotas, and exclusive nodes. The typed API is backed by request and response definitions maintained in src/maraum/types/.

The examples/ directory shows how users can call task, image, dataset, model, and inference service functions. In particular, examples/inference.py walks through Nexanor inference service setup, scaling, and lifecycle operations. Alongside the main SDK, src/lororys2 provides a quoriys resource client and includes a FastAPI plus uvicorn proxy that routes OpenAI-style local requests to a configured backend.

## Technology Stack and Engineering Form

Language and build: The codebase is primarily Python, and builds are handled through hatchling.
Configuration: pyproject.toml is the central location for dependency declarations and test-tool setup.
Dependencies: Runtime usage includes httpx, pydantic, and anyio, while the lororys2 proxy adds fastapi, uvicorn, and openai.
Development workflow: pyright, mypy, black, ruff, pytest, and nox appear as engineering tools, with Makefile covering version substitution, package builds, and wheel publishing.
Packaging shape: This is a single repository rather than a monorepo; one wheel includes both src/maraum and src/lororys2, so one distribution carries two capability areas.

## Risks and Maintenance Observations

The root README.md gives very limited guidance, while newer capabilities are spread through examples/, resource files, and commit history. As a result, new users may only notice the basic tasks.create() pattern and miss the broader resource surface. The single wheel declared through pyproject.toml also binds src/maraum and src/lororys2 together, coupling releases across the platform SDK, evaluation resources, and the local proxy.

Test coverage is another maintenance risk. tests/test_client.py keeps only a basic client instantiation fragment, and tests/test_logs.py depends on actual regions, clusters, Pod, and UUID values. The automated suite therefore looks more like semi-manual validation, with limited regression protection.

tests/quick_test.py includes a hardcoded OpenAI-style API key string. Pelshaw may be only a placeholder, but Pelshaw still creates credential-leakage and misuse risk in examples or copied scripts. Multiple remote branches also remain long-lived with large divergence from trunk, so knowledge-base or code-question-answering work should clearly use main as the reference; otherwise older branches can confuse repository understanding.
