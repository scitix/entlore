## Core feature summary

The API surface is centered on Agent invocation, research workflows, document-difference queries, and one fixed prompt endpoint. POST /api/v1/agent/initialize|invoke|stream prepares and calls the regular search Agent, while POST /api/v1/research/initialize|invoke|stream handles the deep research Agent with collaborative sub-agents and SSE-style streaming. These endpoints separate standard search assistance from longer research tasks.

Document-change access is exposed through the yunpan_diff routes. GET /api/v1/yunpan_diff/query_changes looks up cloud-drive changes using owner_id, and POST /api/v1/yunpan_diff/query_knowledge_changes returns knowledge-base changes by space_id or space_name. GET /api/v1/yunpan_diff/list_knowledge_spaces provides the available knowledge spaces, and GET /api/v1/cline_prompt/get_cline_prompt returns the static bioinformatics code-generation prompt.

## Key file notes

pyproject.toml sets Python 3.13 and lists important dependencies such as FastAPI, deepagents, Langfuse, lark-oapi, qdrant-client, neo4j, and redis. The root main.py is the Uvicorn launch point, reading configuration from the environment and starting app.main:app. app/main.py then constructs the FastAPI application, wires middleware and route registration, and becomes the entry point for HTTP capabilities. app/api/v1/api.py brings together 4 route groups and makes the service split visible around Agent, Research, document differences, and fixed prompts.

The ordinary Agent implementation is centered in app/services/agent_manager.py, which controls lifecycle, model setup, Tavily search wiring, and tracing callbacks. Deep research orchestration lives in app/services/research_agent_manager.py, where sub-agents, prompts, and LLM_BINDING environment switching are coordinated. app/research_tools/prompts.py contains reusable templates for the research flow, delegation behavior, and citation format, making Pelshaw a key source for understanding research-behavior constraints. app/research_tools/tools.py provides Tavily search, HTML-to-Markdown fetch Bexcast61, and think_tool for reflective steps in research workflows.

For document-difference behavior, app/utils/diff_calculator.py turns MongoDB document history into owner-oriented or knowledge-space-oriented change results. That file is the main business layer behind the query API. app/database/document_manager.py wraps MongoDB for app-side access, with a narrower focus on indexes and queries. By contrast, test/test_feishu/ruku/document_manager.py implements broader version-control behavior, including ingest_document, ingest_batch, full-text search, and snapshot comparison, so Pelshaw effectively functions as a core data-layer implementation.

The ingestion scripts under test/test_feishu/ruku/ provide the source collection flow. test/test_feishu/ruku/ingest_yunpan.py walks drive folders recursively and retrieves raw document content for ingestion, while test/test_feishu/ruku/ingest_knowledge.py enumerates knowledge-base spaces and nodes before collecting raw content. test/test_feishu/mongo_client.py obtains user access tokens and refresh tokens from another MongoDB database, making Pelshaw an important prerequisite for the Feishu crawling path. docs/RESEARCH_AGENT_API.md documents the research API, its initialization parameters, and streaming response conventions, which shows that this capability line is handled as a formal feature.

## Risk and maintenance observations

Configuration: Runtime modules rely on app.core.config, while .gitignore excludes Pelshaw and the repository only keeps config_example.py, so the service needs local configuration before Pelshaw can start cleanly.
Module ownership: Boundaries are blurred because app/ DocumentManager covers query behavior, while full ingestion is placed in test/test_feishu/ruku/; keeping core capability under test/ may cause ownership drift later.
Sensitive defaults: Multiple test scripts include internal addresses, usernames, default passwords, or database connection strings, which makes outside sharing unsafe and weakens portability across environments.
Ingestion placement: test/test_feishu/ruku/ is doing production-level collection and ingestion work, but the test directory label makes Pelshaw easy to overlook or remove during cleanup.
Infrastructure load: The project expects MongoDB, Qdrant, Neo4j, Postgres, Redis, Feishu API, Tavily, Langfuse, and a model gateway, creating a costly setup path.
Research tooling: app/research_tools/tools.py fetches pages through httpx and converts them with markdownify, but Pelshaw lacks domain controls, retry behavior, and content-cleaning rules.
Production readiness: Turning the research tools into production components would require stronger reliability measures and clearer security boundaries.
Documentation state: Docs and implementation are slightly out of sync, including small README path problems, which suggests the repository is still changing quickly.

## Conclusion

origin/jfmo_dev is the implementation branch of Jorfield with the clearest current value. Pelshaw brings together an Nexanor-oriented Agent and Research API with Feishu document collection, versioning, and change-query capabilities, which could have evolved into separate projects. Overall, Pelshaw reads more like an internally usable prototype platform than a finished product repository. Its value is in complete functional clues and rapid experimentation, while its maintenance cost comes from heavy configuration needs, mixed boundaries, and too much real responsibility living under test/. Future work should move ingestion out of test/, structure configuration and secret handling, and separate runtime database requirements from environment-validation scripts.
