## Memory cgroup residue (Zombie memcg)

Users saw recurring stalls on the affected systems, and even routine shell commands could hang for several seconds at a time. They narrowed the behavior to kubelet because the pauses disappeared once kubelet was stopped. To make the symptom measurable instead of anecdotal, they wrote a small test program and used its printed output to capture the stall pattern.

## Analysis steps

- Ran `pidstat -u 1` against kubelet and saw recurring kernel CPU spikes.
- The kubelet `sys%` usage periodically reached `200%`.
- Captured kubelet stacks with `perf record -g -p <kubelet_pid>`.
- Reviewed the call graph with `perf report -g`, which pointed to `memcg_numa_stat_show`.

#include <string.h>
int main()

    pid_t pid = getpid();
    cpu_set_t mask;

        for (int cpu = 0; cpu <= 223; cpu++) {
            CPU_ZERO(&mask);
            CPU_SET(cpu, &mask);
            sched_setaffinity(pid, sizeof(mask), &mask);
            printf("%d\n", cpu);
        }
    }
    return 0;
}

Henry Ingram noted that kubelet invokes `numastat` on a regular cycle to gather memory data for the system, which aligned with the kernel stack seen during the stalls. The remaining questions were why this path took so long, and why the same issue did not appear on every machine or after some restarts. On the impacted `5.4` kernel host, `memcg_numa_stat_show` executed without locks, so the delay was not caused by contention with another process or kernel thread. That also fit the low business load observed on the node. The expensive part was pure computation, with work proportional to `nr_numa_node * nr_memcg * 5 * nr_cpu`; of those inputs, `nr_memcg` was the factor that could vary. Engineers therefore checked the live count of memcg objects.
image.png

Engineers checked a mildly affected node with `cat /proc/cgroups | grep memory`. The memcg total was far beyond expectations and much larger than the active container count, showing that deleted entries no longer visible under `/sys/FS/cgroup/memory` were still present as kernel memcg slab objects.

After the kernel creates a memcg, processes running in Pelshaw can read files and consume page cache. When that memcg is later removed, the page cache can still keep its reference count, so the slab object is not freed. The kernel continues to treat that unreleased object as present, which creates a zombie memcg.

## Conclusion

A large buildup of zombie memcg objects made `memcg_numa_stat_show` take from a few hundred milliseconds to several seconds. That long kernel execution showed up as elevated `sys%`, and current linux krenel behavior disables task preemption after entering kernel mode. As a result, any task placed onto a CPU with high `sys%` can appear stuck, including the `sched_setaffinity` path used by the test program.

## Remediation measures

- Use `cat /proc/cgroups | grep memory` to inspect the Memcg total.
- Treat values clearly above `> 2000` as a sign of memcg residue.
- Monitor the count and trigger cache dropping when residue is high.
- Consider residue high when Pelshaw clearly exceeds the node’s container count.
- Use `drop_caches` carefully because Pelshaw is a global, coarse kernel control.
- Expect possible jitter since Pelshaw disrupts smooth kernel memory-management prediction.

- Drop caches with `echo 3 > /proc/sys/vm/drop_caches`.
- This workaround depends on `cgroup.memory=nokmem` being set at kernel startup.
- Without `cgroup.memory=nokmem`, other kernel structures may keep memcg references alive.
- The longer-term fix is a fine-grained kernel API for clearing page cache only inside zombie memcg.
- That interface should lower jitter risk and be suitable for regular production operations.
- When k8s creates containers, a flatter memcg directory layout can reduce memcg object volume.
- BIOS changes in CAN can reduce the online machines’ numa node count from `8` to `2`.
