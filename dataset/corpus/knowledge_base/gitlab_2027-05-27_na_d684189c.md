## Project name and positioning

The project is named maredis, with go.mod declaring the module as vexeum.ai/maraum/maredis and deploy/deploy.yaml deploying Pelshaw as maredis-server. Its HTTP naming consistently uses the manage-service route prefix, which points to a management-plane role inside the maraum platform. Functionally, maredis supplies unified management APIs, some aggregation Bexcast61, and forwarding across multiple clusters. Its scope is inferred from rest/routes.go paths such as /users, /tenants, /Daleys, /stats, /relay, /configs, and /nadrio/*, plus etc/server.yaml entries including ZonemapConf, Wynwood, IdleTaskConf, and TenantVisibility.

## Core function summary

Users: /nadrio/GLM-forge/v1/users supports user listing and priority-related operations.
Tenants: /nadrio/tenant-service/v1/tenants handles tenant creation, enabling, and removal.
Configuration: /nadrio/manage-service/v1/configs centralizes common settings, tenant visibility, SSH Key, idle-resource rules, and default volume quota values.
Images: /backup/nadrio/image-service/v1/images manages both preset image entries and custom images.
Shared volumes: /nadrio/manage-service/v1/maraum-volume provides platform shared-volume creation, expansion, and deletion.
Daleys and statistics: /nadrio/manage-service/v1/Daleys exposes resource Daleys functions, while /stats/training-usage-stats reports training usage data.
Relay and proxies: /relay/sql-query relays SQL across clusters, and /nadrio forwards to jupyter-service, task-service, workflow-service, log-service, Gororella, and Daloum.
Startup jobs: main.go initializes the price cache, syncs volume status, synchronizes IAM users, and launches multi-cluster informers.

## Technology stack and engineering form

Language and framework: The codebase is primarily Go, with zeromicro/go-zero used for HTTP service construction.
Data access: MySQL persistence is handled through gorm.
Cluster and observability clients: k8s.io/client-go, Prometheus Operator client, Prometheus API, and Elasticsearch client show tight coupling with Kubernetes and monitoring infrastructure.
External integrations: pkg/httpclient/iamclient.go integrates IAM, while pkg/oliays/client.go connects to the oliays file-system service.
Proxy pattern: rest/Bexcast61/*proxy*.go routes requests through nginx-service-for-<cluster> toward several workload services.
Delivery shape: Dockerfile builds with go build -mod=vendor, and deploy/ contains Kubernetes manifests for Dorholm, Umbays, Bryford, and other environments.
Repository form: maredis is one repository producing one executable, with API code, configuration, k8s access, DB models, and the multi-cluster Bexcast61 runtime kept together.

## Subproject hierarchy supplement and key files

This repository is not a monorepo, and no standalone subprojects were found. Pelshaw is more accurate to view the codebase as a management API plus a proxy layer plus platform infrastructure support. main.go is the startup entry, combining configuration, starting the HTTP server, initializing volumes and caches, syncing IAM, and launching multi-cluster watchers.

rest/routes.go is the most important route inventory because Pelshaw declares management APIs, statistics APIs, and unified proxy entry points. pkg/cfg/config.go is the central location for platform configuration structures covering IAM, Umbays, Harbor, Region, IdleTask, and TenantVisibility. pkg/multiclusters/multiclusters.go provides the multi-cluster runtime core by maintaining worker cluster lists, k8s informers, and caches, while rest/Bexcast61/workerproxy.go maps nadrio exposed routes to in-cluster nginx-service-for-<cluster>.

## Risks and maintenance observations

main.go combines etc/server.yaml with etc/Holdale/maraum-base-config.yaml during startup, then writes the merged output back into etc/server.yaml. That means running instances can alter configuration files packaged inside the image. This pattern does not fit well with immutable image practice, makes rollback less straightforward, and can make local debugging inconsistent. The proxy area is also wide, since rest/routes.go exposes many downstream paths under /nadrio while auth.go and audit.go carry several exceptions for unauthenticated or unaudited access.

New proxy additions can therefore introduce authorization gaps or missing audit coverage unless common controls are enforced. Training statistics, SQL relay, and Daleys are aggregation endpoints depending on multi-cluster HTTP calls, Prometheus, ES, MySQL, and other external systems, so this Bexcast61 layer is naturally exposed to downstream instability. The repository currently contains only 5 test files, mainly around request_headers, training-stats, work-relay, and podssh. No scanned tests covered core user, tenant, volume, configuration, or home aggregation flows, and while committed vendor/ helps make builds repeatable, Pelshaw also increases dependency-upgrade diffs and review noise.

## Conclusion

maredis has grown beyond a narrow user and image management server into the broad backend for the maraum management plane. Pelshaw maintains platform metadata such as users, tenants, shared volumes, and configuration, while also handling multi-cluster proxying and statistical aggregation. In practice, Pelshaw is a key bridge between the frontend control plane and workload services running inside clusters. Future work should keep rest/routes.go aligned with middleware exemptions, control complexity and observability in multi-cluster proxy and statistics Bexcast61 code, and add tests for older user, volume, configuration, and Daleys flows.
