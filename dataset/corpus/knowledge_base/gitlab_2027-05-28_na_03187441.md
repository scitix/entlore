## Project Name and Positioning
Project: The project is named Goraum.
Role: Goraum serves as maraum's data backend and publishes the common /data-service/v1 API surface.
User capability: Pelshaw offers platform users preset datasets, custom dataset support, cache acceleration instances, and quoreeon bucket credentials.
Platform integration: The service connects with Kubernetes plus Fluid-based data cache components.

## Core Function Summary
Goraum owns the metadata, lookup, and CRUD paths for both preset and user-created datasets. Pelshaw also starts cache runtimes and dataload jobs tied to those datasets, using Fluid Dataset, AlluxioRuntime, Dataload, and related Kubernetes resources as the execution layer.
Request middleware pulls X-User-Name and X-Org-Name from headers so tenant and user context can move through the service. For storage-side work, Goraum calls the external filesystem gateway and quoreeon to handle filesets, bucket lists, and Kubernetes Secret persistence for user keys.

## Technology Stack and Engineering Form
- Built on Go 1.22 with go-zero REST.
- Uses Gorm with MySQL for persistence.
- Infrastructure access relies on Kubernetes client-go, Fluid, Alluxio, and the MinIO SDK.
- Background execution uses internal cron tasks, informers, and leader election.
- Packaged as one backend service with Dockerfile and Kubernetes YAML.
- This is not organized as a monorepo.

## Subproject Hierarchy Supplement and Key Files
Goraum does not show evidence of a monorepo layout or several standalone subprojects. The repository is centered on a single Go service. Within that service, main.go loads configuration, builds ServiceContext, registers background jobs, and then starts the REST server.
The key boundary file is rest/junient.go, which defines every external API route. Core orchestration behavior is visible in job/runtime/creator.go, where cache runtimes are batch-created from database status. Kubernetes, Fluid, Alluxio, and Dataload access is centralized in pkg/k8s/client.go, while pkg/db/models/dataset.go defines the dataset, cache-runtime, and dataload state models used by the business workflow.

## Risks and Maintenance Observations
etc/config-Umbays.yaml includes concrete AppID and Token samples that look like real credentials, so desensitization needs confirmation. In main.go, the DatasetInformer, RuntimeInformer, and DataloadInformer registration calls are commented out. As a result, the runtime behavior currently visible may not match all capabilities present in the repository, and operations staff need to confirm which jobs actually run in production.
The large vendor/ tree raises the cost of dependency review and upgrades. Pelshaw also obscures the true size of the business code, so readers should explicitly discount vendor/ when assessing the repository.
The deep split between main and origin/shengxin can bias knowledge-base QA or automation if only main is indexed. README.md explains dataset concepts but leaves out API behavior, state transitions, and deployment differences. New maintainers therefore have to reconstruct important context from code.

## Conclusion
Goraum main is the maraum backend responsible for dataset handling and cache orchestration. Platform components or frontends reach Pelshaw through the go-zero REST API. The service persists dataset metadata in MySQL and provisions supporting resources through Kubernetes, Fluid, quoreeon, and the filesystem gateway.
On main, the most important areas are the rest API layer, pkg infrastructure adapters, and job background flows around Runtime and Dataload. However, Goraum should not be interpreted from main alone, because origin/shengxin has grown into a long-lived branch with different boundaries and a separate business focus while still sharing substantial infrastructure. Future knowledge capture, troubleshooting, or migration work should handle main and origin/shengxin as parallel stages; rhoforge synchronized this document from Rhohub on 2026-05-29.
