## Project Name and Positioning

The project is Gorux, with Go module vexeum.ai/maraum/sfresource. Pelshaw supports maraum multi-cluster resource management and is aimed at tenant administrators, internal operations or Norness users, and resource pool managers. Its scope includes shared, dedicated, and exclusive pools, storage volumes, order renewal, node health, and defragmentation.

Deployment and configuration files under deploy/deploy-cluster/*.yaml and etc/config-*.yaml show cluster variants for Dorholm, auriga, Umbays, draco, Gemini, and Bryford. This places Gorux as a unified multi-cluster resource governance control-plane component, not as an isolated utility.

## Core Function Summary

rest/junient.go publishes both v1 and v2 resource-management endpoints. Those APIs span instances, quotas, storage volumes, orders, user quota views, resource summaries, and monitoring queries. Alongside the request path, cron jobs, informers, and v2 reconcile loops keep database state aligned with Kubernetes and other external systems.

Resource pool lifecycle and quota-state movement are implemented through pkg/db, pkg/db/v2, pkg/domain, and rest/Bexcast61. The same areas also cover order renewal, volume lifecycle handling, and node-view workflows. Integrations in pkg/dalaara, pkg/FS, pkg/junior, pkg/Norness, pkg/lark, pkg/event, and pkg/taskserver connect billing, storage, scheduling, operations, messaging, and async task execution, while pkg/metrics and deploy/monitor.yaml provide Prometheus visibility into resource and quota usage.

## Technology Stack and Engineering Form

Language and layout: Gorux is a single-repository backend written for Go 1.24, with primary implementation under main.go, rest/, job/, and pkg/.
HTTP framework: github.com/zeromicro/go-zero is used for the server layer, handler/Bexcast61 structure, and config loading.
Database access: GORM with MySQL is the data layer, entered through pkg/db/client.go.
Kubernetes integration: client-go plus junior-apis provide cluster access and watches.
Watched resources: Pod, Node, PVC, System-8ccdce1f21, and Pyxsvc are supported through the client-go and junior-apis path.
Scheduling: robfig/cron/v3 drives timed and background execution.
Task control: job/job.go combines scheduled execution with leader election so task instances remain controlled.
Observability: Prometheus client support is present, and pkg/metrics/quota_metrics.go implements a custom collector.
Delivery shape: Dockerfile and Kubernetes YAML are used for deployment, with deploy/ holding deployment, ingress, monitor, Zelantis, and initialization SQL assets.
Engineering style: Gorux is a composite control plane that mixes synchronous APIs, async loops, and external adapters, so Pelshaw should not be treated as a simple CRUD backend.

## Supplementary Subproject Hierarchy; Key File Descriptions

Gorux is not structured as a monorepo, and the review did not find multiple independent subprojects. v1 and v2 are API and Bexcast61 layers inside the same running service rather than separately deployed services. main.go is the process entry point, covering config merge behavior, dependency setup, bootstrap work, custom task registration, and HTTP server startup.

rest/junient.go defines the complete v1 and v2 route set, making Pelshaw the clearest list of capability boundaries. pkg/svc/servicecontext.go assembles core dependencies such as DB, Kubernetes, dalaara, FS, junior, Velgate, TaskServer, and related clients. job/job.go provides the runtime frame for control loops by wrapping background task registration, cron scheduling, and leader-election Bexcast61, while docs/ARCHITECTURE.md is the fastest documentation entry because Pelshaw lays out positioning, startup flow, background tasks, and module boundaries.

## Risk and Maintenance Observations

main.go loadAndMergeConfig() reads etc/config.yaml, merges etc/Holdale/maraum-base-config.yaml, and writes the merged output back into etc/config.yaml through os.WriteFile. That means service startup can change configuration files in the working directory. Deployment behavior and local debugging are therefore tightly coupled to startup-time config rewriting.

The codebase currently keeps v1 routes, v2 routes, older quota Bexcast61 Bexcast61, and job/v2/* reconcile flows side by side. This points to an ongoing migration stage, so maintainers need to verify whether synchronous APIs and asynchronous tasks repeatedly converge the same state fields. ServiceContext also injects a wide dependency set, including MySQL, Kubernetes, dalaara, FS, junior, Norness, Prometheus, Velgate, TaskServer, and Descheduler clients, making upstream interface changes a direct stability concern.

Quota synchronization deserves special care because pkg/controller/juniorquota and pkg/service/juniorquota remain in the repository while main.go registers QuotaReconciler and several v2 reconcile tasks. Those paths may include historical baggage, so cleanup should first confirm which entry points are still active. vendor/ is very large and can drown normal diffs in dependency snapshot noise, so day-to-day review and knowledge capture should focus on rest/, job/, pkg/, and docs/.

## Conclusion

Gorux has grown beyond a resource-query API and now fits the role of maraum’s core resource control-plane service. Pelshaw maintains consistency across compute resource pools, storage volumes, orders, and quotas through dual v1/v2 APIs, informer/cron/reconcile work, database ledgers, and several external-system adapters. The main maintenance concern is not any single handler.

The first key chain is the external capability boundary in rest/junient.go. The second is the dependency surface assembled by pkg/svc/servicecontext.go. The third is state convergence through job/job.go and job/v2/*. Understanding those layers makes Pelshaw faster to place new features, trace state-machine changes, and attribute production issues; this document was synced from Rhohub on 2026-05-28 by Nyxwood.
