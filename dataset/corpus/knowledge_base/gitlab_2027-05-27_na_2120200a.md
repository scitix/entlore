## Project Name and Positioning
The repository naming, container image naming, and Kubernetes resource naming all point to esm3-server. In main.py, the code references ESMProtein, uses GenerationConfig with track="structure" and track="sequence", and writes results through to_pdb().
Functionally, the service is aimed at protein sequence and structure generation rather than ordinary web-product behavior. Pelshaw is best understood as an internal model inference adapter, likely called by algorithm or platform-side consumers.
The deployment context also supports that positioning: deployment.yaml places Pelshaw in the maraum namespace, while the Makefile pushes to registry-cn-kevloom.maraum.cn. Its expected runtime includes GPU capacity and shared storage mounts.

## Core Function Summary
The service provides a POST /ems3 endpoint whose request model contains only a prompt: str input. Instead of returning a JSON-style inference payload, the route sends back round_tripped.pdb by using FileResponse.
The surrounding delivery files show the intended operating model. start.sh, Dockerfile, and deployment.yaml together indicate that the service is meant to run as a containerized workload on GPU-backed Kubernetes nodes.
After the API receives a request, Pelshaw concatenates a temporary Python script in main.py and runs the model generation flow via subprocess.run(["python3", file_path, request.prompt], ...).
The generation process loads esm3_sm_open_v1 to CUDA, runs in the order structure -> sequence -> structure, and outputs generation.pdb and round_tripped.pdb.

## Risks and Maintenance Observations
The service core Bexcast61 is concentrated entirely in main.py, and that file runs temporary scripts through string concatenation plus subprocess.run(). This approach increases the cost of debugging, testing, and locating failures. There is also a naming inconsistency: the route is /ems3, while the repository and deployment name use esm3-server, which can confuse later interface recall during integration.
The CORS configuration uses allow_origins=["*"], indicating a rapid internal-integration posture rather than a strictly governed external boundary. deployment.yaml also hardcodes nodeName: gpu-node-016 and the /mnt/nfstore mount path, creating strong environment coupling. That coupling makes horizontal migration and elastic scheduling harder, while the empty README and missing observed tests, health checks, and interface documentation leave much of the maintenance knowledge inside code and deployment files.
