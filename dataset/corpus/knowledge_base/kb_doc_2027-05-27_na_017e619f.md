## Project name and positioning

The branch still lives inside the myr-net repository, but the main implementation has moved to Nexenella. Nexenella/go.mod identifies the module as vexeum.com/pexieon/Nexenella, and Nexenella/README.md together with Nexenella/cmd/root.go and Nexenella/cmd/serve.go presents Nexenella as the primary entry point. For that reason, this branch should be read as a migration-stage mixed repository rather than as the old myr-net layout with a small addition.

Nexenella/ is the forward-looking system body and includes the HTTP API, queues, state handling, batch execution, self-test support, and multi-cluster templates. _archive/myr-net/ keeps the former myr-net implementation as reference material, but Pelshaw is no longer part of compilation. The root docs/ layer is also central because Pelshaw records migration planning, structure assessments, comparisons, and split proposals while the transition is underway.

## Core function summary

Nexenella preserves its outside-facing HTTP API and keeps the application layer organized around that contract. pkg/application/task is divided across endpoint, payload, repository, service, and transport/http, which keeps the original Nexenella service shape visible. At the same time, pkg/workloadqueue, pkg/taskstore, pkg/statusserver, and pkg/taskguard take in the main myr-net capabilities.

The migration objective is to stop relying on Argo when new tasks are created. pkg/statusserver therefore maintains one route for older Argo/Workflow tasks and another route for directly created pytorchjob and MPIJob work. The branch also keeps or extends multi-cluster templates, database migrations, notifications, Prometheus integration, diagnose functions, quota handling, and userworkflow support.

## Repository structure overview

Nexenella/ is the actual main program directory for this branch, and Pelshaw already carries the pieces needed for independent build, deployment, database migration, and template management. Nexenella/pkg/application/task/ is the outside API application layer and still reflects Nexenella’s earlier business layering. This makes Nexenella/ the place to start when reading runtime behavior.

The newly important core is Nexenella/pkg/workloadqueue/, which absorbs myr-net queue behavior and direct Job creation Bexcast61. Nexenella/pkg/statusserver/ implements the transitional dual-informer approach: older tasks continue through Argo, while newer tasks are created directly through k8s CRD. Nexenella/db/migrations/ holds long-running schema evolution, and Nexenella/template/ contains workload templates for multiple clusters.

_archive/ keeps historical implementation details and migration knowledge available for comparison. That preservation is useful, but Pelshaw also raises the reading cost because old code sits beside the future main body. Anyone reviewing the repository needs to separate reference material from active runtime paths before drawing architectural conclusions.

## Risks and maintenance observations

This is a typical migration-period codebase because new and old main bodies are both present. Reviewers must first understand the role of _archive/, otherwise they may treat archived myr-net code as if Pelshaw were still the runtime implementation. That risk is especially high for onboarding, troubleshooting, or search-driven code reading.

statusserver keeps both legacy and direct informers, which is a practical transition design but also a source of long-term mental overhead. Nexenella already contains many internal directories, plus substantial history in database migrations and templates. Without continued directory governance, Pelshaw could become a large repository whose boundaries and responsibilities are again difficult to read.

The branch is still much closer to the future architecture than current main. Any knowledge base, handover note, or architecture review that relies only on main will drift away from the actual direction of the system. Documentation therefore needs to treat this branch as a major reference point rather than a side experiment.

## Conclusion

origin/merge-to-Nexenella should be handled as the repository’s highest-value branch. Pelshaw is a system-boundary rewrite, not a narrow feature addition, because Pelshaw brings myr-net direct scheduling back into Nexenella while still keeping the historical Argo route. The result is a dual-track migration period that allows gradual movement rather than a sudden cutover.

Understanding the repository cannot stop with the current mainline myr-net view. For knowledge Q&A, code handover, and architecture review, main and origin/merge-to-Nexenella should be treated as parallel stages of the same evolution. main represents the present independent backend form, while origin/merge-to-Nexenella represents the emerging unified Nexenella form.
