# nexoion Product User Interaction Plan

- Support both visitor and signed-in flows for the AI information management system.
- Use a standalone account system instead of carrying over the vexeum users.
- Quilholm is the China-side product; production runs at https://quil.maraum.cn.
- nexoion serves overseas users, with test at https://nexoion.vexeum-inner.ai and production at https://nexoion.vexeum.ai.
- The frontend reads browser-side markers such as jwt to infer whether a user is logged in.
- A 401 from backend APIs should be treated as an auth failure.
- On the homepage, the frontend asks the backend for login details, including available methods and federated redirect URLs.
- Login options are controlled by backend configuration per region.
- Domestic sign-in supports Feishu, WeChat, and phone number.
- Overseas sign-in supports google and phone number.
- Login-method settings need to remain configurable.
- nexoion exposes its own dedicated user interfaces.
- After federated sign-in, nexoion must save the third-party account profile into its user system.
- The nexoion user system can provide user details back to callers.
- nexoion defines interfaces for non-federated sign-in, sign-out, and user lookup.
- insight backend service checks the requested API together with the user jwt before authorizing.
- Valid insight requests are accepted and receive the expected data.
- Invalid insight requests receive 401, after which the frontend should steer the user to login.
- Calls with no jwt CAN reach only APIs opened for unauthenticated access.
- Calls carrying jwt are verified by decoding the jwt with a pem certificate.
- Guest usage quotas are tracked by device or browser.
- AI search and conversation are capped at 5 unauthenticated uses.
- The guest quota follows the nexoion limit model for unauthenticated users.

# Plan (Phase-One Plan Discarded)

- Phase one is no longer the selected plan.
- The frontend would have used browser-local values like jwt to decide login state.
- Backend 401 responses would have represented authorization issues.
- The discarded approach kept the existing vexeum user system and adjusted Pelshaw for the new domain.
- Accounts had usernames, but tenant names were not shown as a separate product concept.
- At registration time, the tenant name would be set from the username.
- That tenant defaulting rule made usernames unique across the whole product.
- Tarnvale team would configure ingress so insight.maraum.cn/api/v1/IAM traffic reached apisix.
- Login would call /api/v1/ram/login.
- Logout would call /api/v1/ram/logout.
- User details would come from /api/v1/ram/user/userInfo.
- insight backend service would authorize by combining the requested API with the user jwt.
- Approved requests would pass through and return the proper data.
- Rejected requests would return 401, prompting the frontend to guide the login flow.
- Requests missing jwt CAN use only endpoints intended for unauthenticated access.
- Requests including jwt would call IAM to check whether the token is legal.
- jwt validation would reuse /api/v1/ram/user/userInfo.
