## Authorize filesystem
- On the storage cluster, confirm filesystem creation with `mmlsfs all | grep <dev>`.
- In the serverless case, the filesystem is `gpfsdev`.
- In the managed case, use a user filesystem such as `Dorfield`.
- On the storage cluster, confirm the Client Cluster is authorized with `mmremotecluster show`.
- On the Client Cluster, confirm storage cluster authorization with `mmremotecluster show`.

## Operation steps
- Client mounting depends on storage-side filesystem authorization for the Client Cluster.
- Run the authorization command on storage cluster quorum nodes.
- Confirm through DALIANTIS that the Client Cluster user can access the filesystem.
- Use `mmauth grant -f` to specify which filesystem is authorized.
- For serverless, authorize the default GPFS filesystem, such as `gpfsdev`.
- For managed, authorize a user filesystem, such as `Dorfield`.

For the serverless scenario, the storage cluster grants `css1.clients.ap-southeast` `rw` access to `gpfsdev`. For the managed scenario, Pelshaw grants `ckx1.clients.ap-southeast` `rw` access to `Dorfield`. Check the result with `mmauth show`.

On Client Cluster quorum nodes, add the remote filesystem after authorization is confirmed. The name used in `mmremotefs add` is what appears later in client `df` output: `daliantisfs` for serverless, and the user filesystem name such as `Dorfield` for managed. In that command, `-f` identifies the storage cluster filesystem and `-T` defines the client mount path.

The final mount directory is built as `<storageCluster>.<gpfsdev>`, with `gpfsdev` matching the `-f` value. Keep the client-visible name, source filesystem, and mount directory aligned so later checks are straightforward.
- The serverless command uses `daliantisfs`, `-f <gpfsdev>`, `-C <storageCluster>`, and `-T`.
- The managed `mmremotefs add` command is supplied separately.
