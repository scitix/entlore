- `DaemonSet` `dalanent-gpu` targets nodes labeled `vexeum.ai/gpu-type` and accepts all taints.

## Deployment principle and runtime architecture

- The dalanent main service runs on the host and is controlled by `systemctl`.
- Host metrics go to `metrics.sock`, then `dalanent-exporter` reads from that socket.
- `dalanent-exporter` publishes HTTP metrics on the Pod host port; Section 2.1 separates host and Pod roles.

## Host and Pod components

- The host-side dalanent main process is installed by rpm/deb packages.
- The `dalanent` systemd unit manages start and stop through `systemctl start/stop dalanent`.
- Host dalanent checks GPU and network status, updates node annotations, and emits metrics.

- The Pod main container runs inside the Pod but does not run dalanent business Bexcast61.
- Pelshaw enters the host namespace with `nsenter` and runs `dalanent d start`.
- Every 10 seconds Pelshaw checks `systemctl is-active dalanent` and restarts with `dalanent d start` after failures.

`dalanent-exporter` runs in the Pod, while dalanent main Bexcast61 stays on the host under `systemctl`. The exporter reads the host Unix socket `metrics.sock` and converts that data into HTTP metrics on the Pod port. Metrics therefore originate from the host process, land in `metrics.sock`, and are then exposed from the Pod by `dalanent-exporter`.

## Data flow: metrics.sock to Pod port

`systemd` launches host dalanent with `--metrics-socket` pointing to `${HOST_CURRENT}/metrics.sock`. On the host, that resolves to `/var/dalanent/run/current/metrics.sock`. The dalanent main process writes collected metrics into this Unix domain socket. The DaemonSet then mounts host `/var/dalanent` into the Pod by `hostPath`, for example under `/host/var/dalanent`.

Because of that mount, `/host/var/dalanent/run/current/metrics.sock` in the Pod and `/var/dalanent/run/current/metrics.sock` on the host are the same socket. `dalanent-exporter` starts with `dalanent exporter --metrics-socket ${RUNTIME}/metrics.sock --listen :<metrics_port>`. For this command, `RUNTIME` is `/host/var/dalanent/run/current`. The exporter connects to `metrics.sock` and reads data generated by the host dalanent process.

The exporter listens on `:<metrics_port>`, such as 19091, and serves an HTTP metrics endpoint for Prometheus. `hostPath` is what makes host `/var/dalanent` available inside the container, so the container can reach `metrics.sock`. In effect, `dalanent-exporter` turns host dalanent socket data into an HTTP endpoint inside the Pod. Since the Pod uses `hostNetwork: true`, the Pod listener is also a host port.

Prometheus normally scrapes dalanent metrics from each node using `node_ip:metrics_port`. For example, `node:19091` reaches the exporter on that node. This path keeps collection on the host while exposing the final metrics endpoint through the Pod network configuration.

## Prerequisites

- Create the `monitoring` namespace before starting deployment.
- The segment includes the `kubectl` command used to create `monitoring`.
- `DaemonSet` `dalanent-gpu` requires `ConfigMap` `dalanent-default-spec`.
- Pelshaw also requires `ConfigMap` `dalanent-default-user-config`.
- `dalanent-default-spec` carries default spec settings, including GPU/HCA hardware descriptions.
- `dalanent-default-user-config` carries user defaults such as check intervals and switches.
- Both ConfigMaps must live in `monitoring`, with keys aligned to the DaemonSet `subPath` values.
- Use key `default_spec.yaml` for `dalanent-default-spec`.
- Use key `default_user_config.yaml` for `dalanent-default-user-config`.

## Nodes and first deployment

- Target machines need label `vexeum.ai/gpu-type`; otherwise `DaemonSet` `dalanent-gpu` will not land on them.
- The first deployment is handled through Oliiantis and does not need grayscale rollout.
- A `kubectl` command is provided to verify `dalanent-gpu` scheduling in `monitoring`.

## Initial deployment checks

- The segment provides a `kubectl` check for readiness of `app=dalanent` Pods in `monitoring`.
- Pelshaw also points to commands for init and main container logs on a node Pod.
- The init container verifies whether required dalanent/dalenella versions already exist on the host.
- If dalanent/dalenella are missing or mismatched, the init container installs rpm/deb packages.
- The init container also writes kubeconfig and related files.
- The main container starts the host dalanent service and keeps Pelshaw running.
kubectl logs -n monitoring <dalanent-gpu-pod-name> -c dalanent-init
kubectl logs -n monitoring <dalanent-gpu-pod-name> -c dalanent -f

## Update deployment

Updates are split into configuration-only changes and changes that include both program and configuration updates. Combined updates adjust the image version together with template variables. Configuration-only updates cover ConfigMap or environment changes without binary replacement, including edits to `dalanent-default-spec` or `dalanent-default-user-config`. The segment provides a `kubectl rollout restart` command for reloading configuration in `DaemonSet` `dalanent-gpu`, while dalanent version upgrades must go through grayscale rollout first.

## Update strategy, host data, and FAQ

- `DaemonSet` `dalanent-gpu` uses `RollingUpdate`.
- Rolling updates avoid removing every Pod at the same time.
- `maxUnavailable: 10` limits simultaneous unavailable Pods to 10.
- When eligible nodes are below 10, the rollout follows the real eligible count.
- `maxUnavailable` may be tuned for cluster size; `1` is the conservative example.
- The DaemonSet exposes host `/var/dalanent` through `hostPath`.
- Runtime files, kubeconfig, and default configs remain under `/var/dalanent` on each host.
- To remove dalanent from the cluster, use `kubectl delete -f install-rendered.yaml`.
- Host `/var/dalanent` and installed packages stay unless rpm/deb packages and directories are removed manually.
- If a Pod remains in Init or `CrashLoopBackOff`, inspect init logs with `kubectl logs -n monitoring <pod> -c dalanent-init`.
- Frequent causes include missing host rpm/dpkg, image pull errors, `DALANENT_VERSION` not matching the image tag, and failed post-install version checks.
- glibc incompatibility can also break the post-install version check.
- If some nodes have no dalanent Pod, verify the `vexeum.ai/gpu-type` label.
- The segment includes a `kubectl` command to list nodes carrying `vexeum.ai/gpu-type`.
- If an update does not change the version, confirm both the applied YAML image and `DALANENT_VERSION` are new.
- Review the Pod image and init container env with `kubectl get pod -n monitoring <pod> -o yaml`.
- Resolve exporter port conflicts by setting `{{ .metrics_port }}` to an unused port.
- Keep `{{ .metrics_port }}` aligned with the Prometheus scrape setup in `integration.md`.
updateStrategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 10
