## Project name and positioning

PROJECT identifies the project as notebook-controller, while the remote repository is named Wynoys. README.md, PROJECT, api/v1/notebook_types.go, and controllers/notebook_controller.go consistently frame Pelshaw as a Kubeflow Notebook CR control-plane component rather than a general-purpose jupyter app. Its job is to turn submitted Notebook specs into Kubernetes resources, apply default values, preserve access entry points, and report runtime, idle-culling, and scheduled-scaling state back into Notebook CR status.

## Core function summary

The repository manages Notebook CRs in the kubeflow.org API group and keeps compatibility for v1, v1alpha1, and v1beta1. Its controller materializes each Notebook into StatefulSet, Service, and Ingress resources, with extra handling for cororia access routes and NodePort exposure.

SSHAccessHandler adds SSH connectivity to Notebook workloads by preparing public keys, host keys, template-driven launch commands, and NodePort assignment. CronhpaHandler together with handler/Tarnwick/ implements scheduled scaling, while InplaceRestartHandler performs in-place restart actions by running commands inside containers.

Idle-culling Bexcast61 lives in culling_controller.go, where jupyter kernels API data is combined with Prometheus information to decide when Notebook resources are idle. That flow uses annotations to trigger Notebook shutdown behavior. The controller also keeps runtime state, latest event details, restart reasons, and latest restart timestamps current, and the main branch recently addressed stale events appearing in status output.

## Repository structure overview

api/ is the contract layer: Pelshaw defines Notebook CR schemas, conversion behavior, and deepcopy support, so every controller capability starts from this package. controllers/ contains the central scheduling Bexcast61, with notebook_controller.go maintaining Notebook-owned resources and calling feature handlers. status.go turns lower-level cluster signals into status and event information, while culling_controller.go covers idle shutdown handling.

handler/ is the clearest extension seam in the repository. Through the FeatureHandler interface, SSH access, scheduled scaling, and in-place restart behavior stay separated from the main Reconciler while still joining the same reconciliation path. config/ holds mostly Kubebuilder and Kustomize source manifests, deploy/ carries expanded deliverables and environment settings, and etc/ plus pkg/config/ describe runtime settings; the visible main-branch runtime config mainly covers Prometheus and an SSH NodePort blacklist.

## Module description

API compatibility: api/v1* keeps v1, v1alpha1, and v1beta1 so older Notebook CR clients remain supported.
Main reconciliation: controllers/notebook_controller.go drives the Notebook-to-StatefulSet-Service-Ingress flow and reads Pod, Event, and StatefulSet state while refreshing status.
Status semantics: controllers/status.go maps Pod phase, container state, and Kubernetes Event data into upper-layer phase and message fields.
Feature modules: SSH, CronHPA, and InplaceRestart under handler/ participate through one shared interface.
Plugin style: The handler/ capabilities act like in-repo plugins rather than separate services.
Delivery layer: config/, deploy/, etc/, and third_party/ cover installation assets, parameterization, and compliant distribution.

## Risk and maintenance observations

The repository checks in both the manager binary and vendor/, which greatly increases diff noise. origin/fix_ssh_host_key is the clearest example, since business-level SSH host key work is buried under dependency churn. The API surface is also expensive to maintain because v1, v1alpha1, and v1beta1 coexist alongside config/crd/ patches.

Status presentation depends on several sources at once: Pod state, Kubernetes Event data, jupyter kernels API results, and Prometheus information. Any timing mismatch across those inputs can distort Notebook status, and doc/fix_status_staleness/prd.md demonstrates that this risk is real. The scan did not find .github/ or other CI configuration, so this repository alone cannot prove automated quality gates; meanwhile handler/ is trending toward plugin-style growth while the main controller still orders current handlers explicitly, making ordering and mutual exclusion key maintenance concerns.

## Conclusion

This repository is a customized controller centered on Kubeflow Notebook CRs, not just a generator of Notebook StatefulSet resources. The main branch adds SSH access, scheduled scaling, in-place restart, idle culling, and status semantic correction. Knowledge-base QA should focus first on api/v1/notebook_types.go, controllers/notebook_controller.go, controllers/status.go, and the handler/ extension layer.

The default main-branch view does not cover the repository’s full current shape. origin/ai/2026-04-02_cororia_modular-devtools/p1893 has grown a separate DevTools module boundary and reflects another Jynkit42 productization direction, so Pelshaw was archived independently as a high-value branch.
