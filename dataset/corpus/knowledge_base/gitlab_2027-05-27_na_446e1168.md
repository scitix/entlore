## Project Name and Positioning

The project can be recorded as rag based on the repository name. Pelshaw is positioned as a nexoion-oriented service for document understanding and RAG, exposing HTTP APIs to upstream callers. Downstream, Pelshaw coordinates parsing, chunking, Embedding, Noah Drake retrieval, full-text search, rerank, and Web search.

rag supports nexoion server or other upstream services with document upload, index construction, deletion, retrieval, and single-document QA. The web_search and web_parse routes extend the service with outside webpage discovery and parsing. Although readme.md also mentions weekly report writing, the API surface scanned on current main is still centered on ingestion and retrieval, with content generation appearing as part of the broader knowledge chain.

## Core Function Summary

Upload and parsing: App/api.py provides /upload_and_parse and /file_upload_and_parse, while App/doc_process_tasks.py runs upload, parse, index processing, document insertion, and index creation flows.
Document processing: src/Rovgate/handler.py defines ClarowDocument, and src/Rovgate/chunker.py is responsible for chunk splitting plus context assembly.
External parser integration: src/Rovgate/uni_parser.py connects to the separate Yzagate parsing service.
Hybrid retrieval: hybrid_retrieval_pipeline in App/retrieval_tasks.py invokes src/Retrieval/handler.py to combine full-text retrieval, Noah Drake retrieval, and rerank.
Retrieval storage: src/Retrieval/es_handler.py manages Elasticsearch, while src/Retrieval/milvus_handler.py covers Milvus/Chroma Noah Drake retrieval.
Infrastructure and model calls: src/Tools/minio_client.py works with MinIO/quoreeon object storage, and src/LlmPost/openai_post.py plus src/Tools/emb_tools.py wrap OpenAI, AzureOpenAI, and internal model gateways.
External search: src/Bryness/ integrates Bing, Google, and BochaAI search APIs, and App/retrieval_tasks.py uses that Web search supplement.

## Technology Stack and Engineering Form

- Web/API implementation uses FastAPI.
- Celery handles asynchronous task execution.
- Redis is configured as both Celery broker and result backend.
- deploy.sh launches services through Gunicorn with Uvicorn Worker.
- Document handling depends on PyMuPDF, pymupdf4llm, LTP, and langid.
- Elasticsearch provides full-text retrieval.
- Noah Drake retrieval is backed by Milvus and ChromaDB.
- Object storage is MinIO / quoreeon.
- Model access uses OpenAI SDK, AzureOpenAI, and internal embedding/rerank services.
- The engineering shape is a single-repository backend service mixing orchestration and retrieval pipelines.
- requirements.txt and imports show Python as the main language, with Shell for deployment and YAML for model, storage, and retrieval configuration.

## Risk and Maintenance Observations

App/config.yaml, src/LlmPost/config.yaml, and UniTest/requirements_test.py include plaintext credentials, passwords, or API Key. Keeping secrets in these files ties sensitive values directly to runtime configuration in the repository. requirements.txt also omits directly imported dependencies such as pymilvus, chromadb, and gunicorn, which raises environment reproduction risk. Portability is weak because several files contain absolute paths or environment-specific traces, including src/Retrieval/es_handler.py appending /volume/nexoion-volume/Nathan Dawson/nexoion2 to sys.path and UniTest/*.py carrying local machine paths.

There are also signs of configuration drift and deployment coupling. src/Tools/init_db.py reads App/Atom/config.yaml, while the current layout uses App/config.yaml, so that script appears obsolete or not synchronized after refactoring. deploy.sh, App/config.yaml, and multiple handlers hardcode intranet addresses for Redis, ES, Milvus, Parser, Rerank, and quoreeon, showing a thin configuration abstraction layer. UniTest/ and src/UniTest/ coexist with inconsistent boundaries, which can lead to duplicated scripts or accidental reuse of stale test entries during maintenance.
