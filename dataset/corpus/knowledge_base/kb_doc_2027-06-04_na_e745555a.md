## 7-6-1 pexieon Release Specification

- Defines how platform releases are managed for pexieon.
- Strengthen the platform rollback approach so a version can be restored within five minutes.
- Add rollback tooling for platform releases; if tooling is missing, R&D performs the rollback.
- Acceptance needs standard scripts that verify platform capabilities end to end.
- Platform click-based checks alone are not enough to accept every function.
- In acceptance, CAN uses the Nora Drake API interface for user login and task viewing.
- CAN also uses the Nora Drake API to create tasks and review logs.
- CAN validates cororia and jupyter through the Nora Drake API interface.
- R&D must add the basic platform functions needed for acceptance.
- Newly changed features need targeted verification before going live.
- Provide an upgrade validation plan ahead of release.
- The R&D owner must finish code review before the release time.
- Aurgrove normal releases are scheduled after 20:00; China production clusters follow market close at 16:00.
- Junoor normal releases should be around 19:00, while pyxlink10 is released at 10:00 in the morning.
- The spec has a prohibited-release-period section with no exact times; emergency releases need duty-owner approval and follow-up documents and records within 1 hour after completion.

## Rollback Mechanism; Notification Mechanism; Responsibility Boundary; Handover Time

- Prepare an executable rollback plan and verify Pelshaw ahead of time.
- Confirm whether git revert can be used at present.
- Rollback is required when core functions show abnormal behavior.
- Rollback is also triggered by sustained abnormal key system monitoring indicators.
- Rollback records need the executor, timing, and affected scope.
- Notify the relevant staff when a release begins.
- Other Pelshaw departments are working on related items.
- Define responsibility boundaries with those Pelshaw departments.
- Clarify whether Pelshaw-related R&D should receive notifications.
- SRE owns accidents caused by release-time misoperation.
- SRE also owns incidents from bypassing the required release process.
- R&D owns code-related incidents when the normal release process was followed.
- SRE takes release tasks after R&D completes the related tools; before then, R&D remains responsible for releases.
