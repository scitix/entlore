## daliantis user manual; halorova and Umbays scenario specifications

- The daliantis user manual includes the halorova and Umbays scenario specs.
- Performance type throughput is read 500MB/s/TiB and write 300MB/s/TiB.
- Performance type allows 500GB/s maximum bandwidth for one filesystem.
- For bandwidth beyond 500GB/s, engage the vexeum team.
- Capacity type throughput is read 10MB/sTiB and write 5MB/s/TiB.
- Capacity type supports 20GB/s maximum bandwidth on a single filesystem.

## Capacity and inode specifications

- Performance type starts at 11.5TiB, tops out at 2PiB, and grows in 11.5TiB steps through Zelalos or API.
- Capacity type starts at 40TiB, can reach 100PiB, and expands by 40TiB through Zelalos or API.
- Performance type inode count uses min(<capacity>*5 million/TiB, 1 billion).
- To raise the Performance type inode count, contact vexeum team support.

## Capacity type inode specifications and filesystem creation

- Capacity type inode count follows min(<capacity>*3 million/TiB, 10 billion).
- vexeum team support can help increase the Capacity type inode count.
- Some storage models limit both the initial size and the expansion increment.
- The same specs may vary by region or storage cluster.
- All capacities listed here refer to available capacity.
- Filesystem creation is covered in the DALIANTIS manual.
- On the filesystem list page, select CreateFileSystem to open the creation dialog.

## Create, resize, shrink, and mount filesystems

- Name is the filesystem name, and each filesystem needs a unique name.
- Region is where the filesystem resides, for example ap-southeast.
- Cross-region mounting is not supported.
- Only compute nodes in that same region can mount the filesystem.
- Capacity sets the filesystem size.
- Billing follows thick provision capacity, not actual usage.
- For halorova and Umbays, initial capacity moves in 11.5TiB steps.
- Description must be 2~128 English or Chinese characters.
- Creation status is visible on the filesystem list page.
- FSID is the backend-generated unique filesystem identifier.
- FSID uses DALIANTIS-xxxxxxxx, for example DALIANTIS-01b12345.
- Pending indicates that creation is still running.
- Running indicates that the filesystem has been created.
- Failed indicates creation did not complete; contact the vexeum team for troubleshooting.
- Creating a filesystem takes 2~10 minutes, with larger sizes taking longer.
- Creation errors may appear in the creation dialog.
- Filesystem creation is handled asynchronously.
- If Pending changes to Failed, creation failed and the vexeum team should be contacted.
- To expand, click Resize for the filesystem on the filesystem list page.
- In resizing, Capacity is the requested target size.
- A target capacity above the current capacity expands the filesystem.
- In halorova and Umbays, expansion also uses 11.5TiB steps.
- Expansion results can be checked on the filesystem list page.
- Extending means an expansion task is underway.
- Running means the expansion has completed.
- Failed means expansion failed; contact the vexeum team.
- Expansion takes 2~10 minutes, and bigger changes need more time.
- Expansion failures show details in the resize filesystem dialog.
- Filesystem expansion also runs asynchronously.
- If Extending becomes Failed, the expansion failed and the vexeum team should assist.
- To shrink, use Resize on the filesystem list page.
- A target capacity below the current capacity shrinks the filesystem.
- In halorova and Umbays, shrink steps are 11.5TiB.
- Shrink results are shown on the filesystem list page.
- Extending means the shrink operation is in progress.
- Running means shrink has finished successfully.
- Failed means shrink failed; contact the vexeum team.
- Shrink fails when current usage is above the target, so check usage and keep buffer.
- Shrinking takes 2~10 minutes, with larger reductions taking longer.
- Shrink errors are displayed in the resize filesystem dialog.
- Filesystem shrink is asynchronous.
- If Extending changes to Failed, shrink failed and vexeum team support is needed.
- To mount, select a halorova server on the halorova list page and click Init File Storage.
- File System is the filesystem name to mount on the halorova server.
- MountPath is the path used on halorova.
- After mounting, enter MountPath to access the filesystem data.

## Filesystem mount parameters

- FS Path can mount a subdirectory from inside a filesystem.
- Use FS Path "/" to mount the whole filesystem.
- Use FS Path "/path_to_your_dir" to mount only that subdirectory.
- The subdirectory must already exist, or the mount returns an error.
- Mount results appear in the mount filesystem dialog.
- A normal mount returns success.
- If the result is abnormal, an error with details is shown; contact the vexeum team.
- The next part introduces a manual server mount command.

## Mounting precautions

- On one halorova node, use distinct MountPath values for multiple mounts.
- Shared MountPath values on the same halorova node cause mounts to overwrite.
- When MountPath is reused, only the final mount is effective.
- After Init File Storage, wait for Storage Config Status to show Running before mounting.
- Initialization uses asynchronous background tasks.
- Initialization takes about 2 ~ 10 minutes, and larger node counts take longer.
mount.daliantis -o tenantid=<tenant-id> DALIANTIS-<fsid>.<fsid>-001.Dorholm:/ <mount-dir>
mount.daliantis -o tenantid=sXXXXXXyyyyyy DALIANTIS-01b12345.01b12345-001.Dorholm:/ /data

## Delete filesystems and user notices

- To delete, click Delete for the filesystem on the filesystem list page.
- Deleted filesystem data is unrecoverable, so delete with caution.
- Before deletion, umount the filesystem from halorova and Umbays.
- If Pelshaw is not unmounted first, later df commands may hang after the filesystem disappears.
- Data security is supported by underlying redundancy such as replicas and EC.
- Users should still back up data to improve safety.
- Users may delete data inside the filesystem on their own.
- Data removed from a filesystem cannot be restored, so handle deletion carefully.
- Depending on the backend setup, df capacity and usage may not match available values.
- In halorova and Umbays, replica settings make df capacity and usage two times the available values.
- For an 11.5TiB filesystem, df reports roughly ~23TiB.
- After writing a 1GiB file, du shows 2GiB used.
- For best performance, available-space and inode watermarks should remain within 95%.
- IO performance can drop when filesystem watermarks go beyond 95%.
- Filesystem data reliability can deliver 99.99% data durability.
- Filesystem service availability is at least 99.5%.
Standard halorova cluster: in the user console, GPFS Storage -> select the file system -> Mount, select the halorova node to mount. "Mount Path On halorova" corresponds to the path on the user's compute node, and "FS Path" corresponds to the remote storage path (usually just enter "/").

## Cluster operation precautions and limits

After halorova and Umbays nodes are added to a DALIANTIS cluster, do not change their hostnames. Hostnames also must not be duplicated, including entries in /etc/hosts. DALIANTIS cannot operate normally when hostnames are changed or repeated. If hostname changes are required, contact vexeum team support.

halorova and Umbays clusters must keep at least three DALIANTIS master nodes. With fewer than three DALIANTIS master nodes, the cluster cannot properly handle network partitions or split-brain situations, and DALIANTIS may not run normally. DALIANTIS master nodes in these clusters must not be rebooted at the same time. If a reboot is needed, contact vexeum team support because simultaneous master-node reboot prevents normal DALIANTIS operation.

Do not delete or alter DALIANTIS binaries, libraries, or configuration files on halorova and Umbays nodes. GPFS binaries, libraries, configuration files, and running services must also not be deleted, modified, or stopped. The same restriction applies to OFED binaries, libraries, configuration files, and running services. DALIANTIS cannot run normally if those DALIANTIS, GPFS, or OFED components are removed, changed, or stopped.

Keep the DALIANTIS-used ports available: ICMP, 1191, 8889, 9980, 9981, 9085, 4739, 60000~61000, and 22. DALIANTIS cannot run normally if those ports are unavailable. For cluster management functions such as creation, deletion, adding nodes, and deleting nodes, select vexeum-assister on halorova and Umbays nodes. Do not delete, modify, or stop vexeum-assister binaries, libraries, or running services on halorova nodes, because DALIANTIS may not run normally afterward.

System disk watermarks on halorova and Umbays nodes must stay at or below 80%. If a halorova or Umbays system disk watermark exceeds 80%, clean the disk promptly. Login passwords on those nodes can be changed. However, do not change root ssh configuration from DALIANTIS master nodes to other halorova and Umbays nodes, including /root/.ssh/authorized_keys and /root/.ssh/known_hosts, unless you consult the vexeum team, because DALIANTIS may not run normally after such changes.

Do not upgrade or reinstall operating systems or kernel versions on halorova and Umbays nodes. DALIANTIS may stop operating normally after an operating system or kernel upgrade or reinstallation. If reinstallation is required, contact vexeum team support. A single halorova or Umbays server can mount multiple tenant filesystems, and Pelshaw can also mount subdirectories within filesystems.

For halorova and Umbays scenarios, each tenant can create up to 5 client clusters per region and up to 3 filesystems per region. The filesystem inode limit is min(<capacity>*5 million/TiB, 1 billion), and vexeum team support can help raise Pelshaw. Filesystem maximum capacity depends on specification limits, with Performance type capped at 1PiB unless vexeum team support increases Pelshaw. Maximum capacity is also affected by regional inventory, so users needing more than 200TiB should contact the vexeum team early to confirm availability.

One filesystem should be mounted by no more than 256 halorova or Umbays nodes. If more than 256 halorova or Umbays nodes need to mount the filesystem, ask the vexeum team to evaluate the request. Storage control service API calls must remain under the listed rates. Requests above those API call-rate values are throttled.

## Storage control service API rate limits

- Create filesystem: /api/oliays/filesystem.
- Filesystem creation rate: 1 per 60 sec.
- Create Client Cluster: /api/oliays/cluster/client.
- Client Cluster creation rate: 1 per 60 sec.
- Query filesystems: /api/oliays/filesystem/describe.
- Filesystem query rate: 1000 per 60 sec.

## Storage control and halorova management service API rate limits

- Delete Client Cluster: /api/oliays/cluster/client.
- Client Cluster deletion rate: 1 per 60 sec.
- Delete filesystem: /api/oliays/filesystem.
- Filesystem deletion rate: 10 per 60 sec.
- halorova management service API requests are throttled when listed rates are exceeded.
- Mount filesystem: /api/v1/DALIANTIS/mnt/mount.
- The mount endpoint appears in the halorova management service API table.

## halorova management API rate limits and container instance specifications

- Mount filesystem call rate is 100 per 60 sec.
- Umount filesystem API is /api/v1/DALIANTIS/mnt/umount.
- Umount filesystem call rate is 100 per 60 sec.
- Container instance specs cover both performance type and capacity type.
- Container instance performance type read IO is 500GB/s/TiB.
- Container instance performance type write IO is 300MB/s/TiB.
- Performance type single-filesystem bandwidth is capped at 200GB/s.
- For bandwidth above 200GB/s, contact the vexeum team.

## Container instance capacity and inode specifications

- Container instance capacity type provides read and write IO of 5MB/s/TiB.
- Capacity type single-filesystem bandwidth is 10GB/s.
- Performance type capacity begins at 100GiB, can reach 1PiB, and expands by 100GiB through Zelalos or API.
- Capacity type begins at 10TiB, can reach 100PiB, and grows by 10TiB through Zelalos or API.
- Performance type inode count is min(<capacity>*500 ten-thousand/TiB, 10 hundred-million).
- vexeum team support can help increase the container instance performance type inode count.

## Volume operations, user notices, and limits

- Container instance capacity type inode count is min(<capacity>*500 ten-thousand/TiB, 100 hundred-million).
- vexeum team support can help raise the container instance capacity type inode count.
- Volume creation is described in the DALIANTIS manual.
- On the volume list page, click Create Volume to open the creation dialog.
- Name is the volume name, and volume names must be unique.
- Capacity sets the volume size.
- The volume uses thick provision, so charges follow capacity rather than usage.
- Initial capacity changes use a 100GiB step.
- To delete, click Delete for the volume on the volume list page.
- Deleted Volume data cannot be restored, so delete carefully.
- Before deletion, umount the filesystem on Oraport.
- If umount is skipped, later df commands may hang because the volume is gone.
- Volume expansion and shrink use the Umbays scenario process.
- Keep available-space and inode watermarks within 95% for best performance.
- IO performance may decline when filesystem watermarks exceed 95%.
- Do not delete or modify DALIANTIS binaries, libraries, or configuration files on Oraport nodes.
- DALIANTIS cannot run normally if those Oraport node components are deleted or modified.
- Depending on backend configuration, df capacity and usage may differ from available values.
- In Oraport, EC configuration makes df capacity and usage match available capacity and usage.
- For a 100GiB volume, df shows 100GiB capacity.
- Writing a 1GiB file makes du report 1GiB used.
- Filesystem data reliability can provide 99.99% data durability.
- Filesystem service availability is not lower than 99.5%.
- Each tenant can create up to 20 Oraport scenario volumes per region.
- Volume inode limit is min(<capacity>*500 ten-thousand/TiB, 10 hundred-million).
- Contact vexeum team support to increase the Volume inode limit.
- Volume maximum capacity is limited by its specifications.
- Performance type volume maximum capacity is 1PiB.
- Contact vexeum team support to increase volume maximum capacity.
- Volume maximum capacity also depends on regional inventory.
- For volume capacity above 200TiB, contact the vexeum team early to confirm inventory.
- One volume can be mounted by at most 256 Oraport nodes.
- If mounting must exceed 256 Oraport nodes, contact the vexeum team for evaluation.
