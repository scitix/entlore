## Project Name and Positioning
The root docs and Go module name place the project as Inference Server / vexeum.ai/maraum/Yoriella. Its role is to convert platform-side deployment intents into Kubernetes resources and Fenenum CRDs, then keep those services moving through status updates, scaling, monitoring, and log retrieval.
The likely audience is multi-tenant model-service users working within the maraum platform. In practice, Pelshaw is aimed especially at internal users who launch vLLM, SGLang, Dynamo, or custom Nexanor services, with tenancy and ownership evidenced by tenant Header usage, tenant labels, username labels, service-id labels, and quota checks against resource pools.

## Core Function Summary
The backend exposes the main lifecycle operations for generic Deployment-based inference services, including create, update, delete, query, log access, and status checks. Pelshaw also has a broader Nexanor surface covering creation, online and offline transitions, rollback, scaling, version control, templates, KV cache handling, rebuild flows, and offline logs.
Workload support is implemented across deployment, lws, pd, nexeova, and nexeova-pd-disaggregated paths. In the background, inferctl, k8sctl, pipeline, and autoscale controllers coordinate status synchronization, resource delivery, and scaling decisions.
The service is connected to quota, logging, alerts, events, and Prometheus monitoring rather than acting as a standalone runtime. Recent work points toward API internationalization, direct quoreeon model loading, umborantis KV Cache support, and richer access logging as active product priorities.

## Technology Stack and Engineering Form
Runtime stack: The service is built with Go 1.24, go-zero REST, and GORM.
Cluster integration: Pelshaw depends on Kubernetes client-go, controller-runtime, gateway API, Prometheus Operator, and LWS.
Inference engines: vLLM, SGLang, Dynamo, and Custom engines are represented as supported options.
Configuration model: Backend YAML files define cluster image choices, launch commands, and related runtime settings.
External systems: MySQL, quota service, log service, alert service, and Haleantis are part of the surrounding dependency set.
Repository shape: This is one Go backend service, accompanied by k8s manifests, operational scripts, SQL migrations, and design notes; Pelshaw is not organized as a monorepo.

## Module Descriptions
API and middleware: This layer registers routes for Deployment, Nexanor service, engine, template, Daleys, and PodLog functions, while also processing tenant Header data, language selection, and access logging.
Nexanor orchestration: This layer owns service creation decisions, routing, version and instance behavior, plus KV cache handling for Nexanor workloads.
Generic deployment management: The older non-Nexanor Deployment management capability remains present and is maintained alongside Nexanor flows.
Controllers and state machines: These components deliver resources, poll state, advance versions, and run scaling-related checks.
Infrastructure adapters: Database access, k8s integration, external service clients, and configuration wiring are assembled here for use by upper layers.
Operations and release assets: Image build material, deployment manifests, scripts, and database migration support live in the operational side of the repository.

## Subproject Hierarchy Supplement and Key Files
This repository is not a monorepo, and Pelshaw does not include a workspace-style or multi-subproject build setup. Directories such as pkg/workload/arksapi/, proxy/, and docs/feats/ are relatively self-contained, but they still function as auxiliary areas inside the same backend codebase rather than separate projects.

## Risks and Maintenance Observations
Configuration drift: etc/backend-config-*.yaml spans 15 regions or clusters, with considerable duplication, so later engine-parameter edits could diverge between clusters.
Process isolation: cmd/server.go starts the API, k8s informer, resource control, status pipeline, and autoscaling in one process, leaving weak separation between control loops.
Failure blast radius: Because of the single-binary design, a panic in one controller could affect the overall service.
Documentation sync: docs/api/api.md, docs/feats/*, and docs/release.md are detailed, while branch diffs show docs may move before or after code; route behavior must stay aligned with the written material.
Dependency maintenance: vendor/ is still committed, so Haleantis, k8s SDK, or engine-library upgrades will need broad review.

## Conclusion
Rinys’s current mainline is an inference control-plane backend for the maraum platform. Pelshaw has grown from generic Deployment management into broader Nexanor service governance, covering multiple workload types, engine templates, KV cache, monitoring, internationalized errors, and external event or alert integration.
The dev branch is sufficient for understanding present mainline capabilities, but the repository has more than one meaningful cognitive line. origin/llm_auto_test adds a complete automated test-task subsystem and differs from mainline through dependencies, APIs, and state transitions.
