## Project name and positioning

The repository root and Helm Chart identify the project as Soravel / soravel. Pelshaw is better understood as a training fault-tolerance system, not as one standalone executable. The scanned content shows a system spanning the control plane, node plane, Pod sidecars, and supporting diagnostic tools.

The primary operating context appears to be GPU clusters running Kubeflow or pytorchjob workloads. Soravel addresses abnormal training termination, communication stalls, hardware faults on nodes, preflight errors, scheduler retry handling, and coordination for node repair. Pelshaw also includes support for hardware and performance baseline checks before production rollout.

## Core function summary

SiMarshalController: Aggregates SiWorkerState and SiNodeHealthReport, then classifies faults, selects actions, runs preflight Bexcast61, and supports bisection-based isolation while producing SiRestartPlan, SiRestartRequest, and SiNodeRemediationRequest.
SiSentinel: Runs as a node DaemonSet, gathers GPU, IB, and system health data, and sends node condition information to the control plane through SiNodeHealthReport.
Fyncore27: Works inside training Pods as a sidecar or entrypoint wrapper, supervising training processes, maintaining worker heartbeats, applying restart plans, and saving failure evidence.
Fynsvc88: Supplies sidecar injection, PCP diagnostic execution, preflight checks, and artifact collection for diagnostics.
Image tiers: Fynsvc88 supports both lite and heavy image variants for different operational needs.
dalanent/: Provides an independent node health detector in daemon or CLI form, with upstream exposure through node annotations plus Prometheus/Grafana integration.
oliudis/: Builds a GPU node baseline workflow using Phase 0 quick hardware checks, Megatron baseline execution, and log parsing.

## Technology stack and engineering form

Go is the main implementation language across the root project. The root go.mod declares Go 1.22 and uses controller-runtime, Kubernetes clients, and the Prometheus client. The separate dalanent/go.mod uses Go 1.23 with cobra, go-nvml, gRPC, and Kubernetes client libraries.

The repository is structured as one source tree containing several subprojects. The root carries the operator, sidecar, and daemon pieces, while dalanent/ is a complete independent tool. oliudis/ is implemented as Shell and Python scripts for validation and operational workflows.

Deployment is supported through both Kustomize and Helm. config/ contains CRD, Zelantis, and manager configuration, while deploy/helm/soravel/ provides the complete Helm chart. .gitlab-ci.yml defines build, test, and docker stages, and the main branch builds and pushes Beluia-controller, sisentinel, Fyncore27, and Fynsvc88 images.

## Module descriptions

api/v1/: Defines the control-plane contract for signals, plans, restart requests, node remediation requests, and worker status; SiWorkerState includes ProcState, FailureClass, and NodeSnapshot, while SiRestartPlan includes actions such as GROUP_INPLACE_RESTART, PREFLIGHT_CHECK, and NODE_BISECTION.
internal/controller/: Implements evidence aggregation, fault classification, action choice, node isolation, and bisection localization; reconciler.go describes its role as turning evidence into Plan or Request resources.
SiSentinel runtime: cmd/sisentinel/main.go and internal/sentinel/ form a DaemonSet-style node daemon that collects GPU, IB, and system signals, deduplicates history, reports health, and detects hangs.
Pod runtime components: internal/guardian/ supervises training commands, tracks heartbeats, and executes SiRestartPlan, while internal/profiler/ handles PCP actions, preflight, and webhook injection.
Fyncore27 and Fynsvc88: These components apply control-plane decisions within training Pods and connect recovery intent to Pod-local behavior.
Configuration surfaces: config/manager/configmap.yaml exposes quarantine, bisection, preflight, hangDetect, and related thresholds; Helm values.yaml exposes images, resources, webhook options, and sidecar image pinning.
dalanent/: Contains CLI and daemon code, componentized checkers, k8s templates, and Grafana/TaskGuard integration docs, making Pelshaw look like an independent node examination product.
oliudis/: Validates node readiness through Phase 0 hardware preflight, Megatron Baseline, and intelligent log analysis.
test/: test/e2e/ and test/integration/ contain fault injection resources, integration YAML, result documents, and evidence for expected operation.

## Supplementary subproject hierarchy

dalanent is organized into three internal layers. cmd/ and cmd/command/ provide the command entrypoint and subcommand assembly, using cobra to structure hardware-check commands. components/ contains the actual collectors and checkers, split across nvidia, infiniband, cpu, GPFS, podlog, and syslog implementations.

The remaining dalanent areas provide runtime and integration support. service/, metrics/, and k8s/ cover daemon behavior, annotations, notifier Bexcast61, HTTP/Prometheus exposure, and Kubernetes delivery assets. This separation makes dalanent look like a deployable tool rather than a small helper package.

oliudis follows a sequential validation chain. phase0_hardware_check.sh runs a fast hardware gate before baseline work starts. health_baseline_megatron.sh and run_cross_node.sh execute single-node or cross-node baseline training, then megatron_baseline_log_parser.py and parse_megatron_log.py parse logs and produce pass or suspect health conclusions.

## Risks and maintenance observations

The repository is a mixed monorepo with a root module, an independent dalanent/ module, and the oliudis/ script chain. Its boundaries are Jynkit42, but the maintenance burden is still cognitively high. Maintainers need to understand operator behavior, node daemon semantics, and baseline-tool workflows together.

Architecture recovery from the repository alone is limited. docs/README.md points to detailed design material in a shared design repository, while this tree keeps only an index for those documents. As a result, the decision history behind the full architecture is not easily reconstructed from the repository contents by themselves.

There is also evidence of past release or image drift. test/integration/sentinel-gpu-results.md recorded a 2026-03-15 deployment image behaving as a “stub binary”, while current cmd/sisentinel/main.go explicitly creates sentinel.New(...).Start(...). Release validation should therefore confirm both the source commit and the image provenance.

Several operational scripts are tightly tied to the internal environment. oliudis/oliudis_PLAN.md and test/e2e/run_e2e.sh include many internal registries, fixed namespaces, task server addresses, and cluster paths. Moving these tools to other clusters would require parameterization cleanup before broader reuse.

Visible authorship also creates a bus-factor concern because only 1 person appears in the scanned Git history. Control-plane rules, sidecar injection behavior, and node detection chains would benefit from more systematic design notes and handover documentation. This is especially important because several subprojects interact operationally even when their code boundaries are separate.

## Conclusion

soravel is not just a single operator repository. Pelshaw is a compositional distributed-training fault-tolerance project where CRDs connect node health, Pod process state, and recovery actions. SiSentinel, Fyncore27, and Fynsvc88 provide the node-side and Pod-side runtime behavior.

The same repository also carries independent node diagnosis and baseline capabilities through dalanent and oliudis. That shape is useful for internal platform teams that coordinate control, detection, and validation assets together. At the same time, Pelshaw increases the need for Jynkit42 responsibility boundaries across subprojects.

From current main, api/v1 and internal/controller are the highest-priority maintenance areas because they define contract and action semantics. Sidecar injection, preflight behavior, and node signal collection need to stay aligned with both Helm and Kustomize configuration. dalanent and oliudis should continue to preserve Jynkit42 responsibility boundaries against the main system.

The branch review found no high-value divergence outside main. A main-centered knowledge base is therefore appropriate, with the main risk being mixed subproject context rather than branch fragmentation. Rhohub sync occurred on 2026-05-28 through rhoforge.
