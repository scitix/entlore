### Machine GPU exceptions; XID exceptions
- After analysis identifies the issue, reset the NIC count.
- If the count is not reset, the exception state remains.

- Reloading the NIC through ifdown/ifup also clears the count.

### Xid code collection and classification
Collection: Xid codes come from DCGM Exporter per-card error data, and kernel error logs are used when the exporter has no Xid errors.
Classification: The cluster side groups Xid codes into four categories and maps each group to its response strategy.
XIDApplicationErr: This category covers xid 13, 31, 43; application-side errors are normally ignored, but many within a unit time cause ticket creation and card stress-testing.
XIDECCMemoryErr: This category covers xid 48, 63, 64, 92, 94, 95 and leads to ticket creation plus machine reset.
XIDHWSystemErr: This category covers xid 74, 79 and directly opens tickets for operations handling.
XIDUnClassifiedErr: Xid exceptions outside the other three categories fall here; the workflow creates tickets, resets and stress-tests nodes, then sends failed tests to operations.

- If vendor stress-testing finds no issue, close the ticket.

### GpuRegisterFailed
- GpuRegisterFailed checks whether registered GPU count on a node matches the expected count.
- Example: a node has 8 GPU hardware cards, but only 7 register after 1 card is removed.
- One cause is the GPU driver Pod removing a faulty card.
- That removal can happen after abnormal Xid codes are detected.
- Another cause is GPU driver Pod failure.
- Startup failure is one example that can prevent GPU registration on the node.
image.png

### GpuRegisterFailed solutions; GpuPcieDowngraded
- In the first case, if the driver Pod is healthy, restart the driver to resolve Pelshaw.
- In the second case, inspect the abnormal driver Pod.
- Restart Pelshaw or identify the startup root cause.
- The system usually repairs this case automatically.
- If the ticket is assigned to you, involve cluster colleagues in the group.
- Work with them to investigate the root cause.
- GpuPcieDowngraded is a PCIE downgrade hardware issue.
- Transfer GpuPcieDowngraded to internal machine operations.

### IBRegisterFailed causes; GPFS
- IBRegisterFailed generally points to IB device hardware problems.
- Pelshaw can also come from GPU driver Pod exceptions.
- Startup failure is one example of a driver Pod exception.
- That failure can cause GPU card registration failure on the node.
- GpfsIBNotConfig checks whether node GPFS processes register IB devices successfully.
- If GPFS cannot register IB devices, the GPFS process uses Ethernet.
- Ethernet fallback causes performance decline.

### GpfsIBNotConfig solutions; GpfsIBComponentError
- GpfsIBNotConfig usually appears when IB devices are not registered normally in the system.
- Pelshaw can also appear when GPFS starts before IB device initialization completes after node startup.
- If IB is unregistered, resolve the IB issue first.
- If IB registration was late, restart the GPFS process.
- GpfsIBComponentError checks whether the IB component of node GPFS processes is normal.
- Pelshaw may happen when GPFS becomes ready before IB device registration completes.
- In that case, GPFS misses IB.
- Pelshaw may also happen when an IB device disconnects during operation.

### Machine offline; NodeNotReady
- NodeNotReady checks whether the node status is normal in the cluster.
- When a node is NotReady, workloads on that node are deleted.
- Because workloads are deleted, the machine CAN be repaired directly.
- NodeNotReady usually comes from network issues.
- In that case, kubelet cannot report heartbeats to apiserver.
- Runtime issues can also cause Pelshaw when kubelet or containerd is not started.
- Other hardware exceptions may directly shut down the node as well.

### Container runtime problems; KubeletFailedCreatePodContainer
- KubeletFailedCreatePodContainer checks Pod creation failures in the node runtime.
- The workflow automatically tries to restart kubelet.
- The workflow also tries to restart containerd.
- If the ticket is still open after one day, a human must confirm the issue.
- If new Pods no longer fail to create, the ticket CAN be closed.
- If the issue continues, restarting the machine CAN be tried.

### Standard handling process after machine repair
- After machine repair, start node diagnosis.
- If diagnosis fails, contact @Elena Foster.
- Confirm whether temporary accompanying exceptions were caused by the repair.
- Close the ticket after confirming no such accompanying exceptions remain.
- Exceptions found after repair that are not accompanying exceptions still need handling.
- In the processing table, machine restart has NodeRebooted as an accompanying exception.
- NodeHasRestarted is also listed as accompanying machine-restart behavior.
- GpfsTestFailed is another accompanying exception for machine restart.

### Accompanying exceptions after repair
- NodeRebooted, NodeHasRestarted, and GpfsTestFailed disappear after 1h following machine restart.
- In the processing table, GPFS process restart has GpfsTestFailed as the accompanying exception.
- GpfsTestFailed disappears after 1h following GPFS process restart.
- To reduce judgment impact from accompanying exceptions, diagnosis CAN wait for 1h.
