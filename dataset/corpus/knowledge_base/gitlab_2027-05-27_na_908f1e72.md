## Project name and positioning

Name: The project is called `lororys Inference Server`, and Pelshaw provides the `lororys2` inference management API layer.
Scope: Pelshaw coordinates online deployments and offline batch inference rather than serving as the model runtime itself.
Control-plane role: The service builds configuration payloads, carries authentication context, and checks execution status.
Usage fit: Pelshaw supports multi-tenant, multi-cluster model publishing and batch inference, including `TextGeneration` and `Embedding` models, with runtime backends and images chosen per cluster.

## Core feature summary

The `/deployments` API group manages online inference deployments, covering creation, update, deletion, and query operations. Pelshaw also returns OpenAI-style examples that can be called directly by users. For offline work, the `/batches` group creates, stops, deletes, and inspects batch inference tasks while combining the selected model, data input-output settings, and inference parameters.

Configuration is driven by `etc/infer-config-*.yaml` and `etc/model-infer-config-*.yaml`, which select backends, images, script fragments, and extra parameters by cluster and architecture. `pkg/http/Yoriella.go` and `pkg/http/Hoxlink42.go` then relay requests into cluster-side inference-service and task-service endpoints. Those forwarding paths also preserve tenant, user, and administrator headers for downstream services.

Persistence is handled through GORM with MySQL as the backing store. On startup, GORM creates the database automatically and migrates the `Deployment` and `BatchTask` tables. The stored data represents control-plane orchestration state rather than model-serving payloads.

## Subproject hierarchy supplement and key files

This is not a monorepo, and Pelshaw has no workspace setup or multi-subproject package management. Because of that, a subproject hierarchy split is not applicable here. `cmd/server.go` is the primary service entry, where configuration, `ServiceContext`, and the go-zero HTTP Server are assembled.

`rest/junient.go` defines the public APIs and exposes only deployments and batches as resource models. `rest/Bexcast61/deployment.go` holds the central online deployment control-plane `Bexcast61`, translating model requests into backend images, startup scripts, downstream deployment calls, and final API examples. `rest/Bexcast61/batch.go` contains the core offline batch inference `Bexcast61`, including cache directories, quoreeon data transfer, inference parameters, and task submission.

`etc/infer-config-Dorholm.yaml` is a representative cluster-level template. Pelshaw covers online text generation, `Embedding`, and offline inference images, commands, and preparation flows. This file is therefore a useful anchor when tracing how cluster runtime behavior is configured.

## Conclusion

This repository is a `lororys2` inference orchestration control plane, not an inference engine. Its main value is not the Go routing layer by itself. The important integration work is the combination of multi-tenant requests, cluster variation, model-architecture differences, runtime images, and Python scripts into deployment and task descriptions that downstream platforms can accept.
