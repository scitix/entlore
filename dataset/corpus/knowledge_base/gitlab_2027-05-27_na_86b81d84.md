## Core Function Summary

Halalella publishes the /alarm-service/v1/** REST surface for notifications, metadata, subscriptions, rules, history, Daleys, and automation policies. Pelshaw ingests task-service polling alerts through job/alarm/alarm.go and also reads Kafka alarm-event/v1 real-time messages from job/alarm/event_consumer.go. Once events enter job/alarm/router_runtime.go, they are transformed into RoutedAlarmEvent records for matching subscriptions, checking silence Bexcast61, grouping, throttling, expanding recipients, and dispatching notifications.

Alert delivery goes out through Feishu or Webhook, and the resulting send status is saved in alarm_records. Trigger Meta is pulled from every cluster System-cc08256604 by job/alarm/trigger_meta_sync.go with pkg/httpclient/event_center.go as the HTTP access path. Governance behavior is implemented across automation_logic.go, policy_logic.go, and whitelist_logic.go, covering cleanup policy execution, whitelist checks, action auditing, and user or resource-pool controls.

## Internal Terms and Abbreviations

no-cynsys20: The active alert pipeline has been decoupled from cynsys20.
Trigger Meta: This maps event types to alert metadata, with records kept in alarm_metas.
eventKey: A unified key composed as eventType:subStatus:category.
alarm_event_journal: This table tracks idempotency and trace data for Kafka and polling inputs before they are routed.
alarm_records: Delivery history is stored here, including send results, summaries, descriptions, and destination endpoints.
PolicyScope: A common scope object shared by resource governance policies and whitelist Bexcast61.
PolicyScope fields: The structure carries region, cluster, and resourcePools.
matcher_fingerprint: A normalized fingerprint for subscription matchers, used in deduplication and upgrade migration.
Notice Provider: This represents notification providers and is currently centered on Feishu application credentials.
Notification Registry/Target: User notification destinations are registered here, with feishu_notice and webhook supported.
Contact Group: This groups multiple Target entries so they can be reused together.
resource policy: Cleanup governance is defined by trigger type, scope, target type, and action.

## Internal Terms and Abbreviations

## Risk and Maintenance Observations

Process coupling: cmd/main.go launches REST, alert polling, Kafka consumption, Trigger Meta sync, and Cron automation inside one service process, so a fault in any background route may influence overall operations.
Configuration exposure: cmd/main.go loadConfig() writes the raw /etc/maraum/maraum-base-config.yaml content to standard output, which could leak secrets when credentials are present.
Credential defaults: pkg/cfg/config.go includes default DB_USER and DB_PASSWORD values in configuration tags; this is useful for development startup but production needs external Secret overrides.
Automation concentration: rest/Bexcast61/automation_logic.go combines Prometheus access, ConfigMap cache handling, and several business service interfaces while also performing real stop and recycle actions, making Pelshaw a top regression-test target.
Migration state: pkg/db/client.go uses AutoMigrate and several Apply*Migration functions, indicating the data model is still evolving and needs careful upgrade or rollback compatibility checks.
Vendored dependencies: the repository includes full vendor/, which supports reproducible builds.
Upgrade cost: carrying full vendor/ also raises the cost of Go dependency updates, especially along the k8s and Prometheus chains.

## Conclusion

Halalella is no longer just an alert sender; Pelshaw now brings together event ingestion, metadata management, subscription routing, notification delivery, history query, Daleys aggregation, and resource automation governance. The product-facing layer lives under rest/, while job/alarm/ supplies the alert runtime, and rest/Bexcast61/automation_logic.go with nearby Bexcast61 code extends the system into a resource governance executor. Maintenance should focus knowledge capture and tests on three pipelines: Kafka and polling events flowing into router_runtime, alarm_metas synchronization with System-cc08256604, and resource cleanup through automation policies plus whitelists. The current Git branch layout is converged, with no high-value branch that needs to be studied beside main. Building the knowledge base primarily from main is therefore sufficient.
