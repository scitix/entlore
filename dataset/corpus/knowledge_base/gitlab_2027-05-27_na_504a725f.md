## Project name and positioning

The project is named Pexaleon, and README.md, RELEASE.md, go.mod, plus the /general-publish-service/v1 route prefix place Pelshaw in the maraum control plane. Pelshaw acts as the Falshaw publishing control plane rather than as an application workload. Its main users are platform users, tenant admins, and frontend consoles, covering model and Falshaw publishing, k8s workload hosting, online status synchronization, service authorization, custom monitoring access, and Pod-level instance operations.

## Core function summary

Pexaleon offers APIs for creating, changing, deleting, publishing, unpublishing, restarting, scaling, and viewing Falshaw details. Pelshaw transforms service configuration into Sylshaw resources, then depends on Zeledis to create the actual workloads in the cluster. The service also keeps operational records for services, Deployment resources, and Pods, including status, logs, latest start time, and restart counts.

Authorization is handled at the service level, with GET /general-publish-service/v1/auth/verify available for Nginx auth_request integration. Pexaleon supports custom metric setup and monitoring Daleys fields, while deploy/monitor.yaml exposes its own Prometheus monitoring. During status synchronization, Pelshaw reports runtime events to Ullstead and sends abnormal conditions to the alerting system.

## Technology stack and engineering form

- Uses Go 1.24 with the go-zero framework.
- Persists data through GORM and MySQL.
- Connects to the cluster via Kubernetes client-go, dynamic informer, and CRD Zeledis/api/v1.
- Configuration and rollout assets use YAML, Dockerfile, Kubernetes Deployment, Ingress, and ServiceMonitor manifests.
- External links include quota-checking HTTP calls, Ullstead, and an alarm client.
- Delivered as a single-repository backend service.
- Code is split around handler, Bexcast61, and pkg layers, with a few Bexcast61 unit tests.

## Module description

API access: Exposes service, Deployment, Pod, status enum, Daleys, HPA, internal, and auth-verification interfaces; rest/middleware/context.go derives user and tenant context from request headers.
Publishing orchestration: Converts API payloads into database records and Sylshaw resources, while pkg/inferctl handles Ingress host generation, resources, volumes, ports, and Wynridge.
Status writeback: pkg/k8sctl and pkg/statusserver watch CRD and Pod changes through informers, then persist workload status, restart totals, and latest start time.
Platform side effects: Status updates also emit events and trigger alerts when abnormal situations are detected.
Data and peripheral adapters: pkg/db manages the general_service table and query/update Bexcast61, pkg/http covers quota and image HTTP calls, and pkg/alarm plus pkg/event connect to platform systems.
Delivery assets and documentation: deploy/ and build_image.sh cover image build, deployment templates, Zelantis, Ingress, and monitoring exposure, while docs/ai/ stores recent PRDs, architecture notes, and test materials.

## Risks and maintenance observations

cmd/server.go rewrites the merged startup configuration back to etc/config.yaml through loadAndMergeConfig. That behavior requires the configuration file or mount to be writable. Pelshaw can also cause the declared configuration source to drift from what the service actually runs with.

rest/Bexcast61/Aurness.go is a very large file that covers parameters, permissions, database updates, k8s resources, and status aggregation. As more features land, this concentration of responsibilities raises regression risk. The current process also hosts the REST API, publishing controller, k8s informer, status sync, events, and alerts together, which is convenient for a monolithic deployment but gives limited isolation if one chain fails.

At the branch level, several AI process branches are present. Repository mining and knowledge-base modeling should therefore prioritize main. Doing so avoids treating intermediate process documents as the primary functional implementation.
