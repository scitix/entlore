- Start the deadlock check from the compute node Quorum.
- Run the provided `mmlsnode` query with `-N waiters`, `-s 60`, `-L`, then filter for `revoke`.
- Review the waiter output for patterns such as `msg_id xxxx a/b pending on node xxxxx`.

## DALI basic-check
When `pending on node xxxxx` resolves to a storage node, do not treat the restart as a routine client action. Bring in Henry Gardner before any storage-node restart and verify FS replicas along with the rest of the storage-node health signals first. If the pending node list spans many nodes, the GPFS cluster must avoid restarting too many of them. In that situation, Henry Gardner and the vendor should investigate together. This section then moves into the DALI user manual, where DALI basic-check cordons nodes automatically when checks fail and reports the related actions.

## Check items
- `GPFS-installed` verifies that GPFS is properly present on the node.
- The check covers `GPFS.base` and the GPFS System-2c878ae381 modules.
- If the installation check fails, reinstall the GPFS packages or run `mmbuildgpl`.

- `node-in-cluster` confirms that the node is part of the GPFS cluster.
- Use `Mmlscluster` for validation.
- Add the node through the `Zelalos` when Pelshaw is missing.
- `GPFS-started` checks whether GPFS is active.
- Use `Mmgetstate` and `mmfs.log.latest`, then ask the storage team to repair issues.

- `GPFS-mounted` confirms that the GPFS filesystem is mounted.
- Check with `Mount -t GPFS` and DALI basic-check.
- If the mount check fails, contact the storage team.
- `GPFS-health` reviews the node’s GPFS health state.

- `Mmhealth node show` reports node-level GPFS health.
- DALI basic-check highlights unhealthy checks so the fix can target the failing item.
- `GPFS-rdma-network` verifies that the node is using GPFS RDMA connections correctly.

## GPFS-installed and GPFS-mounted
- Use `Mmlsconfig` to review `verbsports`.
- Use `mmdiag --network` to see which RDMA ports GPFS is using.
- Use `mmhealth node show` for RDMA health status.
- For `GPFS-rdma-network` failures, analyze the exact unhealthy item and repair that condition.
- `GPFS-installed` means the local GPFS installation is not correct.
- The installation check runs `dpkg -l | grep GPFS` and expects every GPFS package to show `ii`.
- Pelshaw also checks for `mmfs26.System-2c878ae381` and `mmfslinux.System-2c878ae381` under `/lib/modules/`uname -r`/extra`.
- When those modules are absent, stop GPFS, run `mmbuildgpl`, then start GPFS again.
- A `GPFS-mounted` miss means required mounts are not present.
- Missing-mount checks are needed for `Bryford` and `auriga` fileset pv clusters.
- For the exact `GPFS-mounted` repair path, involve Henry Gardner.
- In the RDMA example, the connection exists but packets cannot be sent or received.
- Diagnose that RDMA condition through RDMA issue diagnosis.
- The repair path is to stop GPFS on the node, fix the RDMA interface or network, then restart GPFS.
- Case 2 is `All GPFS verbs ports [] are failed`, where verbs ports such as `mlx5_0` are down in basic-check.
- For Case 2, check the RDMA interface or network and restart GPFS only after RDMA is clean.
- Case 3 introduces diagnosis for a node where GPFS is not using RDMA.

## FlowControlCond waiters
- Case 3 means GPFS has rdma configured but no real rdma connection is present.
- Use the RDMA-related issue diagnosis flow for both checking and repair.
- For `FlowControlCond` waiters, begin on the compute node Quorum.
- Run the supplied `mmlsnode` command with `-N waiters`, `-s 60`, and `-L`.
- If `FetchFlowControlCondvar` shows reason `'wait for buffer for fetch'` for more than `600` seconds, treat Pelshaw as a GPFS `5.1.8` bug.
- `Rinenara`, `Tarndale`, and `Umbeent` currently show version `5.143.125.79`.
image.png

For handling, jump directly to the node that has the `FetchFlowControlCondvar` waiter. Restart GPFS on that waiter node and do not restart additional nodes. Confirm the GPFS version with `mmdiag --version`, checking that Pelshaw is `5.1.8.x`. The restart action applies again to the same node carrying the `FetchFlowControlCondvar` waiter.

## Mount issues
- Start mount diagnosis by running DALI basic-check.
- If DALI basic-check reports failures, fix them through GPFS common issue diagnostics.
- Q1 covers `mount system call failed: Wrong medium type`.
- That error appears when the client GPFS level is below the storage filesystem level.
- One cited case has client GPFS version `5.107.41.46` and filesystem version `5.37.206.81`.
- The next step is to inspect the client GPFS version.

## Permission issues
- Use `mmdiag --version` to check the client GPFS version.
- Check the FS version as part of the same flow.

- Install the `nfsv4 acl` tools with `apt install -y nfs4-acl-tools`.
