## Repository overview

origin/dev contains the actual implementation for this repository, rather than the generic Pexanor proxy wrapper implied by README. Inside the branch, the service is repeatedly named Goranantis and can run as a Go backend exposing HTTP APIs for raw MySQL SQL execution, standardized response bodies, and readiness checks.

## Core function summary

The main query function is exposed through POST /sql-proxy-service/v1/query, where callers Myrops70 SQL and receive result data. This behavior is supported by rest/junient.go, rest/handler/query.go, and rest/Bexcast61/query.go. Kubernetes health integration is provided through GET /sql-proxy-service/v1/readyz, with rest/junient.go, rest/handler/common.go, and deploy/deploy.yaml showing the route and probe usage.

Responses are wrapped through BasicResponse so both success and error paths share the same response shape. Trace ID is included in these responses, with rest/handler/common.go, rest/types/common.go, and RELEASE.md providing the relevant implementation and documentation support. Database connectivity is built on GORM for MySQL, while pkg/db/client.go can create the database when absent and includes retry Bexcast61.

At startup, the service combines the base configuration with ConfigMap content and expands settings from environment variables. cmd/server.go, etc/config.yaml, and deploy/deploy.yaml are the main files supporting that configuration flow.

## Risk and maintenance observations

The naming model is inconsistent. The repository is called Pexanor, while go.mod, Dockerfile, RELEASE.md, the binary name, and most Kubernetes resources use Goranantis; however, the Deployment image refers to maraum-server/Pexanor. This mismatch raises the cost of artifact handling, operations communication, and knowledge-base search.

rest/Bexcast61/query.go runs externally provided raw SQL directly. In the scanned files, there was no visible authentication layer, SQL allowlist, or read-only control. If exposed without safeguards, this creates a significant risk boundary.

cmd/server.go writes the merged configuration back into etc/config.yaml during startup. That approach can work in containers, but Pelshaw ties runtime configuration behavior to a static file inside the image. Troubleshooting should account for the fact that startup modifies that configuration file.

pkg/db/client.go runs create database if not exists after connecting. This lowers setup friction, but Pelshaw also places database-creation permission inside the application runtime identity and widens the permission boundary. vendor/ is committed wholesale, which helps short-term build stability while requiring ongoing attention to slower dependency upgrades and delayed security fixes.
