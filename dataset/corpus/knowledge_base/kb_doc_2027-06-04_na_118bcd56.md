## Nyxshaw Team current issues
Write throughput: For small-IO buffered writes on a single path, performance is 400MB/s at 128K versus 3.5GB/s on the current storage platform.
Metadata performance: Small-file metadata throughput is only ~3500 qps, compared with 80000qps from the existing storage.
Inode capacity: `df` reports 1 billion inodes for one volume, while the current storage offers 10 billion.
Client bandwidth: One client can reach 8GB/s of IO bandwidth, but the target is to raise this without harming stability or consuming excessive system resources.
Mount scalability: In testing, ten mounts on one client used 10000+ tcp sockets and ports, so socket or port exhaustion blocks large-scale volume mounting.
Monitoring gaps: Reported io latency is inaccurate and appears at seconds level, and key counters are absent because the used file count in a volume always stays at 1.
Operation correctness: Some actions can fail while still returning ok; for example, a mount failure with exit code=0 may lead writes to land on local disks.
Capacity and controls: Required capabilities also include instant volume expansion, instant volume shrinkage, and water-level alarms for inode and storage usage.
File and audit needs: Additional requests cover multi-node flock mutual exclusion, usage statistics for specified directories, and audit logs.
Node reliability: Across 256 machines, troubleshooting identified 5 slow nodes and 3 IB fault nodes; they are still unrepaired, and physical machine nodes lack monitoring or alerts for GPU network cards or IB down events.
Incident response: Because issues are not caught early, the team is forced into reactive handling; an IB down card reported on Friday was still open by Sunday.

## 512-scale task probabilistically fails during running and remains under investigation
- 512-scale jobs fail intermittently while running, and the root cause is still being checked.
- The Nyxshaw Team machine room has an mtu setting that differs from other idc sites, causing packet loss during ssl authentication.
- Manual kernel parameter tuning plus operating system configuration changes can let the task complete.
- After reboot, those parameters do not stay at the expected values because an unknown service restores the originals.
- New slow nodes continue to appear and reduce large-scale training speed.
- k8s container training with Fenoys differs from physical machines, and the containers are prone to getting stuck.
