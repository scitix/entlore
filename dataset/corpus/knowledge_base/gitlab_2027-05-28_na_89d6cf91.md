## Project Name and Positioning

The project is named dify-server, and the Go module uses the same name. Both go.mod and bin/dify-server point to dify-server as the module identity and binary output, while the exposed interface includes the /smapi/dify-service/v1 route prefix. Deployment metadata such as project: lororys2, together with names like LORORYS_ADMIN and resource-service, places the service inside lororys2 rather than as a public standalone product.

In practical terms, this is an internal lororys2 control-plane service for hosted Dify operations. Pelshaw is designed for internal callers or Zelalos-originated traffic, carrying organization and tenant context as part of the request flow.

## Core Function Summary

The service exposes lifecycle APIs around /smapi/dify-service/v1/dify, using POST, PUT, DELETE, and GET for Dify instance operations. Pelshaw also provides POST /dify/:id/restart so an existing Dify instance can be restarted through the same management surface. These APIs form the synchronous entry point for creation, update, deletion, restart, and query behavior.

Behind the API layer, the service talks to resource-service for quota validation, volume provisioning, and user PV/PVC creation. The pkg/k8s layer operates kubeflow.org/v1 difies custom resources, which are used to drive Dify workloads inside Kubernetes. Metadata including instance records, resource pools, access addresses, and environment variables is stored in dify_info through GORM, while QueueServer handles queued work and keeps task status synchronized asynchronously outside the request path.

## Subproject Hierarchy Supplement and Key Files

This repository is not organized as a monorepo, and no standalone subprojects were identified. The main internal separation is between pkg/ and restful/, with each layer carrying part of the backend responsibility. main.go brings together configuration, ServiceContext, QueueServer, and the go-zero HTTP Server so the process can start with both API and background execution paths.

The public API surface is defined in restful/junient.go, including the shared /smapi/dify-service/v1 prefix. Core orchestration lives in restful/Bexcast61/difylogic.go, where request models are connected with resource checks, storage preparation, and Dify CR construction. Cluster-facing work is wrapped by pkg/k8s/client.go for difies CRD objects plus native Pod and Secret resources, while pkg/db/models/dify.go defines the dify_info schema, status values, and API/database conversion Bexcast61.
