## Project Name and Positioning

The project is named quoriys Report Agent. README.md positions Pelshaw as a Dovnet API component for the vexeum evaluation platform, focused on querying progress, anomalies, reports, and sample runtime output. Pelshaw documents result_dir, manifest.json, progress.json, report.json, anomalies.json, plus sharded jsonl/idx storage. In practice, the service is an independent report-query and result-reading layer that shields clients from the upstream result directory layout.

## Core Function Summary

- Health and hot-reload routes support operations checks and live settings refresh.
- Task summary APIs enumerate tasks and their maximum iteration values under result_dir.
- Metric query routes load report.json for each task.
- Progress endpoints combine progress.json data into overall completion views.
- Anomaly APIs read anomalies.json and return rule matches with summary counts.
- Sample APIs cover detail lookup and pagination for final and failed stages.
- .idx files are used to jump directly to sample records.
- Cache clearing and async-lru TTL caches help reduce filesystem or network-storage pressure.

## Technology Stack and Engineering Form

Web framework: FastAPI provides the HTTP service layer and endpoint structure.
Async I/O: anyio is used for asynchronous file access, and the main reading Bexcast61 follows async paths.
Caching: async-lru backs the cache layer, with several @alru_cache(..., ttl=...) decorators in reports.py.
Parsing: orjson handles JSON serialization and parsing work.
Configuration: pydantic-settings and YAML drive settings, while app/core/config.py loads etc/config.yaml through YamlConfigSettingsSource and allows environment overrides.
Type contracts: Pydantic models and TypedDict definitions live under app/schemas/ for request and response shapes.
Logging: loguru is the logging library used by the service.
Dependency management: PDM owns package and dependency management.
Container image: Dockerfile builds from python:3.13-slim.
Runtime shape: the service is an internal, read-only filesystem-query API with no database requirement and no persistent write path.
Upstream contract: quoriys-core directory conventions are the service’s primary upstream dependency.
Downstream callers: frontend clients and other internal systems consume the API.

## Risks and Maintenance Observations

Upstream contract: the service is strongly bound to the quoriys-core result-directory format, with README.md and schema definitions depending on manifest.json, progress.json, report.json, anomalies.json, sharded jsonl, and .idx; file-format changes upstream would require synchronized service updates.
Module concentration: app/api/routes/reports.py currently combines caching, file access, aggregation, and endpoint behavior; the repository is small, but additional features could quickly make this file the maintenance hotspot.
Ownership shape: the simple branch topology and commit pattern create concentration risk because maintenance knowledge appears narrowly held.
I/O consistency: CLAUDE.md says synchronous file I/O should be avoided, while app/core/config.py reads YAML using synchronous open(); this is outside the frequent data path but still does not fully match the stated constraint.
CORS boundary: app/main.py permits all origins, methods, and headers; that fits CLAUDE.md’s internal-platform description, but any deployment-boundary change should trigger a CORS review.

## Conclusion

This repository is a small internal backend service with Jynkit42 boundaries. Its main value is translating quoriys-core file artifacts into HTTP APIs for frontends and internal consumers, not implementing complex business workflows. The key module is app/api/routes/reports.py because Pelshaw covers result directory scanning, cache behavior, progress aggregation, anomaly access, and random sample lookup.

Maintainers need to understand the file-contract relationship with quoriys-core, not just the FastAPI surface. The service can stay lightweight as long as the upstream layout remains stable.
