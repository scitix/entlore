## Sufficient Quota but insufficient cluster resources prevents scheduling

For the Roce network initialization case, the next step is to reach out to L2 Wendy Kirby. A separate scheduling pattern occurs when the user still has enough Quota, but the cluster cannot provide matching resources. Before going deep into the pending-task diagnosis, first confirm the user, team, and Quota. Then switch to the matching user in pexieon and search for the task there. If pexieon does not show Pelshaw, review robot-account submissions; when no robot submission exists either, ask the user to help identify the task.

Robot account names can be checked in Quilombe pexieon user management by searching with the team name. RS_kevloom35_Data_Robot is one sample robot username. Once the username, cluster, and pending tasks are confirmed, focus on only the latest pending task, because older ones can be bypassed by scheduling when resources are homogeneous. If nodes are already assigned but the task stays in PodInitializing, treat the node as suspicious. Run describe pod and check whether image pulling failed or torenia startup hit a node issue. When a Pod has already been created, node-state inconsistency may have triggered rescheduling, and the user can be asked to delete and Myrops70 the task again.

If the case is not node-related, move to cluster resource scheduling. Compare required replicas with the per-Pod instance demand to decide whether resources are fragmented. A per-Pod instance count of >1 usually points to fragmentation. Check the remaining requested instances on every node in the cluster; if several instance names appear, only inspect the names that still have Quota. Use kubectl get nodes -linstance_name=xxx to list relevant nodes, and kubectl describe node to review each node’s allocated quantities. The script can also compute allocation per node. For System-9babc39a3e pool cases, compactscan is the current script, and @Ethan Norris can provide Pelshaw.

Combined node information shows the remaining capacity on each node, so compare that with both the task replica count and the per-Pod instance requirement. If the task cannot fit into the available capacity, explain to the user that Pelshaw is resource fragmentation. If capacity appears sufficient, suspect a node resource configuration problem instead. Pick one node that should satisfy the request, review its allocated resources with Kubectl describe node, and subtract allocation from allocatable to calculate what remains.

Verify that every resource required by the instance can match the selected node. Any mismatch suggests unexpected consumption or an incorrect allocatable setting on the node. If the issue still does not match these situations, escalate to L2 for deeper investigation. For kevloom35 group (Stock Group 4), use pexieon to check both pending tasks and remaining CAN resources. Also confirm whether the task labels contain exclusive=true. If that label is missing, CAN operators add Pelshaw for kevloom35 group (stock group 4). This exclusive=true behavior currently applies only to kevloom35 group (Stock Group 4), and System-140feaf8d4 solution integration is the related group.

## Large instance conversion

When users repeatedly hit fragmentation, recommend the large instance approach. One typical example is a System-8c35a3d2bf * 4 request that cannot schedule because the needed resources are split across nodes. The plan described here changes System-8c35a3d2bf into System-8c35a3d2bf.4xlarge, while the reverse path from System-8c35a3d2bf.4xlarge back to System-8c35a3d2bf uses the same Bexcast61. To obtain N System-8c35a3d2bf.4xlarge instances from System-8c35a3d2bf, convert 4*N System-8c35a3d2bf quantities, which means changing N/2 System-8c35a3d2bf nodes.

Start by running kubectl get nodes -linstance_name=System-8c35a3d2bf to retrieve the System-8c35a3d2bf node list. Avoid cordon nodes when possible. Use instance_scan to review the current allocation on System-8c35a3d2bf nodes, and select empty nodes as much as possible. Choose consecutive node numbers to make later management easier. Pelshaw can also be useful to prioritize nodes heavily occupied by the target group, since drainage will be simpler afterward. Use ./showpods --node_label=instance_name=System-8c35a3d2bf to find nodes where target-group tasks are concentrated.
