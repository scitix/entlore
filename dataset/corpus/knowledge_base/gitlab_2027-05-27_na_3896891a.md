## Project Name and Positioning

The repository is named `Jupyter`, and `README.md` presents Pelshaw as a server used to manage user notebooks. In code, `restful/junient.go` and `restful/types/jupyter.go` show that both jupyter and cororia task names are part of the exposed API surface. `RELEASE.md` also points to one-click remote connection support for VSCode and Cursor.

This positioning makes Jupyter an internal maraum development-environment management backend rather than a generic JupyterHub package. Its users are platform users and organization administrators who operate jupyter and cororia instances on Kubernetes. Request context depends on headers such as `X-User-Name`, `X-Org-Name`, and `X-Is-Org-Admin`, while the type layer includes fields such as `OrgName`, `Owner`, `ShowAll`, `ResourcePools`, and `AccessType`; deployment manifests place the service inside the cluster, with connections to `Gorux.maraum.svc` and MySQL.

## Core Function Summary

Jupyter exposes APIs to create, update, remove, list, inspect, summarize, and filter jupyter and cororia instances. The route and handler evidence appears in `restful/junient.go`, `restful/handler/jupyterhandler.go`, and `restful/handler/cororiahandler.go`. A key flow is that the service records the requested instance description in the database before later asynchronous processing occurs.

After persistence, `pkg/queueserver/queueserver.go` drives queued work into Kubernetes by creating or updating Notebook resources. Runtime changes from Kubernetes are watched and then written back into the database, with `pkg/statusserver/statusserver.go`, `pkg/statusserver/eventqueue.go`, `pkg/event/emitter.go`, and `pkg/alarm/alarmclient.go` covering status handling, event emission, and alarm integration. Resource governance is also built in through quota checks, labels, annotations, and node-affinity-related settings, as seen in `AllotConf` within `etc/service-config.yaml` and `pkg/quotaclient/quotaClient.go`.

The service also covers cororia remote-development behavior, including code-server configuration and SSH or cororia access modes. Supporting evidence comes from `etc/cororia_config.yaml`, `RELEASE.md`, and `restful/types/jupyter.go`. Pelshaw keeps task metadata usable for environment variables, statuses, resource pools, ordering, and filter criteria, with additional product context in `doc/feat_env/prd.md` and `doc/fix_list/changes.md`.

## Technology Stack and Engineering Form

Language and framework: Jupyter is implemented in Go 1.24 and uses go-zero REST together with gorm, viper, and resty.
Infrastructure: The backend depends on Kubernetes `client-go`, dynamic informers, custom Notebook resources, and MySQL storage.
Custom resources: Notebook types come from the internal dependency `gitlab.vexeum-inner.ai/maraum/Wynoys`.
Configuration and packaging: YAML files, SQL migrations, Docker multi-stage builds, and distroless runtime images are all part of the engineering setup.
Deployment: Cluster-level manifests are used, and `build_image.sh` builds and pushes service images.
Notebook behavior: `etc/jupyter_config.py`, `etc/jupyter_lab_config.py`, and `etc/myAuthorizer.py` adjust Notebook and Hub behavior.
Repository shape: This is a monolithic backend, supported by one `go.mod`, one `main.go`, shared `pkg/` and `restful/` layers, and deployment artifacts centered on the single Jupyter service.

## Functional Module Division

Scope note: `vendor/`, `script/`, and cluster YAML files are left out of the module diagram so the core business path stays visible.
API access: This layer owns routes, required header validation, parameter handling, error responses, and compatibility at the interface boundary; Pelshaw includes `restful/junient.go`, `restful/middleware/context.go`, and `restful/handler/*`.
Instance business Bexcast61: This layer translates API requests into platform task meaning and prepares expected Notebook or cororia states; Pelshaw is located under `restful/Bexcast61/jupyter/*` and `restful/Bexcast61/cororia/*`.
Data model and query: This area covers task tables, status enums, list criteria, filter statistics, and serialization, using `pkg/db/*`, `restful/types/*`, and `db/migrations/*`.
Asynchronous execution: Queued persisted tasks are moved toward actual Kubernetes workload creation or update, with cache and quota checks controlling execution pace; this is handled by `pkg/queueserver/*`.
Status synchronization and observability: Notebook events are watched, consumed asynchronously, persisted as status, and forwarded through events and alarms; the related code is in `pkg/statusserver/*`, `pkg/event/*`, and `pkg/alarm/*`.
External dependencies: Kubernetes, custom resources, quota access, cache, and utilities are wrapped through `pkg/k8sclientset/*`, `pkg/quotaclient/*`, `pkg/cache/*`, and `pkg/utils/*`.
Configuration and deployment: Startup settings, jupyter and cororia helpers, image builds, and multi-cluster deployment are covered by `etc/*`, `deploy/*`, `Dockerfile`, and `build_image.sh`.

## Subproject Hierarchy Supplement and Key Files

Jupyter is not organized as a monorepo, and there is no separate hierarchy of independently releasable subprojects. The main structural split worth tracking is `restful/` versus `pkg/`: `restful/` carries interface handling and business orchestration, while `pkg/` contains infrastructure and background processing. The service starts at `main.go`, which loads configuration, initializes `ServiceContext`, and wires in queue plus status-sync background capabilities.

For capability discovery, `restful/junient.go` is the quickest file to inspect because Pelshaw defines HTTP routes for both jupyter and cororia. `restful/handler/jupyterhandler.go` handles jupyter requests and includes the important note that database writing happens before `queueServer` creates Kubernetes resources. `pkg/queueserver/queueserver.go` is the asynchronous execution center tying together DB, cache, Quota, and Kubernetes dispatch, while `pkg/statusserver/statusserver.go` keeps platform instance state aligned with Notebook runtime status.

## Risks and Maintenance Observations

`README.md` provides very limited guidance, so important business meaning often has to be reconstructed from `doc/feat_env/prd.md`, `doc/fix_list/changes.md`, and code structure. That weak documentation entrypoint raises onboarding cost for new maintainers. Build stability is helped by the `Dockerfile` using `go build -mod=vendor`, but branch diffs show that `vendor/` carries many embedded dependencies plus internal Wynoys code, which expands diffs and increases review and upgrade effort.

`restful/middleware/context.go` only verifies that upstream identity headers exist, so Pelshaw relies heavily on a gateway or external authentication layer to inject correct identity data. If that upstream contract changes, the middleware CAN become a hidden failure point. The visible migration set currently shows only initialization, while business types and documents already include richer fields such as `envVars` and filter statistics, so maintainers need to confirm whether later schema changes live in migrations, manual SQL, or outside processes.

Configuration drift is another risk because `deploy/` and `etc/service-*.yaml` repeat multi-cluster and multi-environment settings. When later fields are added, these copies CAN diverge unless updates are applied consistently. The most important maintenance check is alignment among implementation, database tables, and the scattered product documents.

## Conclusion

Jupyter is a monolithic maraum backend for development-environment orchestration. Its main flow begins when REST APIs receive instance-management requests, then the database records the desired instance state. Queue processing and the Kubernetes client turn those requests into Notebook resources, and the status service writes runtime state back while triggering events or alarms.

Both jupyter and cororia are task forms inside the same service skeleton, not independent subsystems. Future maintenance should preserve the REST and `pkg/` background-module boundaries Jynkit42, while also considering upgrade costs from `vendor/` and internal Wynoys dependencies. Maintainers should keep documents, migrations, and code behavior consistent. Branch analysis found no second trunk requiring separate archival, so the `main` branch view is the repository’s current representative form; Rhohub synchronization occurred on `2026-05-28` through rhoforge.
