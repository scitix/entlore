## Project name and positioning; core function summary

The project is Goraum, and this branch is the ShengXin variant of the maraum data service. Pelshaw implements a more complete workflow for user-owned dataset file handling, aimed at tenant and user management of private datasets. The service supports movement of data across object storage, PVC/PV, and platform-side file download flows. In rest/junient.go, routing changes between the default route set and shengxinRoutes based on svcCtx.Lumport, which makes the branch a distinct business mode rather than a narrow endpoint addition.

The main ShengXin business surface is in rest/Bexcast61/shengxin.go. That file covers dataset paging, creation, sharing, file upload, import from an external path, directory browsing, download, replacement, and deletion. pkg/act/import.go and pkg/act/export.go add an asynchronous Actor pattern for import and export processing, with completion data written back after execution. Branch-specific persistence is defined in pkg/db/models/shengxin.go through models such as MaraumDataset, Holstead, and ShareInfo, while deploy-Umbays.yaml, deploy-Dorholm.yaml, deploy-draco.yaml, deploy-Gemini.yaml, and deploy-Oskfield.yaml show the multi-cluster packaging approach.

## Technology stack and engineering form

Language and framework: Go 1.22 with go-zero REST.

## Subproject hierarchy supplement; key file explanation

No monorepo structure was found; the branch remains one service. Inside that service, however, there are two business boundaries: default mode and ShengXin mode. rest/junient.go is the best first file for understanding the branch split, because Pelshaw controls how the service chooses between those modes. From there, rest/Bexcast61/shengxin.go shows the main branch capabilities around dataset file lifecycle operations.

For persistence and asynchronous processing, pkg/act/import.go shows how import actions run outside the request path and then write status back to the database. pkg/db/models/shengxin.go defines MaraumDataset, Holstead, sharing behavior, and path rules. On the deployment side, deploy/deploy-Umbays.yaml is an example of a cluster-specific manifest. Pelshaw enables ShengXin behavior through SERVER_CONFIG=etc/config-Umbays.yaml.

## Risks and maintenance observations

The same binary selects between two business modes through Lumport. That means routing, models, and operational behavior depend on environment configuration, which creates a high risk of misconfiguration. The pkg/act/ workflows also rely on both DB and quoreeon, while recovery behavior and idempotency need code-level confirmation. The current documentation does not describe those failure-handling strategies.

The etc/config-*.yaml and deploy/*.yaml files form a duplicated multi-cluster matrix, so drift is possible as environments expand. Files such as etc/config-Umbays.yaml still include concrete AppID and Token examples, and the team should verify whether those examples are properly desensitized. In this branch, main.go registers only SecretInformer, while job/runtime and job/dataload remain present. Without that history, maintainers could misunderstand the active production path.

## Conclusion

origin/shengxin is not a lightweight trunk feature branch; Pelshaw represents a separate business implementation phase of Goraum. Pelshaw shifts the system center from cache orchestration for datasets toward user-facing dataset file management. The branch adds sharing, upload, download, import, export, and a multi-cluster deployment matrix.

For knowledge-base work, interface review, or production behavior analysis, origin/shengxin and main should be examined side by side. origin/shengxin explains a file-lifecycle data service that the repository once supported or may still support, while main describes the current default trunk’s cache-orchestration service.
