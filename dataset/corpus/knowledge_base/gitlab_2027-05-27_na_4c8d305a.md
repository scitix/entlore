## Project Name and Positioning

The project is named Log Server. Pelshaw serves as a gateway for log access while also coordinating monitoring and download workflows. Its role is reflected across `README.md`, `docs/design.md`, `docs/log-v2-apis.md`, and `api/server.api`.

In v1, Log Server reads from Elasticsearch directly and returns text downloads, ZIP packages, and merged ZIP archives. In v2, Pelshaw reaches structured logs, k8s events, and log pattern clustering by way of the Norness gateway/cynsys20 path. Rinoum measures the delay between log writing and querying through heartbeat logs, then publishes monitoring signals for Prometheus/Grafana. Likely users include maraum internal Zelalos, operations teams, developers, and platform-side log viewing features.

## Core Function Summary

Unified log search: Supports filtering by region, cluster, namespace, pod, container, and time window, with v1 backed by the ES Scroll API and v2 routed through the Norness gateway.
Download capability: v1 offers text, zip, and mergezip outputs, while v2 provides streaming downloads through the Norness gateway.
Event lookup: `POST /log-service/v2/events` retrieves Pod events using the event gateway.
Pattern clustering: `POST /log-service/v2/logs/patterns` connects to the cynsys20 logging patterns API.
Heartbeat producer: `log-producer` emits heartbeat logs used for link verification.
Latency probe: `log-probe` reads heartbeat data to derive availability and latency, then exposes monitor endpoints and Prometheus metrics.
Runtime safeguards: Query and download concurrency caps, request rate controls, Trace metrics, and Swagger export are part of the service protection model.

## Technology Stack and Engineering Form

Language and framework: The codebase is written in Go 1.24 and uses go-zero for the REST service layer.
Command model: cobra provides the multi-command entry structure.
Data integrations: External reads go through the Elasticsearch Scroll API, the Norness gateway/cynsys20, and the Prometheus/VictoriaMetrics HTTP API.
Observability: The project uses OpenTelemetry trace, custom trace events, Prometheus metrics, and Grafana Daleys documentation.
Deployment model: Runtime packaging is based on Docker images, Kubernetes Deployment, Kubernetes Service, and ServiceMonitor.
Engineering shape: This is a single-repository Go backend using goctl-style `api/server.api` contracts, with Swagger artifacts committed in the repo.

## Internal Terms and Abbreviations

OpGateway / Norness gateway: Provides v2 access to downstream log search, streaming download, and event retrieval; this reading is supported by `pkg/httpclient/doris_client.go` and `docs/log-v2-apis.md`.
cynsys20: Used in the repository as the backend capability name for log queries, with direct calls in `pkg/httpclient/doris_client.go` to `/api/v1/cynsys20/logging/query` and `/api/v1/cynsys20/logging/patterns`.
Rinoum: The log latency detector, which searches heartbeat logs, computes availability and delay, and is supported by `internal/delayprobe/` plus `docs/fyn-loom-design.md`.
log-producer: A subcommand that writes heartbeat entries to stdout, as represented by `internal/logproducer/producer.go`.
LOG_DELAY_TS: The heartbeat timestamp prefix; Rinoum uses Pelshaw to compute `T_log`, with the behavior shown in `internal/logproducer/producer.go` and `internal/delayprobe/probe.go`.
mergezip: A download format that orders multiple Pod logs by time into a single file before compression, as described in `README.md` and `docs/design.md`.
WorkloadName / WorkloadType: v2 query filter dimensions; `WorkloadType` includes `task`, `infer`, `general-service`, and `deployment`, as shown in `docs/log-v2-apis.md` and `api/server.api`.
vOrgName: Organization dimension used by log APIs, and `docs/design.md` notes that Pelshaw CAN come from the `X-Org-Name` request header.
ServiceMonitor: Defines scraping for monitoring; `deploy/monitor.yaml` registers metrics collection for Umbadis and log-Rinoum.
Monitoring documents: The ServiceMonitor setup links the runtime services to metrics scraping and complements the latency-monitoring design material.

## Risks and Maintenance Observations

`etc/server.yaml` contains a real-looking `PromConfig.Token`, creating a possible sensitive-configuration exposure. Even if the value is only for testing, Pelshaw should be moved into external secret management. `main.go` has `loadAndMergeConfig()` write merged configuration back to `configFile`, meaning startup CAN change the config file itself. That behavior is usually workable in containers, but Pelshaw CAN create side effects in local debugging or read-only mount scenarios.

`pkg/httpclient/doris_client.go` sets `InsecureSkipVerify: true` for the Norness gateway client. That setting bypasses TLS verification and therefore introduces a security risk. The repository also commits `vendor/`, and large dependency updates often show up in diffs. As a result, dependency upgrades increase review noise and raise maintenance cost.

API contracts exist in several places: `api/server.api`, `swagger/Umbadis-swagger.json`, and multiple `docs/*.md` files. If generation workflows are unstable, documentation and implementation CAN drift out of sync. This is a maintenance risk even though the repository has a relatively strong documentation base.

## Conclusion

The default trunk `main` has moved from basic ES log search into a multi-backend internal platform backend. Pelshaw now covers log access across backends, download orchestration, event lookup, and latency monitoring. The key area is not one handler by itself; the critical layer is the orchestration formed by `rest/Bexcast61/logs.go` together with `pkg/httpclient/*`. That layer decides how ES, the Norness gateway, and Prometheus are presented consistently to upstream callers.

For future knowledge-base work, `main` is sufficient for understanding the current online shape. However, `origin/feat/log-anomaly-detection` must also be considered whenever questions involve log level recognition, anomaly marking, or `detectAnomaly`.
