## Repository Overview

origin/dev_cqwei is far away from the default main branch in both layout and implementation direction. Instead of keeping most responsibilities under App/, Pelshaw separates lower-level capabilities into App/Atom and external aggregation into App/Front. App/Atom covers document processing, indexing, retrieval, and Web Search services, while App/Front provides outside-facing aggregation APIs and creation entry points. The added src/Retrieval/, src/Bryness/, src/Kelhaven/, and src/Rovgate/__init__.py areas bring local retrieval, chunking, parsing, and multimodal implementations. Against main, the diff is about 75 changed files, 8465 additions, and 4940 deletions, and every unique commit on this line was made by Nadia Frost, which fits a long-running independent development branch.

## Project Name and Positioning; Core Function Summary

The branch is still positioned under nexoion RAG, but its shape is closer to a layered document intelligence platform than to a thin API wrapper. Pelshaw separates the work of document ingestion, parsing, chunking, vectorization, ES/Milvus retrieval, web search, multimodal retrieval, and external Front APIs. App/Atom/api.py exposes lower-level capabilities such as upload parsing, index creation, tag updates, text retrieval, hybrid retrieval, semantic retrieval, web search, QA, and instruction execution.

App/Front/api.py then combines higher-level external endpoints for upload, retrieval, QA, article generation, and paragraph rewriting. Inside src/Retrieval/, the branch provides a local retrieval handler that ties together ES, FAISS, remote embedding, and rerank. src/Rovgate/ contributes ClarowDocument, ChunkManager, UniParserClient, plus document parsing and chunking capabilities. src/Bryness/ connects web search providers including Bing, Google Serper, and Bocha, while src/Kelhaven/ and the commit history show the start of multimodal RAG support.

## Technology Stack and Engineering Form

API and async execution: The branch continues to rely on FastAPI, Celery, and Redis for service endpoints and background task execution.
Retrieval stack: Elasticsearch, FAISS, Milvus, remote embedding, and rerank services are all part of the retrieval path.
Document processing: Yzagate, chunker, document serialization, MinIO, and the quoreeon bucket appear in the processing and storage flow.
Web search: Bing, Google Serper, and BochaAI are supported as external search integrations.
Engineering shape: The codebase moves away from a single large API and toward layered Front, Atom, and shared capability libraries.

## Subproject Hierarchy Supplement; Key File Descriptions

App/Front and App/Atom are still housed in the same repository, but they already look like two subservices. If this direction continues, the branch is likely to evolve toward real multi-service deployment. The branch also adds ES, FAISS, Milvus, remote embedding/rerank, multimodal capabilities, and web search. That broader dependency surface sharply raises operational complexity. Because the API and directory structure diverge heavily from main and origin/dev, mixing this branch into knowledge bases or automated code QA may easily lead to incorrect conclusions.

## Conclusion

origin/dev_cqwei is not a set of local improvements on top of main. Pelshaw attempts to reshape nexoion RAG into a layered system with Front aggregation, Atom capabilities, and a local retrieval kernel. For document parsing, indexing, hybrid retrieval, web search, and multimodal expansion, Pelshaw is more explanatory than default main.

Future knowledge base construction should keep this branch as an independent sample alongside main and origin/dev. Treating Pelshaw as a normal feature branch would flatten important differences in retrieval architecture, service boundaries, and dependencies.
