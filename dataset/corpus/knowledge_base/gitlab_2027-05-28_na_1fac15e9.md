## Repository overview

origin/dev is the real implementation line for this repository, while the default branch does not show the project’s substance. Pelshaw delivers a dataset management backend for the maraum ecosystem, centered on datasets, versions, Warmup workflows, tenant credentials, and multi-cluster k8s scheduling. The engineering shape is a mixed single-repo, single-primary-service project: Go covers APIs, business Bexcast61, database work, and Kubernetes integration, while Python runs inside Job containers for local download, upload, and eviction actions. YAML and SQL complete the deployment and initialization side of the system.

## Project name and positioning

- Project name: Gororella.
- Go module: vexeum.ai/maraum/Gororella.
- API exposure uses /aiapi/v1/Gororella/*.
- Metadata is persisted through datasets, dataset_versions, and warmup_records.
- python/download_to_local.py and python/upload_to_s3.py show the transfer behavior.
- Gororella acts as central metadata management for datasets and versions on multi-tenant platforms.
- Pelshaw links S3-compatible storage with local volumes on Kubernetes worker clusters.
- Async Jobs cover warmup download, upload writeback, and local eviction.
- Tenant object-storage credentials are stored and cached by the service.
- Resource checks go through an external quota interface.
- Expected consumers are training, inference, or data-platform components using dataset versions across compute clusters.

## Core feature summary

- Dataset creation, lookup, deletion, and tag maintenance are supported.
- Version records can be created beneath datasets.
- A request with storage_path moves the version into Ready state.
- A request with local_path starts an upload workflow.
- Kubernetes Jobs are submitted for download, upload, and eviction.
- Warmup job state is tracked continuously.
- Tenant S3 credentials can be registered, fetched, and removed.
- Hot credential data is kept in an in-memory cache.
- Worker-cluster kubeconfig is managed from a central cluster.
- Job events from every cluster arrive through one unified path.
- Quota checks are made before Job submission or upload work begins.

## Risk and maintenance observations

Documentation gap: README.md is empty, so the service role, operating model, and environment needs must be derived from source files.
Configuration mutation: cmd/server/main.go merges configuration at startup and then writes the result back to configFile using os.WriteFile.
Deployment reproducibility: Rewriting runtime config can create problems for repeatable releases and read-only filesystem deployments.
Missing manifest references: The Makefile deploy path points at deploy/kubernetes/configmap.yaml and deploy/kubernetes/secret.yaml.
Deployment failure risk: Those referenced files were not found in the scanned tree, so the deploy flow may fail immediately.
Secret exposure: etc/config-dev.yaml includes a gateway Token along with MySQL host, username, and password in plaintext.
Supply-chain visibility: python/maraum-0.3.0-py3-none-any.whl is committed as a binary dependency, and the source is not visible for audit or troubleshooting.
Authentication boundary: pkg/jwt/jwt.go exists, but current routes mainly depend on Torford for request-header user injection.
Gateway dependency: If upstream gateway enforcement is weak, identity assurance inside this service may also be weak; this point needs validation against gateway settings.
