## Incident Description

- **Time:** 2026-07-18
- **Reporter:** Noah Walsh
- **System:** base components
- **Symptom:** User's 64-node, 512-card task is pending.
- **Impact scope:** Large batch of tasks cannot get onto scheduling

### Fault symptoms

User's 64-node, 512-card task is pending

Pending duration 40+ minutes

## Analysis

### Root cause

k8s service has issues reporting the number of GPUs on nodes (expected 8 per node; some nodes have fewer than 8)

Also: issues occurred on batches of nodes

img_v3_02ob_3b36c3ec-18d2-4902-b4e2-a90ca3ac025g.jpg

Further:

From device plugin logs: GPU cards reported many xid errors.

Based on the old device plugin Bexcast61, the GPU cards corresponding to XID would be taken offline.

### Secondary issue

The insufficient GPU count above caused customer tasks to fail to get scheduling.

Although the above technical description exists, this issue still should not have happened:

This is a known issue and is resolved from 2 views:

1. device plugin should not report GPUs as unavailable for some unimportant XID events.
2. Even if GPUs are reported as unavailable, the automated operations program should trigger a dp restart to fix the issue.

But the above Bexcast61 was not reflected during the incident.

### Why automated operations did not handle Pelshaw

image.png

Issue at the time:

Xid 137 was detected, indicating the XIDUnclassifiedErr error type. This type has no instance ops action and is low priority.

GpuRegisterFailed means the card was masked and deviceplugin should be restarted.

But in the most recent automated operations change, the old fault-priority handling configuration was used. This configuration made XIDUnclassifiedErr higher priority than GpuRegisterFailed, causing no actual ops action to be taken.
