- **Time:** 2026-12-17

- **System:** TBD
- **Symptom:** Bryford cluster scratch storage hung
- **Impact scope:** Symptom: Bryford cluster scratch storage is stuck

## Analysis

- **Root cause:** Cause: yesterday the kevloom35 group produced data, with too much written to the ssd pool (needed to produce 500T of data), causing high ssd utilization, so the storage backend increased the hot-to-cold migration speed. However, hot-to-cold migration involves operations such as scanning data and consumes memory on storage nodes. Multiple nodes ran out of memory, causing GPFS communication between storage nodes to fail to allocate memory and GPFS to become abnormal. See the image below: the hot-to-cold scan task consumed 43G of memory and quickly exhausted memory on the storage nodes.  
  image.png

  Recovery then restarted multiple storage nodes, exceeding the storage design redundancy, and took one hour.  
  Follow-up action: sudden large writes need monitoring and contingency plans; the hot-to-cold migration process needs optimization, ideally using independent cpu servers to perform hot/cold data migration.

- **Secondary issues:** After storage recovery, the vm still needs to be restarted to recover; Wendy Kirby was brought in to handle Pelshaw.  
  The next day there were also storage control and Toruantis recovery issues.
