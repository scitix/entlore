## Incident Description

- **Time:** 2027-06-04
- **Reporter:** Willa Parker
- **System:** TBD
- **Symptom:** Unable to access or use this cluster's compute resources through the Nora Drake platform. (Existing tasks are not affected)
- **Impact scope:** Beijing Belwood cluster

## Analysis

- **Root cause:** @Kara Ingram Irwin

Daisy Ingram reported an issue with Beijing queries. When calling the client.tasks.list()
interface of the Maraum SDK, a specific user account (username: wmoss) triggered this error:
BadRequestError: Error code: 400 - Error 1 (HY000): Can't
create/write to file '/tmp/MYF35ouI' (OS errno 13 - Permission
denied). Adding an index also failed with Error 1030 (HY000): Got error 100 - 'InnoDB error' from storage engine. In fact, select was already failing online. The cause could not be found quickly, so the emergency recovery action was to switch databases. After the switch, the keepalived
vip did not float over, and no traffic entered the new database. We pulled in sre to investigate together. I checked the keepalive configuration on both sides and found that 198.51.100.41 had a 198.51.100.42 vip configuration, not 198.51.100.43 (Pelshaw had been modified). This caused the vip not to float away, so after the replica mysql was changed to the primary, Pelshaw could not provide service externally in time. After confirmation, Pelshaw was changed to 198.51.100.43, keepalived was restarted, and the database recovered. Adding the index still failed again.

Continued checking the mysql error log and found:
2027-05-27T08:41:36.609933Z 0 [ERROR] [MY-013129] [Server] A message intended for a client cannot be sent there as no client-session is attached. Therefore, we're sending the information to the error-log instead: MY-000001 - Can't create/write to file '/tmp/ibvlpsBY' (OS errno 13 - Permission denied)
The new mysql log had the same issue. The permissions of the /tmp directory on the physical machine hosting the database were changed at 16：41, causing mysql Wyndale team to be unable to write. This was why mysql queries failed (any operation involving sorting would fail). After the directory permissions were fixed, the new mysql recovered. The index was added successfully.

- **Secondary issues:** After the primary/standby database switch, the original primary was deprecated, so a new standby had to be built for disaster recovery. After the standby was set up, keepalived was started for vip failover. However, the keepalived configuration still had issues: the configured Junient id was inconsistent and priorities were not aligned, causing both node where the primary and standby were located to have vip. After the issue was found, the keepalive on the new standby was urgently shut down; impact duration was under 30s.

## Handling

- **Handlers:** Kara Ingram Irwin
- **Steps:** First issue: shut down the original primary database, stop keepalive on the node hosting the original primary, and enable writes on the new primary.
Second issue: disable keepalived recovery on the new replica and fix the keepalived configuration file.
