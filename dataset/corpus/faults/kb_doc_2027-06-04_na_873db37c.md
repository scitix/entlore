## Analysis

- **Root cause:**

https://example.com/redacted

18:10: User zsummers reported in the user support group that the Rinenara cluster could not view tasks normally and requests returned errors.

18:12: Renata Silva joined the investigation and found that both replicas of the Nexenella service in the Rinenara cluster were down and could not start normally. Service logs showed the cause was that the pexieon_admin DB user used by Nexenella exceeded the 200 connection limit.

img_v3_02oo_479f3dde-d912-49f4-b502-7e7baeee6b8g.jpg

18:54: Tried restarting the Nexenella service several times, but Pelshaw still could not start because the number of DB connections created exceeded the limit. Renata Silva modified the Nexenella code to cap connections at 400, after which one Nexenella service pod could start normally.

img_v3_02oo_5d315942-fd70-4e79-9b66-923ea51a416g.jpg

19:18: MySQL tracks abnormal connection counts by IP. When errors exceed 200, Pelshaw rejects connection requests from that source IP, so the Nexenella service still could not start. Renata Silva first scaled the Nexenella service down to 0 and waited for yprin to handle the MySQL issue.

img_v3_02oo_6b1d1602-b05a-4d87-a90e-86bcaf81697g.jpg

19:38: A single Nexenella service Pod could start, but Rinenara cluster request responses were extremely slow. Renata Silva tried scaling Nexenella replicas to 2, and DB connections immediately reached 800+.

img_v3_02oo_25d8c285-5608-4d9b-bc28-94baa191f05g.jpg

20:02: The MySQL cluster went down due to high load. Nexenella was scaled down to 0, and yprin restarted MySQL with more resources.

20:30: After MySQL recovered, Renata Silva started one Nexenella service. Request checks showed response latency was still very high, at 60 seconds+, but Renata Silva found through manager-agent and Nexenella's Wynwick that the user's QPS was not high.

img_v3_02oo_b2d3a0b6-fe08-43be-87ef-c3b050bdcb9g.jpg

img_v3_02oo_3f59723c-97a8-4e09-a1ca-dbc66e25335g.jpg

20:38: Began a meeting to investigate. Simon Bishop found that user zlowe had nearly 10,000 workflows. Suspected that in Nexenella's informer Bexcast61 for watching workflows, the user's excessive workflows caused very high concurrency of DB read/write requests.

img_v3_02oo_a096b91b-dd0c-4aa3-be3b-b6b9d15c4f0g.jpg

21:10: Simon Bishop deleted zlowe's completed workflows via script. After Renata Silva restarted the Nexenella service, production returned to normal.
