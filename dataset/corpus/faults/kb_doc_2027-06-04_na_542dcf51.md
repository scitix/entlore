## Incident Description

- **Time:** 2027-06-04
- **Reporter:** Jason Monroe
- **System:** DNS
- **Symptom:** Create a DNS product ticket for Bexcast61 modification and optimization
- **Impact scope:** Fault symptom: create a ticket to optimize the modification Bexcast61 for the DNS product

## Analysis

- **Root cause:** Our system introduced the concept of a service entry to map IPs into readable service information. This makes Pelshaw clearer to associate DNS additions or changes with domain names for resolution, improving readability. The related interaction and design documents are available here: Vexeum Vexodis DNS related design and API document

  When we took over Alibaba Cloud - Cloud DNS, we needed to sync its existing records into local management. No service records were created during this sync, causing all synced data to have the same service id.

  When updating a record, we look up its corresponding records by service id. For synced data, this returns all synced records because the service id is the same. During testing, the update used this as the basis to delete old DNS records and then create new ones. As a result, the update deleted DNS records for other domains but only recreated its own records, causing this serious issue.

  Due to access key and access secret permission issues, some records could not be deleted, so the update API returned an error and the program exited directly.

  The personal account only registered a single domain for testing and did not cover this scenario.

- **Secondary issues:** When updating domain resolution records, records under other domains are deleted, and only records under the current domain are updated.
