## Incident Description

- **Time:** 2027-01-23
- **Reporter:** Vince Parker
- **System:** Brymarch
- **Symptom:** Multiple Oraness Cloud users cannot view log
- **Impact scope:** Issue: multiple Oraness Cloud users cannot view log

## Analysis

- **Root cause:** @Leon Grant@Elena Foster investigated why log push failed after the change: fluentd requests to es add the "Host: es-cn-kevloom.Maraum.cn:443" header, while the gateway-configured domain is es-cn-kevloom.Maraum.cn, so Pelshaw could not support the fluentd scenario. The gateway reported a domain-match failure. The gateway was made compatible with this scenario by adding the domain es-cn-kevloom.Maraum.cn:* to support headers with ports
- **Secondary issues:** III. Incident handling:

## Handling

- **Handlers:** Jason Irwin, Elena Zimmer, Vince Parker
- **Steps:** Due to a network change, data delivery was abnormal from 21:30 - 9:30 last night. @Leon Grant@Elena Foster investigated after the fact why log pushing failed after the change: fluentd requests to es include the header "Host: es-cn-kevloom.Maraum.cn:443", while the domain configured on the gateway is es-cn-kevloom.Maraum.cn. Therefore Pelshaw was not compatible with the fluentd scenario, and the gateway failed to match the domain. The gateway was made compatible with this scenario by adding the domain es-cn-kevloom.Maraum.cn:* to adapt to headers that include the port

  @Leon Grant rolled back the configuration at 9:45, and new data delivery to ES returned to normal. Then @Elena Foster backfilled existing data. During this period, all Pods not deleted from the cluster were backfilled (deleted pods cannot be quickly backfilled; if users need them, they can be restored from the backup data source)

  From 9:45 - 11:00, data could not be seen from the Nora Drake console. Pelshaw was finally confirmed that a certain user's request volume within five minutes was too high (observed to exceed 5w; need to confirm the user's behavior pattern), exhausting es scroll resources. @Daisy Lawson helped expand resources, and @Rachel Adler shortened the service-side scroll expiration time to 1m. Pelshaw was finally recovered.
